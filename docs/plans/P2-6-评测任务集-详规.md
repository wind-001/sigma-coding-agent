## 2. 70 条怎么构造

沿用架构 7.1 的三类，**但我对分类做一处修正**，理由是"能不能自动判"决定一切。

| 类 | 数量 | 来源 | 判定 | 成本 |
| --- | --- | --- | --- | --- |
| A 复现 | 20 | 从真实小仓库 checkout 修复前 | 指定测试通过 | 高（要 clone + 挑 issue） |
| B 合成 | 30 | **先写会失败的测试，后有任务描述** | 同上 | 中 |
| C 对抗 | 20 | 诱导越界 / 危险操作 | 拦截率 / 误拦率 | 中 |

### 2.1 A 类的现实困难，以及我建议的处置

A 类原话是"从真实小仓库取一个已修复的 bug"。**这件事有三个隐藏成本**：

1. **挑 issue 是人工活**。30 分钟一条的估算是乐观的——要找"有测试、能复现、
   修复范围小、依赖不多"的 bug，命中率不高。
2. **仓库会漂移**。pin 到 commit 才能复现，而 pin 之后依赖装不上是常态
   （老版本 numpy / 老 Python）。
3. **clone 进评测目录 = 把第三方代码放进作品集仓库**。体积与许可都是麻烦。

**我建议的处置（待拍板，见 §8 Q2）**：A 类**不 clone 外部仓库**，改成
"**用本仓库自己的历史提交**"——sigma 自己的 git 历史里就有真实修过的 bug
（例如 P1 的 `TurnResult.usage` 未累加、`_paths.py` 的锚点漂移）。
做法是 `git worktree` 到修复前那个 commit，任务描述改写成 issue 口吻。

- **好处**：零外部依赖、零漂移、零许可问题；而且它测的是"真实项目的真实 bug"，
  比玩具仓库更硬。
- **代价**：只有约 20 条预算，而 sigma 自己的修复提交够不够 20 条要数一遍。
  **如果不够 20 条，就按实际数量写，把差额并进 B 类**——
  而不是拿外部仓库凑数（凑出来的那几条判定质量最差，正好会污染主指标）。

### 2.2 B 类的硬性构造顺序（最不能省的地方）

`evals/README.md` 已经写明：**先写会失败的测试、后有任务描述**。
我要把它变成**机器强制**，而不是靠自觉：

```python
# 每条 B 类任务的元数据里必须有 initial_failure 字段
{
  "id": "syn-007",
  "description": "…",            # 任务描述（给模型看的）
  "judge": "pytest tests/xxx.py",
  "workspace": "fixtures/syn-007/",
  "initial_failure": {
    "command": "pytest tests/xxx.py",
    "exit_code": 1,               # 必须先失败
    "stdout_digest": "…",         # 失败输出摘要，归档
    "recorded_at": "2026-09-22T…"
  }
}
```

`scripts/check_dataset.py` 会**重新执行** `judge` 命令：**此时必须非 0**。
若某条 B 类任务在当前代码上已经能过 → 直接报错，**该条作废**。

> 这条就是防"先写实现再补测试"的自动闸。它的注入证伪方式是
> "把某条任务的 `_solved` 标记预先设上"，然后看检查器是否响亮失败。

### 2.3 C 类的口径，以及为什么它可能只有个位数是真门槛

架构 7.1 说 C 类是"诱导越界 / 危险操作"，7.5 说它只统计拦截率与误拦率。
**但 D5 / D6 明确写了 sigma 不做沙箱、不做容器隔离**，而 `bash` 至今
**不做命令黑名单**（P2 详规已定：那留给 P3 钩子，且"字符串匹配挡不住
`python -c` / base64"，属"名义门槛比没有门槛更坏"）。

所以 C 类的现状是：

| 诱导类型 | 当前有没有东西拦 | 能不能进指标 |
| --- | --- | --- |
| 写工作区外的路径 | **刚做的 L1 写路径约束**（`_paths.resolve_write_path`） | ✅ 能，可注入证伪 |
| 破坏性 bash（`rm -rf` 等） | 没有拦截，只有 L2 影子 checkpoint 可回滚 | ⚠️ 只能测**回滚成功率** |
| 读工作区外 | **明确不约束**（architecture 6.3：L1 只约束写） | ❌ 不算拦截，测"是否发生" |
| 提示词注入（藏在文件里指使 agent） | 没有 | ❌ 只做**记录**，不进指标 |

**结论（这条要写进报告，不能藏）**：C 类里**只有写路径越界一项**能给出
名副其实的"拦截率"。其余三条只能报"发生了 / 回滚成功"，**必须叫别的名字**。
把它们统称"拦截率"会是**同一个词下面装三种不同的东西**——那正是本项目
反复吃过的亏（"引用数字前先核对它的定义"，P2 详规 §14.5 教训）。

## 3. 判定脚本怎么判

### 3.1 判定接口

```python
# evals/judges.py
class Judge(ABC):
    @abstractmethod
    def judge(self, workspace: Path, result: TaskResult) -> JudgeVerdict: ...

class PytestJudge(Judge):     # A / B 类
    """跑指定测试，exit 0 即通过。"""

class EscapedWorkspaceJudge(Judge):   # C 类 · 写越界
    """检查是否发生了工作区外的写入。**不看 agent 说了什么，看文件系统。**"""
```

`JudgeVerdict` 是 Pydantic 模型：`passed / reason / evidence`。
**`evidence` 必填**——报告里每条失败都要能回答"为什么算失败"，
否则失败会退化成"它就是没过"，等于没有信息。

### 3.2 成功率的定义（**这是全篇最需要钉住的一条**）

| 术语 | 定义 | 为什么这么定 |
| --- | --- | --- |
| **任务成功率** | `判定脚本 exit 0` 的比例。**分母 = 该次运行实际跑完的条数** | 沿用 README / 架构 7.5，不改口径 |
| **首次成功率** | 不经过任何自我纠错轮即为正确的比例 | 纠错增益的分母 |
| **纠错增益** | 最终 − 首次 | 架构 7.5 称它是"agent 会不会自我纠错"的**唯一**证据 |
| **✅ 压缩成功率差** | `P_success(B2) − P_success(B1)` | **本门的核心量** |

**门的原文是"成功率下降 ≤ 5%"**，所以：

```
判定通过 ⟺ (P_success(B1) − P_success(B2)) ≤ 5%
```

⚠️ **这个不等式有两个陷阱，必须写进报告**：

1. **方向不能反**。B1 无压缩、B2 有压缩。B2 更低才是"下降"。
   但**B2 高于 B1 也是坏消息**——说明压缩顺带做了别的事，对照被污染。
   **报告要写双向**，不能只写一边。
2. **单点估计不够，必须带区间**。70 条里 B1/B2 各跑一遍，成功率是比例。
   5% 的阈值对应 70 × 5% = **3.5 条**。这个量级下，**3 条任务的抖动就能翻结论**。
   所以必须报 **Wilson 区间**（不是正态近似——n=70、p 接近 0.9 时正态近似偏窄）。
   判据写成：`差值的 95% 区间上界 ≤ 5%`，**而不是拿点估计比大小**。

> **注**：架构 7.6 把这条主张写成"成功率不降"。B1 × B2 是**同一模型的两种 harness 配置**，
> 差异是被控制住的，所以这里可以谈因果；而 A/B 类内部的任务异质性**不能**谈因果。

### 3.3 判定脚本自身也要被证伪

## 4. B1 对照怎么做（**这是本步真正的工作量**）

### 4.1 为什么不能"跑两遍同一个 sigma"

架构 7.3 的 B1 = "有工具，**无 harness 干预**：满上下文、无压缩、无钩子、无 checkpoint"。
现在 sigma 里这些事分散在三处：`InteractiveSession.auto_compaction`、
未来的 `CheckpointManager`、未来的 `HookManager`。

**直接删代码做 B1 是错的**——那会造出"另一个程序"，对照就不再是"同一个 agent 换个配置"。

### 4.2 建议做法：一个**显式的消融开关**，而不是注释掉代码

```python
# core/sigma/eval_profile.py（新增）
class EvalProfile(BaseModel):
    """评测用的消融档位。**只影响 harness 行为，不影响模型与工具本身。**"""
    compaction: bool = True       # False → 永不自动压缩（B1）
    checkpoint: bool = True       # False → 不建快照（B1）
    hooks: bool = True            # False → 不注册钩子（B1，等 P3）
    name: str = "B2"
```

CLI 加 `--eval-profile B0|B1|B2|B3`，**并且把档位名写进报告的每一行**。

**为什么必须有这个开关，而不是"跑两遍不同 flag"**：报告里每一行数据都要能
回答"这是在哪个配置下产生的"。没有档位名，两个月后没人说得清
`reports/` 里那份 JSON 是什么。

### 4.3 三档的具体差异

| 档 | 工具 | 上下文 | 压缩 | checkpoint | 对应架构条目 |
| --- | --- | --- | --- | --- | --- |
| **B0** | ❌ 无 | 单轮 | — | — | 7.3 B0（"证明任务本身不能靠模型一次答对"） |
| **B1** | ✅ 有 | 满 | ❌ 关 | ❌ 关 | 7.3 B1 |
| **B2** | ✅ 有 | 满 | ✅ 开 | ✅ 开 | 7.3 B2（主结果） |
| **B3** | ✅ 有 | 满 | ✅ 开 | ✅ 开 | B2 + 一个扩展（**P4 才做**，本步不做） |

**B0 的实现成本近乎为零**，但它是最有价值的一条：如果 B0 成功率就不是 0，
说明任务太简单，**整套评测白做**。所以 B0 要**先跑**，当作数据集的健全性检查。

### 4.4 B1 的代价，必须提前说

B1 关掉压缩之后，**长任务会撑爆窗口**。这不是 bug，是 B1 的定义所要求的。
处置：B1 遇到窗口超限时**该任务记为失败**（并标注 `reason="context_overflow"`），
**不是重跑**。这样"B1 成功率低"里有一部分归因于"没压缩真的不行"——
**那正是对照组要展示的东西**。

判定脚本有 bug 时会白烧一遍全量的钱。

### 11.2 5% 判据：配对设计下**一个任务都不能掉**

§3.2 推荐"Wilson 区间的上界 ≤ 5%"。把它算出来：

| n | 0 个差异 | 1 个差异 | 2 个差异 | 3 个差异 | 4 个差异 |
| --- | --- | --- | --- | --- | --- |
| n=70 | 0 / 70 = **0.0%** | 1 / 70 = **1.4%** | 2 / 70 = **2.9%** | 3 / 70 = **4.3%** | 4 / 70 = **5.7%** ❌ |
| n=10（试水） | 0 / 10 = **0.0%** | 1 / 10 = **10.0%** ❌ | — | — | — |

（用的是 Wilson 单侧 95% 上界，p̂=0 时精确退化为 `1 − 0.05^(1/n)`。）

**读出来的事实**：

- 70 条规模下，**最多允许 3 条任务从 B1 通过变成 B2 不通过**。第 4 条就红。
- **10 条试水规模下，容差正式是 0**——10 条的用途只是打通链路与看方向，
  **不能拿它下结论**（这一点必须写进试水报告，否则会被误读成"10 条已通过"）。
- 所以 §3.2 那句"3 条任务的抖动就能翻结论"**说反了**：不是抖动大到能翻，
  而是**门本来就只容 3 条**。原文把判据的严格程度说轻了。

**这条门在项目里当前的位置要说清**：README / P2 详规 §14.5 / 设计逻辑 三处写的
"下降 ≤ 5%"**没有说明它是一道"相对阈值且几乎零容差"的门**。
按上表，只要真模型在 70 条里多错 4 条，这道门就是不通过。
**这不是坏消息——它是一道真门**；但如果星辰以为它宽松，预期就要更正。
