## 3. 验收门与证据

**验收门：CI 全绿；每条契约都能被一次注入实验证伪。**

后半个条件是关键。P0 实施过程中出现过一个反例（见 4.4 节）：
只配 `layers` 一条契约时，`sigma_tools → sigma_session` 这个
文档明令禁止的依赖被静默放行，而 CI 依然全绿。
**「配置跑绿」不等于「约束生效」。**

以下为实测结果（Python 3.13.14，import-linter 2.14，mypy 2.3.1）。

> **2026-09-20 补记**：当时跑门禁的环境**不是项目 `.venv`**（见 4.5 节），
> 现已修复。在项目 `.venv` 下重跑的实测结果见 4.5 节，**三项结论一致**，
> 差异仅在版本号（Python 3.13.9 / import-linter 2.15）。

### 3.1 三道门禁

```
$ lint-imports
Contracts: 3 kept, 0 broken.                     exit=0

$ mypy core
Success: no issues found in 6 source files       exit=0

$ pytest -q
5 passed                                          exit=0
```

`lint-imports` 的三条契约：
```
分层只允许向下依赖 KEPT
核心层不得依赖评测与扩展 KEPT
内置工具与会话层互不依赖 KEPT
```

`pytest` 的 5 个用例：1 个跑真实仓库树，4 个是 fixture 正反双向
（`layers` 与 `independence` 各一对）。

### 3.2 门槛验证：真实仓库注入违规

只证明「违规会失败」是不够的——契约配置写坏时它同样会失败。
因此对每条契约都做一次注入实验：

| 注入 | 结果 | 退出码 |
| --- | --- | --- |
| `core/sigma_ai` 加 `import sigma_agent` | `分层只允许向下依赖 BROKEN` | 1 |
| `core/sigma_ai` 加 `import evals` | `核心层不得依赖评测与扩展 BROKEN` | 1 |
| `core/sigma_tools` 加 `import sigma_session` | `内置工具与会话层互不依赖 BROKEN` | 1 |
| `core/sigma_session` 加 `import sigma_tools` | `内置工具与会话层互不依赖 BROKEN` | 1 |
| 全部还原后复检 | `Contracts: 3 kept, 0 broken` | 0 |

还原后 `diff` 确认所有文件逐字节一致。

**结论：三条契约都不是摆设，它们真的会拦。**

其中第三条是补上了 4.4 节记录的缺陷之后才成立——
补之前同样的注入会拿到退出码 0。

### 3.3 契约测试的自证设计

`tests/test_architecture_contracts.py` 对每对 fixture 断言**两个方向**：

- 合法样例必须通过 → 证明契约配置有效
- 违规样例必须被拦 → 证明契约有拦截力

每对 fixture 之间**只差一个 import 的方向**，其余完全一致。
这样测试失败时原因只有一种解释。

另外还断言**「只有目标契约坏掉」**：违规样例里 `Contracts: N kept, 1 broken`
必须恰好是 1。这排除了「样例顺带把别的契约也弄坏了、
于是测试因为错误的原因而通过」这种假绿。

## 4. 实施中踩到的坑

记录下来，避免重复踩。

### 4.1 `core/` 布局导致工具静默失效

五个包放在 `core/` 下时，`sigma_ai` 等不是顶层包名，`lint-imports` 与 `mypy`
会**静默找不到包**——不报错，只是什么都不检查。

修法（已写入 `pyproject.toml`）：

```toml
[tool.setuptools]
package-dir = { "" = "core" }

[tool.setuptools.packages.find]
where = ["core"]

[tool.mypy]
mypy_path = "core"
```

### 4.2 `forbidden` 契约引用非 root 包会报错

一开始把 `evals` / `extensions` 写进 `forbidden_modules`，但二者不在
`root_packages` 里（它们不是被安装的包），import-linter 报：

```
The top level configuration must have include_external_packages=True when there
are external forbidden modules.
```

修法：在 `[tool.importlinter]` 顶层加 `include_external_packages = true`。

### 4.3 配置位置：写在 `pyproject.toml` 而不是 `importlinter.toml`

早前在对话里说过用独立的 `importlinter.toml`。**实测 import-linter 2.14 从
`pyproject.toml` 的 `[tool.importlinter]` 读取，不需要单独文件。**
以本文件为准。

### 4.4 【缺陷，已修】`layers` 契约无法表达兄弟层，配置静默放行违规依赖

**发现方式**：本人质疑「`sigma_tools` 为什么要依赖 `sigma_session`」。

**缺陷本身**：`docs/architecture.md` 第 8 节写明

```
sigma_tools   → sigma_agent, sigma_ai
sigma_session → sigma_agent, sigma_ai
```

即两层是**兄弟**、互不依赖。但 P0 只配了 `layers` 一条依赖方向契约，
而 `layers` 是**线性栈**——语义只有「下层不许引用上层」，
**默认放行所有向下的 import**。

把 `sigma_tools` 排在 `sigma_session` 之上，等于给
`sigma_tools → sigma_session` 发了一张通行证。
**结果是：配置在放行文档明令禁止的依赖，而 CI 全绿。**

**实测确认**（向 `core/sigma_tools/__init__.py` 注入 `import sigma_session`）：

| 状态 | 结果 |
| --- | --- |
| 修复前 | 两条契约均 KEPT，退出码 **0** —— 被静默放行 |
| 补 `independence` 契约后 | `内置工具与会话层互不依赖 BROKEN`，退出码 1 |
| 反向注入（session → tools） | 同样 BROKEN，退出码 1 |

**修法**：新增第三条契约

```toml
[[tool.importlinter.contracts]]
name = "内置工具与会话层互不依赖"
type = "independence"
modules = ["sigma_tools", "sigma_session"]
```

**同时固化为测试**：新增 `siblings_clean` / `siblings_violating` 两个 fixture，
并把契约测试改为参数化（4 个 fixture 覆盖 `layers` 与 `independence` 各自的正反两面）。
测试还断言「只有目标契约坏掉」，以证明该样例测的确实是兄弟约束、
没有顺带把 `layers` 也弄坏。

**教训（比缺陷本身重要）**：

> 「配置跑绿」不等于「约束生效」。
> 一条只有能力表达 A 的契约，不会因为你在文档里写了 B 就自动覆盖 B。

所以每新增一条架构约束，都必须先做一个**能证伪它的注入实验**，
再声称它生效。

### 4.5 【环境问题，已修】项目 `.venv` 是空的，依赖实际装进了助手侧隔离环境

`No such file or directory`。检查 `.venv/Scripts/` 只有 `pip` 和 `python`，
**没有 lint-imports / mypy / pytest**。

**根因**：`pip install -e ".[dev]"` 这一步实际作用在了
`C:\Users\刘康鑫\.workbuddy\binaries\python\envs\default\`

#### 契约仍然生效（对空 venv 修复后的独立验证）

修好环境不等于契约还生效——**换了环境必须重做注入实验**，
否则又是「配置跑绿」陷阱的翻版。因此重做一次：

| 注入 | 结果 | 退出码 |
| --- | --- | --- |
| `core/sigma_tools/__init__.py` 加 `import sigma_session` | `内置工具与会话层互不依赖 BROKEN`，其余两条 KEPT | 1 |
| 还原后再跑 | `Contracts: 3 kept, 0 broken` | 0 |

`git status` 确认还原后工作区无代码改动。

**教训**：**"测试通过"要先确认"是谁在跑测试"。**
验收证据必须能追溯到可复现的环境，否则那条证据只能证明"当时某处能跑通"。

**推论（已固化为纪律）**：**换环境等同于换证据。**
`venv` 重建、Python 版本变更、依赖升级之后，**注入实验必须重做一遍**，
不能沿用旧结论。
