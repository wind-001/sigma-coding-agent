## 0. 为什么是 P2 而不是 P3/P4/P5

**结论先行**：P2 是 P5 的**硬前置**，而 P5 是当前作品集最大的缺口。

三条理由，都可核验：

1. **P5 需要能跑多轮任务**。B0–B3 对照与 ablation 矩阵要的是"同一批任务在不同配置下跑"，
   而当前 `sigma_session/context.py` 是**纯内存**的（方法只有 `append` / `history` /
   `build_messages` / `verify_resident_region`），进程一退历史就没了。
   → 评测只能跑单轮，7.6 节"会话树比线性省"那一行**现在根本无法验证**。
2. **P2 的验收门里有一条依赖评测**：「压缩前后成功率下降 ≤ 5%」。没有运行器就测不出来。
   → 这条依赖必须在计划里**显式解决**，不能假装它会自己好（见 §1.1）。
3. **P3（钩子）与 P5 无依赖**，可以更晚；但它压着一个真实风险：
   `bash.py` 现在**只处理超时 kill，没有 `ctx.signal` 取消路径**（实测确认）。
   这条与 P2 无耦合，所以它不构成"必须先做 P3"的理由。

**我不推荐**先做 P3：钩子是把危险操作拦在外面。但当前项目是**单人本地使用**，
真正的危险源（模型误删文件）在 P3 之前还有一个更便宜的兜底——影子 git（也在 P3）。
把 P3 提到 P2 前面，代价是 P5 依然做不出来，而 P5 才是作品集的评分点。

## 1. 目标与验收门

**目标一句话**：让 sigma 的会话**能跨进程续、能分支、能在上下文满时压缩而不丢关键信息**，
且这三件事都有可量化的证据。

**架构方案第 9 节给 P2 定的硬性验收门（原文照录，不软化）**：

1. 分支 / 回滚可用；
2. 常驻区稳定性断言生效；
3. **压缩前后成功率下降 ≤ 5%**。

### 1.1 第 3 条的依赖冲突，以及我的处置

第 3 条需要一个能跑评测的运行器，而 `evals/` **只有 P0 建的目录骨架**
（实测：`README.md` + `datasets/{reproduce,synthetic,adversarial}/` 三个**空**目录 + `reports/`，
除 `.gitkeep` 外无任何文件，**没有 `runner.py`、没有一条任务**）。
`P1-最小闭环.md` 第 2 节的交付项 16/17（评测集 10 条 + 运行器）**当时列了但没做**，
所以这笔账在 P1 就欠下了。

三个选项：

| 方案 | 判断 |
| --- | --- |
| **在本阶段做一个最小运行器（推荐）** | 复用已有的 `FakeProvider` + `load_transcript`（批次 1.5 已实现），**不需要联网不需要花钱**。压缩是确定性的，用回放场景就能测成功率 |
| 把第 3 条推到 P5 | 违背"每个阶段都有硬性验收门，不达标不进下一阶段"（第 9 节开篇）。**不接受** |
| 用真实 API 跑 | 花钱、不确定、与"离线可测"纪律冲突 |

推荐第一种。**注意口径**：用回放场景测"压缩前后成功率"，测的是
"压缩有没有破坏 agent 的决策能力"，**不是**"真实任务成功率"。这个范围缩小必须写进报告，
不能拿它冒充 B2 的成功率。见 §7 的风险 R2.1。

### 1.2 我补的第四条（理由见 §0）

4. `tests/fixtures/transcripts/` 的**六个回放场景**（含 `context_overflow` 一个），
   且每个场景都能在离线状态下跑通。

架构方案 7.2 节把这个文件清单列出来了，但**目录到现在还不存在**（实测：
`tests/fixtures/` 下只有 `arch/`）。

**要说清楚，避免夸大**：回放机制本身**是通的**且**有测试**——
`sigma_ai/fake.py` 的 `load_transcript()` / `FakeProvider.from_file()` 已实现，
`tests/test_sigma_ai_fake.py` 用临时文件覆盖了解析、往返一致、坏 JSON 拒绝。
缺的是两件事：

1. **六个真实场景文件**（挂在 `tests/fixtures/transcripts/` 下）；
2. **让 agent loop 的测试真的用它们**——现有 18 个 loop 测试全部用
   `FakeProvider.from_rounds()`（内存里手写 rounds），**没有一个走 `from_file`**
   （实测 `grep from_file tests/test_agent_loop.py` 无命中）。

所以"agent loop 单测全部走回放"这条 P1 验收门**兑现了一半**：
确定性有了，但**没有从磁盘回放的真实场景**。这也意味着
"场景文件格式变更会让老测试红"这种保护现在**不存在**。

**连带**：加载路径目前是"坏 JSON 直接抛"（`test_load_transcript_rejects_invalid_json`）。
但会话**存储**的坏行处置采用"跳过 + 警告"（Q1 第 2 点），
两条路径的取舍**相反且都有理由**（前者是测试夹具，错误就该响亮；后者是用户数据，
能救多少救多少）。**这个差异必须在两处代码注释里互相指认**，否则以后会被"统一"掉。---

## 3. 关键决策（Q1–Q6，推荐值已给，待拍板）

### Q1 会话树的存储形态：**单文件 JSONL + 每条带 `parentId`**

架构 3.1 与 2.1 已经定了"会话树 JSONL（`id` + `parentId`）"，理由是
"性价比最高的单项设计，成本极低、收益极大"。本阶段照做，不重新论证。

要定的**细节**是三个：

1. **文件粒度**：一个会话一个文件（`~/.sigma/sessions/<id>.jsonl`），不是全局单文件。
   理由：全局单文件在追加时是全表锁、且一处损坏拖垮所有会话。
2. **损坏行处置**：**跳过 + 记录 warning**，不整体拒绝加载。
   理由：这是"能读回一部分"远好于"全都读不了"的场景；
   与"宁可崩不要错"不冲突——那条针对的是**认不出的消息类型**（语义不明），
   而这里是**已知结构里的坏行**（语义明确：这行废了）。
   **差异要写进代码注释**，否则以后会有人按"宁可崩"把它改成抛错。
3. **`id` 生成**：用累积计数或 uuid。**推荐 uuid4**——
   理由：多进程/多会话同时追加时，计数器会撞。

### Q2 `path_to` 的语义：**返回根到该节点的消息列表**

这是"分支"能成立的前提：从任一节点回溯到根，得到该分支的完整历史。
实现上要注意**必须按树深度排序去环**——如果 `parentId` 形成环（数据损坏），
朴素回溯会**死循环**。要加访问集合。

### Q3 压缩的触发与形态

- **触发条件**：动态区（会话历史 + 工具输出）超过**预算的 80%** 时触发。
  为什么不是 100%：压缩本身要花一次 LLM 调用，那时上下文已经快满了，
  可能连"把要压缩的内容发出去"都做不到。
- **压缩目标**：把**最旧的一段**消息替换成一条 `user` 消息（摘要）。
  **保留最近 N 轮原文**——理由：最近的对话决定当前决策，压掉它等于让 agent 失忆。
- **摘要保真要求**：必须保留 ① 用户的任务目标 ② 已经改过哪些文件
  ③ 失败过什么（否则 agent 会重复踩坑）。
  **这三条要写进摘要提示词**，不是靠模型自觉。
- **成本**：一次压缩 = 一次 LLM 调用。**这个成本要记进 `details`**，
  否则评测里"每任务 token"会漏掉压缩的开销，指标失真。

### Q4 `BaseStore` 要不要抽：**我倾向不抽**（需裁决）

按本项目已固化的判据——**"只有一个子类的抽象基类 = 纯间接，要删；
被真实出现的第二个实现所要求的抽象才抽"**（删 `BaseLoop` 与抽 `CreditLedger` 是这条判据的两次应用）。

本阶段只有 JSONL 一个存储实现，所以按同一条判据，**`BaseStore` 现在是纯间接**，
应该等到真有第二个后端（SQLite / 内存测试替身）时再抽。

**但架构 3.1 的目录树里写了 `base.py # BaseStore（ABC）`**——所以我给两个选项：

| 方案 | 判断 |
| --- | --- |
| **不抽 `BaseStore`，只做 `store.py`（推荐）** | 与已固化判据一致；等第二个实现来了再抽，代价几乎为零（那时是一次 `git mv` + 提取） |
| 照架构树抽 `BaseStore` | 与 3.1 目录树一致，但违反已固化判据，且会成为一个"只有一个实现"的抽象 |

**推荐前者，并且要把"为什么没做 base.py"记进本详规**——不然下一个人对照架构树会以为漏了。

### Q5 `AGENTS.md` 的注入位置（**这条最关键**）

架构 5.1 表里写 `AGENTS.md ≤ 1500 token`，落在**常驻区**。

**但这里有一个真实的预算冲突，必须现在解决**（我实测过）：

| 项 | 实测 token |
| --- | --- |
| 当前常驻区（两个联网工具全开） | **≈ 2007** |
| \+ `AGENTS.md`（≤1500） | ≈ 3507 → **已超 D4 的 3500** |
| \+ 技能索引（≤600） | ≈ 4107 → **超 600+** |
| \+ checkpoint/摘要（≤1000） | ≈ 5107 → **超 1600+** |

> **⚠️ 2026-09-21 更正（P2-3 施工时实测发现）：上面这张表算错了。**
>
> D4 的原文定义是「常驻区（系统提示词 + 工具 schema + **项目说明** + 技能索引）」——
> **摘要不在里面**（它降级成 `user` 追加到尾部，属动态区）。
> 而技能索引是 **P4** 才做的。把这两个都加进来是**重复计算**。
>
> 按 D4 的口径实测（两席联网全开）：`286 + 1 729 + 1 500 = 3 515`，**超 15**，
> 不是超 1 607。**这个差别很大**——说成"超 1 600"会让人以为 D4 已不可维持，
> 于是下一次倾向于继续放宽它（而放宽 D4 是明确反对的选项）。
>
> **`AGENTS.md` 收到 800 的结论仍成立，但理由换了**：不是"现在快爆了"，
> 而是**给 P4 的技能索引留空间**（`2 815 + 600 = 3 415 ≤ 3 500`）。
> 详见 `docs/architecture.md` 5.1（已就地更正并附实测表）与 `docs/设计逻辑.md` 图 11。

**5.1 那张表在批次 7/8 之后已经不再自洽了。** 可选栏两席（约 +810 token）
吃掉了原本留给 `AGENTS.md` 与技能索引的余量。

三个选项：

| 方案 | 判断 |
| --- | --- |
| **砍可选栏的常驻成本 + 收紧 `AGENTS.md` 上限（推荐）** | 联网工具的 schema 有压缩空间（description 可以缩短）；`AGENTS.md` 1500 → 800 |
| 放宽 D4 到 5,000 | **反对**。D4 是 prompt cache 的经济性主张，放宽等于把主张改掉以迁就实现 |
| `AGENTS.md` 不进常驻区，改成首轮 user 消息 | 可行，但会让"项目指令"优先级降低；且 5.2 规则二要求动态内容只能尾部追加，首轮追加**不违反**规则二 |

**我推荐第一个，并把实测数字写进 architecture 5.1**（这一条本身就是一个"设计决定被追问"的素材）。
这件事**必须在 P2 里做完**，因为 P2 正好要把 `AGENTS.md` 与技能索引接进来——
不解决就会真的超限。

### Q6 技能索引：**本阶段不做**

架构 5.1 里有"技能索引（≤600 token）"一行，但**技能的加载与执行属于 P4**（扩展系统）。
本阶段只做 `AGENTS.md`。理由：先做索引却没有技能可索引，等于造一个空壳。

## 5. 门槛（G48–G53）与注入实验

沿用既有形态：逐条"破坏 → 跑门槛 → 断言失败 → 还原 → 断言通过"。
**名义门槛比没有门槛更坏**——每条都必须能写出"注入后红在哪"。

| 门槛 | 断言 | 注入方式（证明它不是名义门槛） |
| --- | --- | --- |
| **G48 树路径正确** | 分支节点 `path_to` 只返回本分支祖先，不含兄弟分支 | 让 `path_to` 返回全部节点 → 分支历史混入兄弟消息 |
| **G49 环检测** | 构造 `parentId` 成环的数据，`path_to` **不死循环**（抛错或截断） | 去掉访问集合 → 测试超时 |
| **G50 常驻区稳定** | 会话内二次 `build_messages` 的常驻区哈希与首次一致；不一致抛 `ResidentRegionChanged` | 让提示词带时间戳（模拟"忘了冻结"） → 哈希变化但**不抛** |
| **G51 压缩降级为 user** | 压缩产出的消息 `role == "user"`，且**不占常驻区** | 改成 `system` → 常驻区哈希变化（G50 连带红） |
| **G52 压缩保真** | 摘要提示词里含"任务目标 / 改过哪些文件 / 失败过什么"三条要求 | 删掉其中一条 → 摘要用例断言失败 |
| **G53 存储追加幂等** | 同一批消息重复 append 后读回不产生重复节点 | 去掉去重/幂等键 → 读回节点数翻倍 |
| **G54 `AGENTS.md` 硬截断** | 超长 `AGENTS.md` 被截断到上限，且 `details` 记明截断 | 去掉截断 → 常驻区超预算 |

**连带**：`scripts/gate_injection_batch1.py` 到 `batch8.py` 全部**重跑一遍**。
理由（元纪律②）：本阶段会改 `context.py`，而批次 1 的注入锚点就在那里。
**不允许把老批次挂在那不管**——那正是"验证工具自身会腐化"要防的事。
本阶段预计**至少 batch1 的锚点会移动**。

### 12.5 环检测的"两条防线"（这条值得单独记）

`detect_corruption` 有两条独立机制：`seen` 集合给**精确环链**（`A -> B -> A`），
步数上限（节点总数 + 1）保证**不挂死**。

第一次设计时我想只留一条，结果发现两条都留才对，理由不对称：

- 只留 `seen`：一旦它被重构掉，症状是**测试进程无限循环**——
  而挂死的 CI 比失败的 CI 难排查得多，且注入实验本身就跑不起来（会挂住）。
- 只留步数上限：结果正确但**诊断质量差**（只能说"链太长"，说不出环在哪）。

**连带影响了 G49 的断言设计**：不能只断言"节点被判坏"——
防线二会在防线一失效时兜住，那条断言**依然会绿**（假绿）。
必须断言**只有防线一才能提供的信息**（具体环链），门槛才真实可证伪。
**兜底不等于正确**——这条门槛就是为这句话设的。

### 13.4 三处施工发现

1. **`SessionContext.append` 原本返回 `None`** → 调用方拿不到节点 id，
   **P2-2 做的分支/回滚到不了本层**，只能绕过 context 去用 `context.tree`。

2. **截断标记会撑破预算**：详细标记约 60 token；上限配 50 时

   参数化扫多档上限的用例抓到的（单点断言恰好避开边界）。

### 14.3 对 §3 Q3 的**有意偏离**：压缩是"视图"，不是"替换"

Q3 原话是「把最旧的一段消息**替换**成一条 `user` 消息」。P1 的历史是列表，
"替换"就是重新赋值；但 P2-2 之后历史住在**只追加**的 `SessionTree` 里，
"替换前缀"要么改写节点、要么重新挂父——**两者都等于改写历史**。

代价不是"实现麻烦"，而是 `store.py` 里写死的那条：改写历史会让
「这条消息当时是否存在过」不可考，而**审计链正是会话树存在的理由**。

所以：**压缩产出派生视图**（`[摘要, *保留窗口]`），树里原文一个字节不动；
`history()` 仍是原始历史，`effective_history()` 才是发给模型的那份。
由门槛 **G60** 钉住（注入"让 history() 返回视图"必须变红）。

### 14.4 **§5 关于 G51 的预判被实测推翻**（值得单独记）

§5 写的注入方式是「改成 `system` → 常驻区哈希变化（G50 连带红）」。
**实测不成立**：常驻区指纹由 `_resident_text()`（系统提示词 + 项目说明）
与工具 schema 算出，**与历史无关**——把摘要的 `to_llm()` 改成 `SystemMessage`，
指纹一点都不会变。

这条门槛其实是**两件独立的事**，所以拆成两条注入：

- **G51（类型层）**：摘要降级成什么。错在"模型会把一段历史摘要当成系统指令"。
- **G51b（位置层）**：摘要在不在常驻区。错在"每压一次 prompt cache 全失效"。

**预判错得有价值**：它说明这条门槛原本只被想成了一条。

### 14.5 ⚠️ 第 3 条验收门**离线测不了**（不是"没做"，是"做不到"）

P2 的硬性验收门第 3 条是「压缩前后回放成功率下降 ≤ 5%」。它**离线测不了**：

- 「成功率」要判定"压完之后模型还够不够用"，需要**真模型**理解任务；
- `FakeProvider` 是回放录音，拿它算出来的"成功率"只是在数"脚本还对得上吗"，
  **与压缩质量无关**——那会是一条彻头彻尾的假指标。

所以它必须等 `evals/datasets/` 的 70 条任务集落地（需真实 API key）。
**在那之前它是"未验收"，不是"已通过"。**

**离线能做到、也做了的**是"压缩不破坏 loop"：自动压缩后本轮任务照常完成、
压缩失败不打断会话、摘要不进常驻区、压缩确实让动态区变小。

### 14.6 四处施工发现

1. **`context_window_tokens` 没有默认值**（`CompactionPolicy` 里的必填字段）。
   它是"这个模型能装多少"，属于**调用方的知识**；写个默认值等于让会话层
   假装知道一个它无从知道的事实。产品壳里给了一个**保守下限 32k**
   （`DEFAULT_CONTEXT_WINDOW_TOKENS`），理由是**两个方向的代价不对称**：
   猜小 → 多花一次调用（贵但不坏）；猜大 → 该压不压直到请求被拒（坏，且离根因远）。
2. **`needs_compaction` 在常驻区自己就超窗口时返回 False**。
   那不是"压缩能救的问题"——省下来的是历史，超的是常驻区。
   那种配置错误归常驻区预算闸（G59）管，**不让压缩背锅**。
3. **`keep_from` 存节点 id 而不是下标**。下标会在压缩后继续追加消息时漂移，
   而 id 稳定。有专门用例（"压完再追加两轮"）钉住它。
4. **压缩失败被吞掉，但不清 `_last_compaction`**。压缩是"为了跑下去"的优化，
   它自己失败不该让用户丢掉整个会话；而上一次**成功**的压缩结果仍然有效，
   不该被一次失败抹掉。

**根因**：更早那条"跑 batch1–batch8"的**合并命令被 SIGTERM 打断**
（pytest 变长后超了前台超时），而 `finally` 里的还原**不会**在 SIGTERM 时执行
——SIGTERM 的默认处置是立即终止。于是 `web_search.py` 里
`if not decision.allowed:` 被永久留成了 `if False:  # 注入：忽略额度判定`。

**为什么难查**：它的症状是"基线不是绿的，实验无效"，
**看起来像环境噪声**（本机沙箱确实制造过类似噪声），
而实际是**源码被改坏了**。第一轮排查方向因此指向了别处。

**当时的排查动作**（可复用）：`git status --short` 看有没有意外的 M；
`grep -rn "注入" core/` 找标记。两步就定位了。

### 15.5 为此给注入框架加了两道保险

这是「验证工具自身会腐化」的又一次应用——**"还原成功"这件事本身也需要被检查**。

1. **开工前扫描残渣**（`assert_no_residue`）：扫 `core/**/*.py` 里有没有
   `# 注入：` 标记，有就直接退出并告诉你 `git checkout -- <文件>`。
   已在 `experiment()` 开头调用，**所有批次自动都受保护**。
2. **终止时也还原**：给 SIGTERM / SIGINT 挂处理器，调 `Repo.restore_all()`。
   配套把"未还原文件"从实例级改成**类级**（信号处理器够不到实例），
   并把登记的原始内容从"归一化文本"改成**原始字节**——还原必须逐字节精确，
   不该再经过行尾转换那一道。

**两道保险都验证过会红**：人为制造一条残渣，`assert_no_residue()` 立刻响亮退出。

1. **注入实验必须在前台跑**。后台运行拿不到沙箱对 pytest 临时目录清理的批准，

   所以：**注入脚本一次最多跑两个**，别把 8 个串在一条命令里。
