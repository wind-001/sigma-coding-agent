## 1. ①-c 落地设计:所有子会话统一 worker 面

### 1.1 现状(评审取证,均已复核)

- `sdk.py:493-500` 只注册一个 `role="lead"` 的 TeamBoard;子会话 registry =
  `clone(exclude=("task","todo"))`(`sdk.py:589`),而 `registry.py:131` 明写 clone 是
  **实例共享** ⇒ 子会话拿到的是 lead 面,可 create/reclaim/abandon/cancel。
- 详规 §2 要求 worker 面下发,但 `role="worker"` 在 `src/` 里**零构造**。
- `multi_agent` 同样不在排除项 ⇒ 子会话能自己 `start` 一个引擎,破 §5"多团队并存(单主会话一板)"。

### 1.2 改动点

1. `sdk.py::_make_sub_agent_factory` 的 clone 排除项扩为
   `("task", "todo", "team_board", "multi_agent")`。
   - **为什么是 exclude 而不是覆盖**:`register` 重名时**抛错且注册表保持原样**(G24),
     项目明令**不允许静默覆盖**——所以必须先排除,再注册。
   - `multi_agent` 的排除是①-c 的附带组成(顺带修 §5 破口),不是额外功能。
2. `enable_team_tasks` 为真时,往子注册表注册**worker 面**实例并**共享 store/mailbox**:

   `TeamBoard(lead_session_id=..., role="worker", store=self._team_store, mailbox=self._team_mailbox)`

   - **共享是硬要求**:两个实例各造各的 `BoardStore`,锁就分成两把,claim 互斥
     (G-TEAM-2)变成名义上的——`multi_agent.py` 的 docstring 已把这条纪律写死。
   - `self._team_store/_team_mailbox` 现在只在 `enable_team_tasks=True` 分支里赋值
     (`sdk.py:491-492`),而工厂闭包在 dispatch 时才执行 ⇒ 必须在 `__init__` 里先置 `None`,
     工厂内按 `is not None` 判断,避免 `AttributeError`。
3. 引擎 worker **不需要额外接线**:引擎 runner 走的就是同一个工厂
   (`sdk.py:505-507`),自动拿到 worker 面。

### 1.3 连带面:这边比看上去大(①-c 的核心风险)

worker 面**真的把 `fail` 交给 LLM**了(`WORKER_OPS = {list, finish, fail}`)——
这正是详规 §3.2"fail 是 worker 的主动义务"所要求的能力。但引擎现在的收尾是**无条件**的:

```
result = await self._runner(worker_id, description, max_rounds)
await wb.finish(claimed.id, result)      # ← worker 若已自己收尾,这里撞非法迁移
except Exception as exc:
    await wb.fail(claimed.id, ...)       # ← 同上,又撞一次
```

迁移表里没有 `(fail, FINISH)` / `(fail, FAIL)` ⇒ `ValueError`;except 分支再抛 ⇒
worker 协程带异常结束且异常无人回收,而任务停在 `fail`(**非终态**)⇒ 引擎**永不收敛**。
所以 ①-c **必须**同时做幂等收尾,否则是用一个新死锁换掉一个文档不一致。

4. `WorkerBoard` 增幂等收尾:`try_finish(task_id, result) -> TeamTask | None`、
   `try_fail(task_id, reason) -> TeamTask | None`——**同一事务内**回读板,
   任务已不在 `running` 就返回 `None`(跳过),否则照常收尾。
   放门面层而不是引擎里:它是"这个角色现在还能不能对这个任务动手"的规则,属协作域;
   放引擎里则要在引擎内重写一遍读-改-写。
5. `engine._worker_loop` 改用 `try_finish` / `try_fail`,不再重复收尾。
6. worker 派发文案改写——现在写的是"用 team_board 的 op=finish 收尾**没有意义**"
   (`engine.py:163-168`),与 ①-c 直接冲突。改为:
   "正常完成:直接回结论文本,引擎替你登记。搞不定:**调 team_board 的 board op=fail
   写明原因**(装死要等 lease 超时才被回收)。"

### 1.4 已知代价(按 ①-c 的选择登记,不藏)

`task` 工具派发的子 agent 也变成 worker 面 ⇒ **子 agent 不能再往板上建任务 / 重派 / 撤销**,
只能 `list / finish / fail` + `send / inbox`。

- v1 的"**双向信箱**"完全保留:`send`/`inbox` 不受 role 约束(role 只过滤 `board` 的 op)。
- 变的是 v1"共享任务板"的含义:从"主会话与子 agent 都能写板"收成
  "**只有 lead 建与派,子 agent 只报**"。
- G-TEAM-4"派发融合"仍然成立(子会话照样注册 team_board),但**语义要重写**,
  判定面从"看到 team_board"变成"看到 worker 面的 team_board"。
- 这是本次拍板的**有意代价**,登记在详规 §3.3 的修订记录里,不是实现走样。

### 1.5 新门禁(编号 14+ 已确认未被占用)

| 编号 | 断言 | 怎么证伪 |
| --- | --- | --- |
| G-TEAM-14 | **装配级**角色面:装配后子会话拿到的 team_board `role == "worker"`,且 create/reclaim/abandon/cancel 在子会话调用时被拒;主会话仍是 lead 面 | 把装配改回 lead 面 → 必须红 |
| G-TEAM-15 | **引擎幂等收尾**:worker 自己 finish/fail 之后,引擎不重复收尾、不抛非法迁移、任务终态正确 | 去掉"回读跳过" → 必须红 |

## 2. ②-b 落地设计:失败兜底通知

### 2.1 缺口(评审取证)

- 引擎异常分支落 `fail`(`engine.py:177-178`):保留失败原因、重派权归 lead
  ——这与详规 §5"自动重派策略(lead 的元决策保留给模型)"一致,所以**保留**。
- 但 `fail` **不是终态**(`engine.py:50` `_TERMINAL = {success, dead, cancelled}`),
  而收敛判据要求"全部任务终态"(`engine.py:137-139`)⇒ 只要有 fail 任务而 lead 不介入,
  **引擎与 worker 永久空转**(每 `poll_s` 一轮),汇总永远不写、`multi_agent` 永远"运行中"。
  这是"记 fail"路径的真实缺口:**不是记错了,是没人知道**。
- 本条**不改收敛判据**(那会动 §3.1 自动收敛的语义),只补"让 lead 必然知道"。

### 2.2 设计

- 引擎每轮 poll:在事务内收集"新出现的 `fail` 任务",**出事务后**给 lead 发一封信
  (不在事务里做 I/O,避免持锁写盘):

  `[失败待决] t1《标题》attempts=1 — RuntimeError: ... → 请 reclaim 重派 或 abandon 放弃`

- 去重键 `(task_id, attempts)`:同一失败状态不刷屏;重派后再失败会**再通知一次**(正确行为)。
- **为什么放 poll 而不是放在引擎的 except 分支**:①-c 之后 worker 也能自己调 `fail`,
  那条路径不经过引擎的 except;只有 poll 能同时覆盖两条路径。

### 2.3 门禁

| 编号 | 断言 | 怎么证伪 |
| --- | --- | --- |
| G-TEAM-16 | fail 任务出现后,lead 信箱**恰好一封**待决提醒;同一 fail 重复轮询不重复发;reclaim 后再失败会再发一封 | 删通知 → 红;删去重 → 红(收到多封) |

### 2.4 残余暴露(诚实登记)

- **lead 收到但不处理 ⇒ 团队仍不收敛**(空转、不汇报)。是否加"僵局超时自动 abandon"
  = **A5,本批次不做**。本批次只承诺"lead 必然会看到"。
- **A3 追认的"3 次判死"真实触发条件要说准**:触发条件是"同一任务被**重派 3 次**且每次
  fail"(或 lease 超时 3 次),**不是"崩 3 次"**——因为涨 `attempts` 的路径只有
  FAIL / WORKER_LOST / LEASE_EXPIRED 三条,全都需要有人去动它;一个静止的 `fail`
  只有 lead `reclaim` 才会被再次推动。C8 会把这句话写进详规,免得日后按错误理解依赖它。
