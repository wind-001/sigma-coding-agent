## 0. 本批次要回答的问题

**一句话**：让 sigma 第一次**能自己动手**——接收一个任务，跟模型来回几轮，
中途调用真实工具改文件，直到模型说"做完了"。

**为什么这一批不能省**

    前两批做完，sigma 能跟模型通信（`sigma_ai`），也能正确表达消息（`agent_messages`），
    但它**不能做任何事**。它是一台能听见你说话的机器，没有手。

    而"harness 到底有没有用"这个核心命题，**只有在 agent 能动手之后才可测**——
    B1 基线（有工具无 harness）与 B2（完整 sigma）的对照，
    两边的差别全在"循环怎么组织工具调用"这件事上。

## 3. 关键设计

### 3.1 `ToolCall` 不另定义，直接用 `ToolCallBlock`

架构方案 4.3 节的示意代码写 `calls: list[ToolCall]`，本详规**不照做**——
agent 层直接使用 `sigma_ai.messages.ToolCallBlock`。

**理由（三条）**：

1. **字段完全一致**：`id` / `name` / `arguments`，一个不多一个不少。
   再定义一次只能靠复制粘贴保持一致，属于"靠约定维持的正确性"。
2. **不增加转换点**：`ToolCallBlock` 本来就是协议无关的调用描述
   （协议差异在 provider 里消化）。中间加一层映射，等于每个工具调用多一次
   转换，而**多一处转换就多一处可错的代码**。
3. **依赖方向本来就是允许的**：`sigma_agent → sigma_ai` 是既有契约，
   agent 层使用 LLM 层的类型不违反任何分层规则。

**但保留一个反对意见供你判断**：如果将来 provider 层因为某种协议需要给
`ToolCallBlock` 加字段（比如 `thought_signature` 已经在里面了），
agent 层会被动跟着变。**我判断这个风险可接受**，因为那个字段本来就是
"provider 返回、必须原样回传"的语义，agent 层理应持有它。

### 3.2 `ToolResult` 与 `ToolContext`

```python
class ToolResult(BaseModel):
    """工具执行结果。**两段式**（研究笔记 9.5.8 / 14.1 第 4 条）。"""
    content: list[ContentBlock]        # 进上下文，给模型看
    details: dict[str, Any] = {}       # 不进上下文：UI / 审计 / 评测
    is_error: bool = False

class ToolContext(BaseModel):
    session_id: str
    workspace_root: Path
    signal: CancelToken
    emit: Callable[[str], None]
```

**`content` 与 `details` 的切分是硬约束**，不是风格偏好。
判定依据沿用架构 4.2 节：**如果一段内容不需要模型看到，它就必须在 `details` 里。**
这直接决定上下文预算。

**具体到五个工具**：

| 内容 | 去哪 | 例子 |
| --- | --- | --- |
| 文件正文 / 命令 stdout / 匹配行 | `content` | 模型要读的东西 |
| 退出码、耗时、字节数、完整输出文件路径、截断标记 | `details` | 模型不需要看 |
| stderr（**要**给模型看） | `content` | 它是纠错信息，见 3.6 |

**这条容易做错**：把退出码塞进 `content` 是一种常见的图省事写法，
它会让每轮多几个 token 且模型未必用得上；而把 stderr 放进 `details`
则是**功能性错误**——模型看不到报错就没法纠错。

### 3.3 `BaseTool`：`params` 是抽象属性，`json_schema()` 给默认实现

```python
class BaseTool(ABC):
    name: str = ""
    description: str = ""
    read_only: bool = False
    needs_approval: bool = False

    @property
    @abstractmethod
    def params(self) -> type[BaseModel]:
        raise NotImplementedError

    @abstractmethod
    async def run(self, args: BaseModel, ctx: ToolContext) -> ToolResult:
        raise NotImplementedError

    def json_schema(self) -> dict[str, Any]:
        """由 params 生成 JSON Schema。**默认实现，非抽象。**"""
        return self.params.model_json_schema()
```

**为什么 `json_schema` 给默认实现而 `params` 不给**：

判据是"**有没有一个对所有子类都正确的实现**"。

- `params` 每个工具不同 → 必须是抽象的，否则"忘了定义"会变成静默继承一个空的参数模型，
  而症状是"模型永远调不对参数"，不指向根因。
- `json_schema` 的通用实现（`model_json_schema()`）对所有工具都正确
  → 让它抽象只会逼 5 个内置工具各写一遍完全相同的代码。

这与架构 4.2 节"用足 Pydantic"的意图一致：**Pydantic 同时给了参数校验、
类型提示和 schema 生成三样东西**，不该只当类型标注用。

### 3.4 注册表：重名时必须"不改动旧状态"

```python
class DuplicateToolError(ValueError):
    """重名注册。继承 ValueError，与批次 1 的 `TRY004` 经验一致
    （类型错误用 TypeError，值非法用 ValueError）。"""

class ToolRegistry:
    def register(self, tool: BaseTool, *, source: str = "builtin") -> None: ...
    def get(self, name: str) -> BaseTool: ...
    def names(self) -> list[str]: ...
    def schemas(self) -> list[dict[str, Any]]: ...   # 拼给 provider 的 tools 参数
```

**两条硬要求**：

1. **重名抛错，且注册表保持原样**。不能"先删旧的再插新的，插到一半失败"。
   实现上很简单（先查再写），但**必须用测试钉住**，因为一次"半更新"
   会让某个工具永久消失，而症状是"模型突然不会用某个工具了"。
   → 门槛 **G24**。这是架构 4.4 节三个失败场景里"半更新状态"的早期版本。
2. **`get()` 每次查表返回，调用方不得缓存 `ToolDefinition`**。
   P1 还没有热重载，所以现在**看不出来**违反的后果；但这条约束必须在
   P1 就写进 docstring，否则 P4 加 `reload_source` 时会发现调用方到处缓存了实例。
   → 批次 4 复核项（见第 9 节）。

**`schemas()` 的顺序必须稳定**（按注册顺序或字典序），
因为它进常驻区、参与哈希（3.7）。**顺序不稳定的字典迭代会让常驻区哈希每轮都变**，
而症状是"prompt cache 永远命中不了"，极难排查。

### 3.5 五个工具的行为约定

| 工具 | 参数 | 只读 | 关键约定 |
| --- | --- | --- | --- |
| `read` | `path`, `start_line?`, `end_line?` | ✅ | **必须支持行范围**，否则截断后的内容无法读取 |
| `write` | `path`, `content` | ❌ | 覆盖写；父目录不存在时**不自动创建**（要显式报错） |
| `edit` | `path`, `old_string`, `new_string` | ❌ | 精确替换 + 返回 unified diff，**多匹配必须拒绝**（见下） |
| `bash` | `command`, `cwd?`, `timeout_s?` | ❌ | 超时**必须**，否则一条挂起的命令让 loop 永久卡死 |
| `grep` | `pattern`, `path?`, `glob?` | ✅ | 返回**带文件名与行号**的匹配行 |

**`edit` 的三态规则**（`P1-最小闭环.md` R4 已定，此处照录并强化）：

```
old_string 在文件中出现 0 次     → is_error=True，提示"未找到，请先 read 确认当前内容"
old_string 出现 1 次             → 执行替换
old_string 出现 N > 1 次         → is_error=True，要求提供更大上下文消除歧义
```

**绝不"替换全部"。** 静默替换多处是最难排查的一类 bug——
它会产出一个"看起来改对了"的文件，而错误要到测试才暴露。
这与架构 4.4 节"不允许扩展静默覆盖内置工具"是**同一条原则的不同应用**：
**有歧义时宁可报错，不要猜。**

**所有工具失败的统一形态**：返回 `is_error=True` 的 `ToolResult`，**不抛异常**。
理由见 3.6。

### 3.6 工具失败必须变成"模型可见的信息"

这是架构 4.3 节第 3 点，也是整个 loop 里**最能体现设计意图**的一条：

> 单个工具失败不中断批次，转成 `is_error=True` 的 `ToolResult`
> ——让模型自己看到失败原因并纠错，比抛异常好。

**为什么这条重要**：它是"agent 能自我纠错"的前提，
也是评测里**纠错增益 = 最终成功率 − 首次成功率**这个核心指标能拉开差距的原因。

如果工具失败抛异常，第一次失败就终止任务，那个指标永远是 0。

**具体实现要求**：

- 工具的 `run()` 内部捕获自己知道的所有异常，转成 `is_error=True`
- loop 再兜一层：`run()` 意外抛出时也转成 `is_error=True`（**不要让异常穿透到 loop 外**）
- `stderr` 与错误信息**必须进 `content`**，不能只进 `details`

**这条也意味着 loop 里不能有"第一个工具失败就 return"的分支**。
它看起来像防御性编程，实际会静默关闭整个纠错能力。

### 3.7 `context.py`：常驻区哈希断言（内存版）

> **注意（2026-09-20 参照 Pi 后调整）**：`AgentLoop` **不依赖** `SessionContext`——
> loop 接收的是消息列表（3.8.1）。本模块服务于 `sdk.py` / `cli.py`：
> 由它们维护历史累积，并**在把消息交给 loop 之前**完成常驻区校验。
> 于是常驻区纪律仍然是强制的，而 loop 保持无状态。

```python
class SessionContext:
    """P1 内存版。不做落盘、不做压缩、不做会话树。"""

    def __init__(self, *, system_prompt: str, tools_schema: list[dict[str, Any]]) -> None:
        self._system_prompt = system_prompt
        self._tools_schema = tools_schema
        self._history: list[AgentMessage] = []
        # 构造时冻结指纹
        self._resident_fingerprint: str = self._compute_fingerprint()

    def append(self, message: AgentMessage) -> None: ...

    def build(self) -> list[LlmMessage]:
        if self._compute_fingerprint() != self._resident_fingerprint:
            raise ResidentRegionChanged(...)
        return convert_to_llm([self._system_message(), *self._history])
```

**指纹的算法**：对 `{"system": <提示词>, "tools": <schema 列表>}` 做
`json.dumps(sort_keys=True)` 后取 SHA-256。

**为什么这是零成本的高价值约束**（架构 5.2 节的判断，我认同）：
它把"常驻区不得变化"这条容易违反的约定，变成**不可违反的约束**。
代价是一次哈希计算，收益是"prompt cache 命中率"这个指标的前提条件被机器保证了。

**P1 的启动路径上确实没有东西会改常驻区**——所以这个断言在 P1 **不会真的触发**。
但**门槛的验证方式恰恰是让它故意触发一次**：测试里改掉 `_system_prompt` 再 `build()`，
必须抛异常。→ 门槛 **G26** + 注入 **E24**。

**这点必须写清楚**：一个"不会失败的断言"很容易被后来者当成死代码删掉。
所以它必须配一个**能证明它会失败**的测试。

### 3.8 `loop.py`：核心循环

```python
class AgentLoop(BaseLoop):
    """参照 Pi 的 `agentLoop` 形状：**消息数组进、新增消息出**，不持有会话对象。"""

    def __init__(
        self,
        *,
        provider: BaseProvider,
        registry: ToolRegistry,
        model: str,
        max_rounds: int = 20,
        sampling: SamplingParams | None = None,
    ) -> None: ...

    async def run_turn(self, messages: list[AgentMessage]) -> TurnResult:
        produced: list[AgentMessage] = []

        for round_index in range(1, self._max_rounds + 1):
            # 第 2 步 transformContext：P1 无钩子，此处**跳过**（P3 在此接入）
            llm_messages = convert_to_llm(messages + produced)          # 第 3 步

            assistant, calls = await self._stream_model(llm_messages)   # 第 4 步
            produced.append(assistant)

            if not calls:                                               # 第 8 步
                return TurnResult(status="completed", messages=produced, ...)

            results = await self._execute_batch(calls)                  # 第 6 步
            for call, result in zip(calls, results, strict=True):       # 第 7 步
                produced.append(ToolResultAgentMessage.from_result(call, result))

        return TurnResult(status="stopped", reason="max_rounds", messages=produced, ...)
```

#### 3.8.1 与 Pi 八步流程的逐条对照（2026-09-20 按「参照 pi 框架」补齐）

Pi 的一轮流程（调研笔记第 5 节，对应 `agent-loop.ts`）：

```
接收 AgentMessage[]
   ↓ transformContext()   —— 可重塑已保存的上下文
   ↓ convertToLlm()       —— 转成 provider 能接受的格式
   ↓ 模型流式返回文本 + 工具调用
   ↓ 校验工具参数
   ↓ 执行完整的工具批次（batch）
   ↓ 逐个 append toolResult
   ↓ 判断是否需要再来一轮
```

| # | Pi | sigma P1 | 差异 |
| --- | --- | --- | --- |
| 1 | 接收 `AgentMessage[]` | `run_turn(messages)` | **形状照抄** |
| 2 | `transformContext()` | **跳过**（代码里留注释标位） | P1 无钩子；P3 接 |
| 3 | `convertToLlm()` | `convert_to_llm()` | 批次 1.5 已实现 |
| 4 | 流式返回文本 + 工具调用 | `_stream_model()` | 见下方 |
| 5 | **校验工具参数** | **两级校验**（`json.loads` → `params.model_validate`） | **本项是参照 Pi 补进来的**，见下方「参照 Pi 补出来的一步」 |
| 6 | 执行完整工具批次 | `_execute_batch()` | P1 只做两条规则，见下 |
| 7 | 逐个 append toolResult | 追加进返回值 `produced`，**不是 append 到会话对象** | 见下方说明 |
| 8 | 判断是否再来一轮 | 同 | — |

**第 7 步的差异是本次「参照 Pi」最关键的一处。** Pi 的 loop **不持有会话对象**——
它接收消息、产出消息，**存到哪儿是调用方的事**。

sigma 采纳这个形状，于是 `AgentLoop` **既不依赖 `SessionTree`、也不依赖 `Context`**：

1. **P1 不需要会话管理**——符合本次裁剪要求，不用造空壳。
2. **loop 变成无状态的**，测试可以直接喂消息、断言输出，不必先搭一套会话设施。
3. **P2 引入会话树时，只要在调用处把树上的消息取出来传进去**，
   `loop.py` **一行都不用改**。这是"参照 Pi"换来的真实收益，不是照抄形态。

**代价要说清**：调用方要自己维护历史累积。这个代价由 `sdk.py` 兜住（3.9 节），
换来的是"loop 可被独立测试"——这笔交易划算。

**`zip(..., strict=True)` 是刻意的**：它要求 `_execute_batch` 返回的结果数量
与调用数量**严格相等**，少一个就立刻抛 `ValueError`。
比返回 `list[tuple[ToolCall, ToolResult]]` 更严——后者允许"静默少返回一个"。
这与门槛 G27（顺序不错配）是同一道防线的两种强度，取强的那个。

**`_stream_model` 是 loop 里最容易写错的地方。** 它要把 `StreamEvent` 流
聚合成一条 `AssistantMessage` + `list[ToolCallBlock]`。职责边界来自
`openai_compat.py` 的注释：

> ``tool_acc`` 在此处已累积完整，但把它拼成 `AssistantMessage` 的工作
> **不在这里**——那是 loop 的职责（批次 4）。

要处理的四件事：

1. **文本累积**：`TextDelta.text` 按到达顺序拼接。
2. **工具调用累积**：`ToolCallDelta` 按 `index` 分组，`arguments_delta` 字符串拼接。
   **不能按到达顺序硬拼**——多工具并行时两个 index 会交错到达。
3. **`arguments` 的**两级**校验**（第 5 步，参照 Pi 补进来）：拼完后先 `json.loads`，
   再 `params.model_validate(parsed)`。**两级都会失败**——模型可能输出截断的 JSON，
   也可能输出合法 JSON 但字段不符合 schema。
   **失败时不能抛异常**，要转成 `is_error=True` 的结果让模型纠正（3.6）。
   **必须把"是哪一级失败的"写进错误文案**："不是合法 JSON"与
   "JSON 合法但缺少必填字段 `path`"是两种完全不同的修法，模型需要知道是哪种。
4. **`usage` 与 `stop_reason`**：从 `UsageEvent` / `StopEvent` 取。
   注意 `usage` 在 OpenAI 协议里位于**最后一个只有 usage 的 chunk**，
   而 `finish_reason` 在前一个 chunk——**两者的到达顺序与直觉相反的部分要按实际协议写**。

**参照 Pi 补出来的一步（原设计漏了）**

我最初的设计只有"`json.loads` 失败 → `is_error`"，**漏了 schema 校验**。
对照调研笔记第 5 节的八步流程后补上——Pi 明确有「校验工具参数」这一步
（它用 typebox 做）。

**这一步对 sigma 比对 Pi 更划算**：`BaseTool.params` 返回的就是 Pydantic 模型
（研究笔记 9.5.8 指出 Pi 的 `Tool` 只有 typebox schema、没有可执行函数），
所以 `params.model_validate(arguments)` 是**一行代码拿到完整校验 + 精确错误信息**。
这是 Python 侧的现成优势，**没有理由不用**。

**校验失败的处置与 JSON 失败相同**：`is_error=True`，错误内容进 `content`，
并带上 Pydantic 的校验错误（它含字段路径，模型能直接定位到是哪个参数错了）。

**离线自测已确认第 2、3 点的形态**：`scripts/real_api_smoke.py` 的 P4 探测
已经在录制的 SSE 上验证过"三片拼一个调用"与"两个 index 交错到达"，
本批次的实现可以直接照那个聚合逻辑写（那段逻辑经过自测）。

**`_execute_batch` 的三条规则，P1 只做两条**：

| 规则 | P1 | 说明 |
| --- | --- | --- |
| ① 只读工具并发、写工具顺序 | **做** | `read_only=True` 的用 `asyncio.gather` |
| ② 每个调用过钩子，钩子可阻断 | **不做**（P3） | 钩子需要完整设计（超时、异常、顺序），半成品比没有更坏 |
| ③ 单个工具失败转 `is_error` 不中断 | **做** | 见 3.6 |

**规则①的实现有个必须写对的细节**：并发执行后，
**结果必须按原始调用顺序排列**再 append。
`asyncio.gather` 返回的顺序与传入顺序一致，但如果中途用了
`as_completed` 或把结果塞进 dict，顺序就会丢。
**顺序丢了会导致 `tool_call_id` 与结果错配**——而症状是"模型拿着 A 的结果回答 B 的问题"，
这类错误在长对话里极难定位。→ 门槛 **G27**。

**并发的边界**：P1 的写工具（`write` / `edit` / `bash`）**一律串行**，
即使它们操作的是不同文件。理由：并发写带来的不确定性，
会让"确定性回放"这个测试地基失效——而那是整个评测的前提。

### 3.9 `sdk.py` 与 `cli.py`

**`run_task` 承担了「维护历史」这件事**——因为 loop 参照 Pi 之后不再持有会话对象
（3.8.1）。它做三件事：构造 `SessionContext`（含常驻区校验）、
调 `loop.run_turn(messages)`、把返回的 `messages` 追加回 context。
**P1 到此为止**：不落盘、不压缩，进程结束即丢——这是 0.1 节列明的代价之一，不是遗漏。

```python
async def run_task(
    task: str,
    *,
    provider: BaseProvider,
    workspace_root: Path,
    model: str,
    max_rounds: int = 20,
    registry: ToolRegistry | None = None,
) -> TurnResult: ...
```

CLI 形态：

```
sigma -p "把 utils.py 里的 off-by-one 修掉" --workspace ./demo --max-rounds 20
```

**退出码严格遵守 Q4**：

| 情况 | 退出码 |
| --- | --- |
| 正常跑完（**无论任务成没成**） | `0` |
| harness 自身故障（provider 连不上、workspace 不存在、配置非法） | 非 `0` |
| 达到 `max_rounds` 上限 | `0`（`TurnResult.status == "stopped"`，写进输出） |

**`stopped` 必须打印出可见提示**，不能静默退出。
"没做完但退出码是 0"正是 Q4 要的语义，但用户必须能看见它没做完。

**P1 的 CLI 必须在启动时打印一行安全提示**：

```
⚠ bash 工具在 P1 无任何限制（D5 的三层边界尚未实现），仅建议在受控目录内使用。
```

理由见 0.1 的第 3 条代价。**不知道边界在哪，比边界不存在更危险。**

### 3.10 输出截断（`truncate.py`，Q2 已拍板提前）

**P1 只做截断，不做落盘与分页**（分页由 `read` 的行范围参数承担）。

```
输出 ≤ 8 KB              → 完整进 content
输出 > 8 KB              → content 里放：头 40 行 + 尾 40 行 + 总行数 + 截断说明
                          完整内容**不落盘**（P2 做），只记字节数进 details
```

**与架构 5.3 节三元策略的差异要登记**：架构写的中间档
（8KB–256KB）是"落盘 + 头尾各 40 行 + 文件路径"，P1 没有落盘能力，
所以中间档与高档合并成同一处理，**只少了"文件路径"这一项**。

**这个差异有一个可观测的后果**：模型被截断后**无法拿到完整输出**
（P1 没有落盘、没有分页到文件），它只能靠 `read` 工具重新读文件。
对 `bash` 的输出（不是文件）**就是真的丢了**。

**所以截断说明文案必须写清这一点**，例如：

```
[输出被截断：共 12345 行 / 890 KB，此处只显示头 40 行与尾 40 行。
 P1 版本不保存完整输出，如需完整内容请缩小命令的输出范围。]
```

**"请缩小命令的输出范围"** 这句是关键：它把限制**变成了模型的行动指引**，
而不是让模型反复重试同一个命令。→ 这个文案本身值得一个单测。

## 7. 风险

### R1. `bash` 在 P1 无任何保护（最高风险）

D5 的三层软边界（工作区约束 / checkpoint / 钩子规则）在 P1 **一层都没有**。
`bash` 会以当前用户权限执行任意命令。

**对策**（三选一，建议乙）：

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| 甲 | 不做任何处理，只在文档写明 | 与 D5 的承诺脱节 |
| **乙（建议）** | CLI 启动时打印安全提示；评测任务全部在临时目录里跑 | 提示是"提醒"不是"约束"，挡不住真出事 |
| 丙 | P1 就给 `bash` 加命令黑名单 | 与 P3 的钩子设计冲突，大概率重写 |

**选乙。** 理由是 P3 的钩子体系是完整设计，现在做黑名单等于用一个必然被替换的东西
换取虚假的安全感——**名义防护比没有防护更坏**（这是本项目已固化的纪律）。

### R2. 没有压缩 → 长任务必然失败

见 0.1 代价第 2 条。**对策：评测任务限定为短任务，且把这条限制写进报告**。
不做"挑任务规避"，而是**如实声明适用范围**——这两者的区别在于是否说清楚。

### R3. `_stream_model` 的聚合逻辑（技术风险最高）

多工具 index 交错、arguments 跨片拼接、JSON 解析失败、usage 与 finish_reason
的到达顺序——**四件事里有三件在离线测试里很难造全**。

**对策**：`scripts/real_api_smoke.py` 的 P4/P5 探测先在真实 API 上跑一遍，
把真实的分片形态录下来，**用录制数据造回放场景**。
先冒烟、后写 loop——这个顺序有硬理由，不是偏好。

### R4. `from_result` 与 `exclude_from_context` 的交互

若 `exclude_from_context=True`，消息进了历史但降级时被丢弃。
**症状**：模型看不到自己刚执行过的工具的结果，会重复调用同一个工具。

P1 没有场景需要这个字段（是给 P4 的扩展准备的），
**但它是"类型有能力、实现没验证"的典型**。
→ 列入第 9 节待复核清单，**不假装已验证**。
