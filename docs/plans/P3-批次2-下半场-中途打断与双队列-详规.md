# P3-批次2(下半场):用户中途打断 + steering/follow-up 双队列 详规

> 立项:2026-09-26 ｜ 需求方:星辰 ｜ 状态:**✅ 已落地(2026-09-26,拍板见 §4;G108–G110 全绿)**
> 前置阅读:`architecture.md` 4.3(steering 送达时机)、`sigma_ai/base.py`(CancelToken,P1 预留)、`P4-批次5`(增量持久化=断点重续的地基)、`P3-批次2 上半场`(交互通道)

## 0. 需求原话(星辰,2026-09-26)

> 1. 支持用户中途打断——断点重续之前已经实现了,只需要增加一个用户使用的、用于强制打断当前 loop 的外部信号;
> 2. 同时支持用户 steering:给当前 loop 追加新的 context 作为补充信息,指导 agent 工作方向;
> 3. 支持用户等待过程中发送下一条消息:消息处于等待队列中,上一条消息处理完毕自动执行。

一句话:**架构 4.3 的双队列 + P1 的 CancelToken,接到 REPL**。增量持久化已让打断后的状态落在树上,断点重续(轮前悬空修复)免费复用。

## 1. 现状

| 件 | 现状 |
| --- | --- |
| 外部信号 | `CancelToken` 抽象 P1 就有,provider 每个流块检查 `raise_if_cancelled()`;但只有 `NeverCancelled` 一个实现,CLI 从未接过 |
| steering | 只有 todo steering(防跑偏提醒);用户主动注入的通道没有。loop 在轮开始处已有注入点(信箱 drain 同款) |
| follow-up | 没有。CLI 横幅明说"不支持中途打断" |
| 断点重续 | ✅ 增量持久化 + 轮前悬空修复(Review-2026-09-26) |

## 2. 方案

### 2.1 外部信号(需求 1)

- `sigma_ai/base.py` 新增:
  - `TurnCancelled(RuntimeError)` —— 打断异常,**树上状态已持久化**,可断点重续;
  - `InterruptToken(CancelToken)` —— 线程安全的可触发令牌(`cancel()` 可从任意线程调,读输入在后台线程)。
- `AgentLoop.run_turn(messages, *, signal: CancelToken | None = None)`:允许**按轮覆盖**信号(构造参数仍是默认值);轮开始处与 provider 流块边界都会检查 → **协作式打断**:当前工具跑完、流在下一个块边界停——不留半截写操作,协议状态干净。
- `InteractiveSession`:构造参数 `signal=None` 时,**每次 send 新建一个 `InterruptToken`**(打断状态不跨任务泄漏);新增 `interrupt()`(外部线程调用,cancel 当前轮令牌)。调用方显式传了固定 signal(评测的 `NeverCancelled`)→ `interrupt()` 无操作。
- REPL:`/stop` 或 `!!` → `manager.current.interrupt()` → 打断异常从 send 冒出 → REPL 打印"已打断,进度已保存(树上 N 条消息),下次继续会自动接上" → 回到提示符。Ctrl+C 行为不变(整程序退出,exit 130)——Windows 的信号处理复杂度不值得,打断有专用命令。

### 2.2 steering(需求 2,架构 4.3 语义)

- `AgentLoop` 新增 `steering_drain: Callable[[], list[AgentMessage]] | None`:**每轮开始时**(模型调用前)取走并注入——与信箱 drain 同一个注入点、同一条持久化路径(`MessageInjected` 事件)。
- `InteractiveSession.submit_steering(text)`(后台线程可调,线程安全):把文本包成 user 消息放进队列;`steering_drain` 回调由产品壳接线。
- 送达时机按架构 4.3:**当前批次的工具执行完后、下一次模型调用前**——不打断在跑的工具,补充信息指导"接下来"的方向。

### 2.3 follow-up 等待队列(需求 3)

- `InteractiveSession.submit_followup(text)` / `pop_followup()` / `has_followups`(线程安全)。
- 自动执行在 **REPL 层**:send 正常完成后,若队列非空 → 取一条 → 作为新任务再 send(压缩/预算边界自然生效);`status != "completed"`(error/stopped/被打断)→ **不自动续**,失败先让人看到。

### 2.4 REPL 输入重构(三功能共用的底座)

- **单一 stdin 消费者**:REPL 启动时开一个守护读线程,把所有输入行放进队列;REPL 空闲时从队列取(替代现在的 `to_thread(input)`)。**任务运行期间**由一个 feeder 协程消费同一队列,按约定分类(见 §4 拍板):打断 / steering / follow-up。这消除了"运行中读输入"与"提示符读输入"的抢线问题(P5 机制的延伸)。
- EOF(管道/CI)→ 读线程放哨兵 → REPL 正常退出;现有测试的 monkeypatch input 继续可用(读线程吃全部行进队列)。
- 一次性 `-p` 模式:不变(无交互),Ctrl+C 仍走 exit 130。

| 项 | 结果 |
| --- | --- |
| 外部信号 | `sigma_ai/base.py`:`TurnCancelled(RuntimeError)` + `InterruptToken(CancelToken)`(线程安全置位;协作式检查点 = provider 每流块边界 + 每轮开始)。`run_turn` 新增按轮覆盖参数 `signal`;loop 内部 `effective_signal` 两级回退到 `NeverCancelled` |

**踩坑记录**:① 信号沿调用链传递时两度漏传(`_execute_batch`/`_run_write_batch` 是独立方法)与两度引用错名——全套测试当场 NameError 47 连红,这正是"全量跑绿"纪律的价值;② 读线程首版**漏写成功路径的投递**(只有 EOF 分支 put)——表现为"所有输入消失",用探针测试(fake_input 调用记录 vs broker 收到内容)定位;③ FakeProvider 轮次瞬时完成,"运行中敲入"在测试里必然竞态——REPL 级 G110 用例改用**预置队列**的确定性写法,运行中分类的时序正确性由 `turn_running` 标志 + InterruptToken 单测覆盖。
