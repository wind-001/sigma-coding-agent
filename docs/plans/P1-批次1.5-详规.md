## 0. 本批次要回答的问题

**一句话**：把消息模型补齐成**两层**——会话里存的是 `AgentMessage`，
发给模型的是 `LlmMessage`，中间隔一个显式的单向降级函数。

**为什么这一层不能省**

    架构方案 4.0 节的原话是：

    > **这两层不是同一个东西，混为一层是本设计最容易犯的错误。**
    > 会话里存的东西**不等于**发给模型的东西。

    混为一层的代价在三处兑现：
    - 「存了 UI 专属通知但模型看不见」——单层结构下要额外加过滤机制，
      双层结构下**免费得到**；
    - P2 的压缩摘要无法作为一等公民消息存放（见 1.3）；
    - 扩展想注入自定义消息时，只能去污染 wire protocol 的四类 role。

**本批次不接触 loop、工具、会话树、压缩。** 它只做"两层结构的那一半"，
但这一半里有三处**必须现在做对、否则后面返工**的地方：

1. **注册表与重名报错规则**（P2 加压缩摘要类型时不能回头改核心）
2. **认不出的类型不得静默丢弃**（Python 没有编译期穷尽性检查）
3. **`*_signature` 字段必须原样透传**（降级函数的实现细节，漏了就丢）

## 2. 逐项规格

### 2.1 `AgentMessage`：同时继承 `BaseModel` 和 `ABC`

```python
class AgentMessage(BaseModel, ABC):
    """agent 层消息抽象基类。

    继承 BaseModel 是为了序列化（会话树要落盘 JSONL）；
    继承 ABC 是为了强制子类实现 to_llm()。
    """
    timestamp: int

    @abstractmethod
    def to_llm(self) -> LlmMessage | None:
        """降级成 LLM 层消息。

        返回 None 表示这条消息不进模型上下文
        （例如 UI 专属通知、被 exclude_from_context 标记的 bash 记录）。
        """
        raise NotImplementedError
```

**两个必须现在想清楚的点**：

**（一）这是一个**例外**，要登记。**
`AGENTS.md` 第 3 条说"元数据类型尽量用 BaseModel"，第 2 条说"采用继承制"。
本类**两者都要**——架构方案第 2 节（第 65 行）已经把它标为
「一处需要按层判断的例外」。**有意的例外要写在文档里，不能沉默地存在**，
否则后来的人会以为是笔误。

**（二）Pydantic 的 `ABC` 与 `model_config.arbitrary_types_allowed` 无关。**
多继承 `BaseModel, ABC` 是标准做法，不需要任何额外配置。
但要注意：**`@abstractmethod` 在 Pydantic 下仍然生效**——
`AgentMessage(timestamp=1)` 会抛 `TypeError`，这是 G15 的断言内容。

### 2.2 注册表：`register_message_type()` 与 `DuplicateMessageType`

```python
_MESSAGE_TYPES: dict[str, type[AgentMessage]] = {}

class DuplicateMessageType(ValueError):
    """同一个 role 被注册了两次。**不允许静默覆盖。**"""

def register_message_type(cls: type[AgentMessage], *, role: str) -> type[AgentMessage]:
    """扩展用这个函数挂载自己的消息类型。

    对应 Pi 的 `declare module`（declaration merging），
    但 Pi 是编译期被动填充，这里是运行期主动注册。
    代价是失去编译期穷尽性检查，收益是不用改核心包、且可在运行时注册
    ——与 D3 节「扩展层是运行时可变状态」更契合。
    """
    if role in _MESSAGE_TYPES:
        raise DuplicateMessageType(role)
    _MESSAGE_TYPES[role] = cls
    return cls
```

**三个设计决定**：

**（一）`role` 作为参数传，不从类上读。**
替代方案是让子类定义一个 `role: Literal[...]` 字段再 `getattr`。
**否决理由**：那样注册表与字段会形成一棵隐式的耦合，
且"注册时给的 role"与"实例上的 role 字段"可能不一致——
不一致时按哪个走？**没有好答案的设计就是错的设计。**

**（二）`DuplicateMessageType` 继承 `ValueError`，不是自定义 `Exception`。**
理由：它与 `errors.py` 里的 `ErrorCode` 家族无关（那是 provider 错误语义），
但它确实是"值非法"。继承 `ValueError` 让调用方可以用标准的异常处理，
且 `mypy` 的类型检查方向也认可这个方向（批次 1 已经踩过一次）。

**（三）`register_message_type` 的返回值是 `cls`。**
让它能当装饰器用：`@register_message_type(role="custom")`。
**这是 Pi 没有的能力，但成本为零**（一个 `return cls`）。

### 2.3 两个子类（P1 只落地这两个）

架构方案 4.0.3 节明确：「P1 只要两个子类」——`LlmMessageWrapper`、
`ToolResultAgentMessage`。**压缩摘要与分支摘要留到 P2，类型不写。**

```python
@register_message_type(role="llm")
class LlmMessageWrapper(AgentMessage):
    """包住四个 LLM 模型。

    为什么需要它：会话里存的是 agent 层消息，但 LLM 层的四条消息
    **语义上已经是 agent 层消息的一种**——它们没有额外的应用语义。
    用 wrapper 而不是让四个 LLM 模型直接继承 AgentMessage，
    是为了保持 LLM 层「严格对应 wire protocol、无基类」这条边界
    （架构方案 4.0.1 节的结论）。
    """
    role: Literal["llm"] = "llm"
    message: LlmMessage

    def to_llm(self) -> LlmMessage | None:
        # 规则 1：原样透传，不重新构造。见 2.4。
        return self.message


@register_message_type(role="tool_result")

    role: Literal["tool_result"] = "tool_result"
    tool_call_id: str
    tool_name: str
    content: list[ContentBlock]

    @classmethod
    def from_result(cls, call: ToolCallBlock, result: ToolResult) -> ToolResultAgentMessage:
        """从工具执行结果构造。loop 用这个（批次 4）。"""
        ...

    def to_llm(self) -> LlmMessage | None:
        if self.exclude_from_context:
            return None          # 规则 3：显式丢弃
        return ToolResultMessage(...)
```

**关于 `ToolResult` 的类型**

    它定义在批次 2 的 `sigma_agent/types.py`，**本批次还不存在**。

### 2.4 `convert_to_llm()`：四条规则，逐条落地

```python
def convert_to_llm(messages: list[AgentMessage]) -> list[LlmMessage]:
    """agent 层 → LLM 层。**唯一通道。**"""
```

**规则 1：LLM 消息原样透传，不重新构造。**

    这是防"丢 `*_signature` 字段"的关键。**不要写
    `UserMessage(role=m.role, content=m.content, timestamp=m.timestamp)`
    这种"看起来更明确"的代码**——它会在 LLM 层新增字段时静默丢字段，
    而症状（多轮对话异常）不指向根因。

    **落地形式**：`LlmMessageWrapper.to_llm()` 直接 `return self.message`。
    单测断言"透传后的对象与原来**是同一个对象**"（`is` 而不是 `==`），
    这条断言能证伪任何"重新构造"的实现。

**规则 2：agent 层自定义消息统一降级成 `user`。**

    本批次只有 `ToolResultAgentMessage` 是非 LLM 消息，而它降级成
    `ToolResultMessage`（`role="tool_result"`）。
    **所以规则 2 在 P1 没有实际的适用对象**，但**降级路径要通**——
    单测用一个临时注册的自定义类型来验证它降级成 `user`。

    **这条不能等到 P2 再加**：P2 的压缩摘要必须降级成 `user`（不是 `system`），
    而那是架构方案第 8 节门禁「摘要降级位置」的断言对象。
    本批次把这条路先铺通，P2 只是往里填一个类型。

**规则 3：`exclude_from_context` 的消息显式丢弃（返回 `None`）。**

    落地在 `ToolResultAgentMessage.to_llm()` 里。
    单测断言：标记后的消息**完全不出现在**结果列表里（不是变成空消息）。

**规则 4：认不出的类型——记录 warning，不静默丢弃。**

    **这是本批次唯一一处"不照抄 Pi"，也是最需要想清楚的一处。**

    | Pi 的做法 | sigma 的做法 |
    | --- | --- |
    | 认不出的 role 返回 `undefined`，被 `filter` 静默丢弃 | **记录 warning，并透传原样（若可能）或抛错** |

    Pi 静默丢弃是**安全的兜底**，因为它的联合类型在编译期已封闭、
    `default` 分支理论上不可达。**Python 没有编译期穷尽性检查**——
    静默丢弃会变成"消息莫名消失"且无从排查。

    **具体处置**（这里有个必须做的选择）：

    | 方案 | 行为 | 取舍 |
    | --- | --- | --- |
    | 甲 | 抛 `UnconvertibleMessageError` | 最严格，但**一个坏消息会毁掉整轮对话** |
    | 乙 | 记 warning + `str(msg)` 包成 user 消息 | 不丢信息，但会把垃圾塞进上下文 |
    | **丙** | **记 warning + 丢弃** | 保留可运行性，但仍是丢弃 |

    **推荐丙**，理由：
    - 与"宁可崩不要错"的**表面**冲突，但与**实质**一致——
      架构方案 4.0.5 节的原话是「记录 warning **或**直接抛错」，
      它没规定必须抛错；
    - 抛错（甲）的代价过高：扩展写错一个类型会让整个 session 崩掉，
      而这条消息可能只是 UI 通知；
    - warning 保证"不会无从排查"——这是第 4 条真正要防的东西；
    - 乙会把不可控内容塞进上下文，**污染 prompt cache 且不可预测**。

    **但丙有一个必须补的约束**：`warning` 必须**可捕获且带上下文**
    （消息的 `type` 与 `role`），否则 warning 本身就成了新的"无从排查"。
    用 `warnings.warn(..., UnconvertibleMessageWarning)`，单测 `pytest.warns` 断言。

    **这条选择需要你确认**——见第 10 节待确认项 W1。

### 2.5 会话落盘格式（本批次要定，否则批次 4 返工）

`AgentMessage` 要能 JSONL 往返（会话树落盘）。**Pydantic 的判别联合
在这里有一个真实的坑**：`AgentMessage` 是基类，
反序列化时 Pydantic 不知道该造哪个子类。

**两条路**：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 甲 | 每个子类用 `Literal` 判别字段 + `Annotated[Union, Field(discriminator=...)]` | **每加一个类型都要改那个 Union**——与 D3「扩展层是运行时可变状态」冲突 |
| **乙** | **注册表驱动的手工分派**：读 JSON → 取 `role` → 查 `_MESSAGE_TYPES` → 造对应子类 | 要自己写序列化/反序列化函数，但**扩展注册的类型自动生效** |

**推荐乙**，理由：
- 甲方案下，扩展注册的新类型**无法被反序列化**（因为不在 Union 里），
  除非扩展能改核心包的 Union——那正是 D3 要避免的；
- 乙方案让注册表成为**唯一的事实来源**，与 2.2 节的设计一致；
- 乙的额外成本约 20 行。

**落地形式**：

```python
def message_to_dict(message: AgentMessage) -> dict[str, Any]:
    """序列化成可落盘的 dict。role 由注册表反查，不从实例读。"""

def message_from_dict(payload: dict[str, Any]) -> AgentMessage:
    """从 dict 还原。未知 role 抛 UnknownMessageType（不返回 None）。"""
```

**注意"未知 role"在两个方向上的不同处置**：
`convert_to_llm` 遇到未知类型是 **warning + 丢弃**（运行期容错），
`message_from_dict` 遇到未知 role 是 **抛错**（落盘数据不可信）。

**看起来矛盾，其实不矛盾**：前者是"这条消息暂时没法处理"，后者是"这份数据坏了"。
**这个区分要写进 docstring**，否则下一个人会以为是疏忽。

## 4. 三处设计取舍

### 4.1 为什么 `LlmMessageWrapper` 而不是让四个 LLM 模型继承 `AgentMessage`

四个 LLM 模型直接继承 `AgentMessage` 更省一层包装。**否决理由**：

- 会让 LLM 层产生基类依赖，而架构方案 4.0.1 节的结论是
  「这一层不做抽象，加基类只会让协议转换更难写」；
- LLM 层是**协议对齐层**，它不该知道 agent 层的存在——
  这正是 G18 契约要机器检查的边界。

**判据**：**LLM 层的字段是为协议服务的，agent 层的字段是为应用服务的。**
混成一层的症状是"为了满足某个应用需求去给协议消息加字段"。

### 4.2 为什么不用 Pydantic 的 discriminated union 做反序列化

见 2.5 节。**核心冲突是 D3**：

> 扩展层是运行时可变状态。

`Annotated[Union[...], Field(discriminator="role")]` 是**静态集合**，
扩展无法在不改核心包的前提下往里加类型。**这与 D3 直接冲突**，
所以只能走注册表分派。

### 4.3 `exclude_from_context` 放在 agent 层而不是 LLM 层

放 LLM 层的话，`ToolResultMessage` 会多一个协议里不存在的字段，
而它**会随消息发给 provider**（除非转换时排除）。

**判据**：**只有 agent 层能持有"不进上下文"的语义。**
LLM 层一旦有了这个字段，就必须在任何发送路径上记得排除它——
这是典型的"靠约定维持的正确性"，会漏。

### G11 是本批次最该做对的一条

    批次 1 的 G2 验证的是「签名字段能经 JSON 往返存活」，
    它防的是**序列化丢字段**。

    G11 验证的是「签名字段能经降级函数存活」，
    它防的是**转换时重新构造对象**。**这是两个不同的失败模式。**

    一个看起来更"明确"的实现：

    ```python
    def to_llm(self) -> LlmMessage:
        m = self.message
        if isinstance(m, AssistantMessage):
            return AssistantMessage(
                role=m.role, content=m.content, usage=m.usage,
                stop_reason=m.stop_reason, timestamp=m.timestamp,
                # ← 忘了 api / provider / model / response_id / error_message
            )
    ```

    **它完全合法、能跑通、批次 1 的 G2 也拦不住它**——
    因为 G2 测的是 Pydantic 自己，不是这段代码。
    而结果是多轮对话里 provider 元数据丢失。

    **所以 G11 的断言必须是 `result[0] is original`（同一对象）**，
    不是 `==`（值相等）。`==` 在"重建了但字段凑巧全对"时也会过，
    而那种实现会在 LLM 层新增字段后的**下一次**才出问题。

### G15 是一个新的组合，不能假设批次 1 的经验能直接套

`AgentMessage` 同时继承 `BaseModel` 和 `ABC`。
批次 1 测过纯 `ABC`（`BaseProvider`）与纯 `BaseModel`（四个 LLM 模型），
**但没测过两者多继承**。

**要验证的具体问题**：
- `@abstractmethod` 在多继承下是否仍然在**实例化**时报错？
- Pydantic 的 `model_fields` 与 ABC 的 `__abstractmethods__` 是否互相干扰？

### 10.2 评审修复的真实缺陷：`convert_to_llm` 用类相等性替代了 `to_llm()`

**发现方式**：2026-09-20 独立评审（不采信交付方转述，直接对磁盘现状跑验证）。

**缺陷**：判据 `_MESSAGE_TYPES.get(role) is not type(message)`
要求实例的类**恰好等于**注册的类，于是**已注册类型的子类实例**
会被 warning + 丢弃——`to_llm()` 一次都没被调用。

| 实测 | 结果 |
| --- | --- |
| `Sub(LlmMessageWrapper)` 实例直接调 `to_llm()` | 返回 `UserMessage`（合法） |
| 同一实例过 `convert_to_llm` | `[]` + 1 条 warning（消息被丢弃） |

**它同时违反本模块自己写下的两条规则**：
①「所有消息都经 `to_llm()`」——`is not type(...)` 就是绕过；
②「丢弃是子类的显式表态」——由实现替子类做了决定。

**为什么 `9/9` 全绿与这个缺陷能同时成立**：E11–E18 **全部不覆盖子类化路径**。
这是**第三次出现「配置全绿但约束有洞」**（前两次：P0 的 `layers` 兄弟层、
批次 1 的 G10 目标测试指错对象）。

**修法**：把判据拆成两个——
① 注册表**认不认识这个 role**（`_MESSAGE_TYPES.get(role) is None` 才丢弃）；
② **降级成什么**完全交给 `to_llm()`。

**注意 `message_to_dict` 里的同一表达式是对的、不得改**：
编码要严（子类可能有父类没有的字段，存下去会丢），降级要宽（由子类表态）。
**同一个写法、两处语义相反，是有意的**——由 `test_encode_stays_strict_for_subclass` 钉住。
