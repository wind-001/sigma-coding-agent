## 1. 现状诊断(为什么值得重构)

### 1.1 结构问题(实锤,不是感觉)

| # | 事实 | 后果 |
| --- | --- | --- |
| 1 | 技能系统**分裂两处**:`sigma_agent/skills.py`(发现/索引)与 `sigma_session/resources.py`(AGENTS.md)各管一摊,`sigma_tools/skill.py` 是第三个相关文件 | "技能在哪"要跨三个包才能答全 |
| 2 | 钩子被**三层消费**:loop 发事件、`sigma_session/trace.py`+`persist_hook.py` 是订阅者、`sigma/_approval.py` 又定义审批——"钩子系统"没有一个家 | 与朋友布局的 hooks/ 相比,模块边界模糊 |
| 3 | 装配逻辑(`sdk.py` 1102 行)与 CLI(1466 行)同居 `sigma/` 包,系统提示词**硬编码在 sdk.py 里**(159-247 行) | 提示词是核心资产却埋在装配代码中间;挑刺#3 成立 |
| 4 | 私有模块靠 `_` 前缀约定:`_paths` `_approval` `_selector` `_credit_ledger` `_source_policy` | 目录化后这些前缀失去意义,名字也不达意(`_paths` 看不出是安全边界) |
| 5 | 包名 `sigma_ai / sigma_agent / sigma_session / sigma_tools` 是"层名"不是"功能名" | 面试官/新读者无法从目录名读出系统做什么 |

### 1.2 封装问题(减 pydantic 的证据)

全库 **43 个 BaseModel 子类 + 34 个 dataclass**。逐类核对后分三档:

| 档 | 数量 | 判定 |
| --- | --- | --- |
| **必须保留 pydantic** | ≈27 | 工具参数模型 13 个(JSON schema 自动生成是机制核心)、LLM 消息 10 个(JSONL 落盘 + 协议字段保真)、协议载体(Usage/SamplingParams/StreamOptions/ToolCallDelta 参数) |
| **超配,应降 dataclass** | 6 | `sigma_ai/events.py` 的流事件家族(TextDelta…ErrorEvent)。**项目自己的判据**写着"事件是瞬时通知,不是领域模型"(hooks.py 头注),钩子事件也确实全是 dataclass——流事件用 pydantic 与自家判据**不一致**,这是现成的减封装论据 |
| **待逐个核对** | ≈10 | `eval_profile` / `store` / `skills` / `hooks` / `todo` / `task` / `_credit_ledger` 里的散装模型,按 §5 三问判定 |

### 1.3 命名问题(浅显易懂的差距)

典型:`_paths.py`(实为工作区路径边界=路径沙箱)、`compact.py`(上下文压缩)、
`checkpoint.py`(影子 git 回滚)、`_selector.py`(按键式交互选择)、
`agent_messages.py`(agent 层消息模型)。对照朋友简历词汇
(path_sandbox / context_compressor / sub_agent),sigma 的实现**有实而无名**。

### 2.2 新分层契约(import-linter 重写,不是删除)

层表自上而下(上层可 import 下层,反向即 CI 失败)。
**2026-09-29 修正**:初版层表把 agent 排在 events 之上是排序错误——events 的
载荷引用 agent 层消息,必须 events 在上、agent 在下。开工前逐边核对后的定稿:

```
1  sigma.cli            ← 无(参数解析、REPL、渲染、交互)
2  sigma.sdk            ← 组装一切(唯一装配点)
3  sigma.observability  ← hooks, sessions, agent, providers
4  sigma.runtime        ← tools, security, hooks, sessions, events, agent, providers
5  sigma.tools          ← skills, security, agent, providers
6  sigma.skills         ← providers
7  sigma.security       ← hooks, agent, events
8  sigma.hooks          ← sessions, events, agent
9  sigma.sessions       ← agent, providers, config
10 sigma.memory         ← providers
11 sigma.events         ← agent
12 sigma.agent          ← providers
13 sigma.prompts        ← providers
14 sigma.config         ← 无
15 sigma.providers      ← 无(最底层)
```

排位依据(为何 security 在 hooks 之上、tools 在 security 之上):
`security/approval.py` 的审批门实现 ApprovalHook(→ security 必须高于 hooks);
`tools/builtin` 的写工具引用 path_sandbox(→ tools 必须高于 security);
`hooks/persist.py` 引用 sessions.tree(→ hooks 必须高于 sessions)。

保留两条配套契约:核心包禁止 import `evals`/`extensions`/`scripts`;
删除原"内置工具与会话层互不依赖"independence 契约(它只为钉住旧兄弟层而存在,
新结构里 tools 与 sessions 相隔三层,无歧义)。

**每条新依赖边在搬迁时逐边核对**(以 grep 实际 import 为准,层表允许微调),
搬迁完成的标志 = lint-imports 对新层表全 KEPT。

### 2.3 与朋友布局的差异(有意为之,逐条给理由)

| 朋友布局 | sigma 处置 | 理由 |
| --- | --- | --- |
| infrastructure/(db/redis/file_storage/logger) | **不设** | sigma 无数据库;JSONL store 属会话域不属基础设施;日志即钩子(trace+persist)。**不造空壳目录装样子**——空目录在面试里一戳就破 |
| agent/(base_agent/mailbox/team_task) | 拆开:循环→runtime/,子agent→runtime/sub_agent.py | sigma 刻意只有一个循环(唯一 loop 契约);mailbox/team_task 是 sigma 明确不做的(D2/2.3),不为对齐布局造假抽象 |
| config/(permission_rules/mcp_config) | config/ 只装真实存在的(settings/caps);审批规则在 security/approval.py | MCP 在砍掉清单;不为布局造配置文件 |
| runtime/task_converger.py | 并入 event_loop.py | 收敛逻辑就是循环的一部分,sigma 没有独立收敛器,不拆 |
| memory/providers/(tencent_db/python_custom) | memory/file_store.py 单实现 | MemoryHub 多 provider 是朋友的项目;sigma 的记忆是文件式单实现(T1 拍板),不虚构 provider 抽象 |
| events/event_bus.py | 不设独立总线 | HookManager 就是总线,再设 event_bus 是重复抽象 |

**原则:结构向朋友布局对齐(功能域分目录),内容向 sigma 现实对齐(有实才有名)。**
虚设的目录不是资产,是面试负债——被问"redis 用来干什么"答不上比没有更糟。

## 3. 五条挑刺的处置(逐条)

### 3.1 events/ 与 hooks/ 职责重叠 → "events 定义机制,hooks 提供订阅者",写死边界

- `events/lifecycle.py` = **纯事件定义**(frozen dataclass,零行为);
- `hooks/base.py` = BaseHook(订阅者 ABC)+ HookManager(总线);
- 流事件(StreamEvent)**留在 providers/events.py**,不进 events/——理由:
  它是 Provider 抽象的返回类型(协议表面的一部分),且其载荷引用 Usage(协议类型),
  搬进 events/ 会造成 providers↔events 包级循环。两套事件在 runtime 汇合:
  loop 消费流事件、转发生命周期事件给钩子。
- 边界写进两包 `__init__` docstring + 一条单测断言(events 不得 import hooks,
  hooks 必须只通过 events 的类型声明订阅签名)。

### 3.2 sessions/compaction 与 memory/ 边界 → 名字分家 + 双向指认

- `sessions/compaction.py`:**短期**——会话内上下文超预算时的有损压缩(对 prompt 有损、对磁盘无损);
- `memory/file_store.py`:**长期**——跨会话的 markdown 记忆文件(允许过时,渐进披露);
- 两个模块的 docstring 首段互相点名对方并划界(现 memory.py 已写"不是事实记录(那是会话树)",
  迁移时补对称一句进 compaction.py)。不叫 context_compressor/compactor 这种易混对,
  从词根上断开。

### 3.3 缺 prompts/ → 新建,把提示词从 sdk.py(1102 行)里请出来

`prompts/system_prompt.py` 收编:`_SYSTEM_PROMPT_HEAD`、`_SYSTEM_PROMPT_RULES_*`、
`SYSTEM_PROMPT`、`build_system_prompt()`、TODO/ASK_USER 工具行、联网工具行、
记忆纪律段、todo 工具行拼接。sdk.py 只调用,不持有文案。
**注意**:提示词逐字节稳定是 D4 的前提,搬迁必须逐字节等价(门槛 G-P6-4 用哈希断言)。

### 3.4 缺装配层 → sdk.py 显式化为唯一装配点

sigma 本就有 `create_session()`(三处组装会各自漂移的纪律),问题只是它埋在
cli.py(1466 行)旁边不显眼。处置:sdk.py 独居包根,`cli/` 与 `evals/`/`scripts/`
一律经它组装;`cli/main.py` 只做参数解析与循环调用。补一条 lint:cli 不得直接
import runtime/tools/sessions(只能经 sdk)——装配单一,写进契约。

### 3.5 缺可观测性 → observability/(trace + timeline)

已有实现在 `sigma_session/trace.py`(逐事件 JSONL)与 `sigma/timeline.py`
(--timeline 视图),合并成 observability/ 包。挑刺成立的部分是**它们现在分居两会话相关包**,
观感上像"会话的附属品";独立成包后与简历叙事对齐。
