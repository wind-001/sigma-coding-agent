## 1. 目标与验收门

**目标一句话**：让 sigma 能在一个真实小仓库上，端到端修好一个单文件 bug，
并且这个能力**有数字**。

**架构方案第 9 节给 P1 定的硬性验收门（原文照录，不软化）**：

1. 在真实小仓库上端到端修复一个单文件 bug；
2. agent loop 单测全部走回放、离线通过；
3. **10 条评测任务跑出第一份报告**。

**我补的第四条（理由在 1.1）**：

4. 输出**一份对照表**：B1（有工具无 harness）与 B2（完整 sigma）在同一批 10 条任务上的
   成功率与 token 对比。若 B2 相对 B1 无优势，**本阶段判定为失败，不是"再看"**。

### 1.1 为什么第 4 条不能推后

架构方案第 9 节末尾已经写了「P1 里就要有评测报告这一条不是可选项」。
但只跑 B2 是不够的：**没有 B1 做对照，"harness 有用"这个论断是空的**
（见方案 7.3 节，B1 是整份报告里最关键的一条对照）。

B1 的实现成本极小——它只是 `AgentLoop` 关掉压缩、钩子、checkpoint 之后的配置，
不是另写一套代码。所以没有理由推迟到 P5。

**如果说 P1 只保一个产出，就是这张对照表。**

## 4. 关键技术决策（已确认，见第 7 节）

本节原为"待确认的 4 项"，2026-09-20 已全部拍板，**结论以第 7 节为准**。
保留本节的作用是记录**当时的取舍理由**，供 ADR 与后续阶段回看。

### 4.1 内置工具的默认集 → **5 个**（P1 定稿）

原建议是 4 个（严格对齐 Pi 核心集），拍板时加了 `grep`，理由：
4 个工具覆盖不了"先跨文件搜索定位、再修改"这一任务形态，
而这类任务在真实修 bug 场景里占比高。

架构方案 5.1 节的常驻区预算（工具 schema 4 个 ≈ 700 token）**需要相应上调**：
`grep` 的 schema 约 120 token，**常驻区预算从 3,500 不变，但工具段从 700 调到约 820**。
剩余 3 个可选工具（`find` / `ls` / 其他）仍留到 P2 之后，并同时补 ablation 对照行。

### 4.2 `bash` 输出上限 → **提前到 P1**（Q2 已拍板）

只做截断，不做分页，不做落盘。分页与落盘仍属 P2。
理由见第 6 节 R2：P1 没有压缩机制，大输出会直接撞上下文上限；
靠"评测任务里不出现大输出命令"规避等于评测造假。

### 4.3 首个被测模型 → **DeepSeek `deepseek-chat`**（Q3 已拍板）

理由：国内直连可用、价格低、OpenAI 兼容协议原生支持、上下文窗口足够。

**成本预估**：10 条任务 × 2 档配置 × 平均 30K token/任务 ≈ 600K token，
按 DeepSeek 现行价格约 ¥2 以内。这个量级不需要走缓存优化。

**注意**：该价格需在批次 5 真正开跑前**重新核对一次**，
评测报告里的成本数字必须以实跑时的官方价目为准（不要沿用本节这个估算数）。

### 4.4 `-p` 一次性模式的退出码约定 → **0 = 正常结束，非 0 = harness 自身失败**（Q4 已拍板）

任务本身的成败（bug 有没有修好）**不进退出码**，由判定脚本记录到评测报告。
理由：任务失败是正常业务结果，把它混进进程退出码会让"harness 崩了"与"任务没做对"
无法区分，而 CI 与脚本调用只关心前者。

## 6. 风险与对策

### R1. 评测集自欺（最高风险）

方案 7.1 与 R3 已写明。**本次新增一条执行纪律**：

> 任务描述写完、跑评测之前，先把 10 条任务交给一个"没有工具的裸模型"（B0）跑一遍。
> **任何一条 B0 能直接答对的 A 类任务，作废重换。**

理由：B0 基线的作用就是证明"任务本身不能靠模型一次答对"（方案 7.3）。
如果 B0 通过率过高，说明任务太简单，B2 的成功率再高也说明不了 harness 有用。

### R2. `bash` 输出撑爆上下文（P1 特有）

P1 没有压缩（那是 P2）。当 `bash` 命令吐出 10 万 token 时，
**没有截断的 P1 会直接撞上 provider 的上下文上限，任务失败**。

这不是评测数据问题，是 P1 的实现缺陷。两个选项：

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **甲（建议）** | 把 `truncate.py` 的**截断部分**挪进 P1，不做落盘、不做分页 | 与方案 P2 的分配有一处出入 |
| 乙 | 严格遵守原分配，P1 靠"评测任务里不出现大输出命令"规避 | **用任务选择回避实现缺陷 = 评测造假**，不接受 |

**建议选甲。** 乙这条路的性质要认清：它让 P1 的评测结果看起来干净，
但那是因为任务被挑过了，不是因为 harness 做对了。这正是方案 R3 要防的事。

### R3. 时间预算（未解决，见第 8 节）

P1 按方案估算约 3 周 @ 8h/周 = 24 小时。**但 8h/周是总预算不是单项目预算。**

### R4. `edit` 工具的正确性

精确字符串替换 + unified diff，最容易出错的点是**多次匹配**。
方案没写这一条，**本计划补上约定**：

```
字符串在文件中出现 0 次   → is_error=True，提示"未找到，请先 read 确认当前内容"
字符串出现 1 次           → 执行替换
字符串出现 N > 1 次       → is_error=True，要求提供更大上下文或 occurrence 序号
```

**绝不"替换全部"**。静默替换多处是最难排查的一类 bug，与 4.4 节
「不允许扩展静默覆盖内置工具」同源。
