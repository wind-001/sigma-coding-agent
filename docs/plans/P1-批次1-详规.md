## 2. 逐项规格

### 2.1 `messages.py` —— 四个消息模型

```python
class SystemMessage(BaseModel):
    """system 消息。

    ⚠️ **不要往这里放压缩摘要。**

    摘要必须降级成 UserMessage（架构方案 4.0.6 节）。理由：system 消息进常驻区，
    而常驻区在会话内必须逐字节稳定（D4）；中途变化会让 prompt cache 从变动点起
    全部失效。见本文件 G9。

    本类字段集合由单测断言固定，新增字段会导致测试失败——这是有意的。
    """

    role: Literal["system"] = "system"
    content: str | list[TextBlock]
    # 提示词段落的具名增删改；None 表示删除该段（架构方案 4.0.4）
    sections: dict[str, str | None] | None = None
    tools_added: list[ToolMeta] | None = None
    tools_removed: list[str] | None = None      # 仅工具名，对应 Pi 的 ToolReference
    timestamp: int

class UserMessage(BaseModel):
    role: Literal["user"] = "user"
    content: str | list[ContentBlock]
    timestamp: int

class AssistantMessage(BaseModel):
    role: Literal["assistant"] = "assistant"
    content: list[ContentBlock]
    api: str = ""
    provider: str = ""
    model: str = ""
    response_id: str = ""
    usage: Usage
    stop_reason: StopReason
    error_message: str = ""
    timestamp: int

class ToolResultMessage(BaseModel):
    role: Literal["tool_result"] = "tool_result"
    tool_call_id: str
    tool_name: str
    content: list[ContentBlock]
    details: dict[str, Any] = {}
    is_error: bool = False
    timestamp: int

LlmMessage = SystemMessage | UserMessage | AssistantMessage | ToolResultMessage
```

**四个内容块**：

```python
class TextBlock(BaseModel):
    type: Literal["text"] = "text"
    text: str
    text_signature: str | None = None

class ThinkingBlock(BaseModel):
    type: Literal["thinking"] = "thinking"
    thinking: str
    thinking_signature: str | None = None
    redacted: bool = False

class ImageBlock(BaseModel):
    type: Literal["image"] = "image"
    data: str
    mime_type: str

class ToolCallBlock(BaseModel):
    type: Literal["tool_call"] = "tool_call"
    id: str
    name: str
    arguments: dict[str, Any]
    thought_signature: str | None = None

ContentBlock = TextBlock | ThinkingBlock | ImageBlock | ToolCallBlock
```

### 2.2 三个 `*_signature` 字段 —— 本批次最容易被做错的地方

**它们是什么**：provider 返回的不透明串，**必须原样回传**。
典型例子是 Gemini 的 `thought_signature`、Anthropic 的 `thinking_signature`。

**漏了会怎样**：多轮对话里模型行为异常（例如工具调用后不继续、
thinking 模式报错），**但症状完全不指向根因**——你不会想到是这里丢的字段。

**本批次的硬门槛**（比"能跑通"更重要）：

> 构造一条带全部三个签名字段的 `AssistantMessage`，
> 经过 `model_dump_json()` → `model_validate_json()` 往返后，
> **三个字段逐字节不变**。

这条断言很便宜，但**它防的是一类极难排查的 bug**。

### 2.3 `base.py`

```python
class CancelToken(ABC):
    """取消信号。用 ABC 因为未来会有多种实现（signal / asyncio / 计时器）。"""

    @abstractmethod
    def is_cancelled(self) -> bool: ...
    @abstractmethod
    def raise_if_cancelled(self) -> None: ...


class SamplingParams(BaseModel):
    """采样参数。**2026-09-20 补入（B1.3 的产物）。**

    原先 `stream()` 签名里没有这些字段——那是只写 FakeProvider 时会犯的错：
    FakeProvider 不需要它们，于是签名看起来够用。真实 provider 必须能传。
    """
    temperature: float | None = None
    max_tokens: int | None = None
    top_p: float | None = None


class StreamOptions(BaseModel):
    """流式请求的可选项。**2026-09-20 补入（B1.3 的产物）。**

    `include_usage` 尤其关键：OpenAI 兼容协议默认**不在流里返回 usage**，
    必须显式请求。没有这个开关，P1 的用量统计只能靠估算——
    而估算数不能进评测报告（见 4.1 节）。
    """
    include_usage: bool = True
    response_format: dict[str, Any] | None = None


class BaseProvider(ABC):
    @abstractmethod
    def stream(
        self,
        messages: list[LlmMessage],
        tools: list[dict[str, Any]],
        *,
        model: str,
        signal: CancelToken,
        sampling: SamplingParams | None = None,      # ← B1.3 补
        options: StreamOptions | None = None,        # ← B1.3 补
        timeout_s: float | None = None,              # ← B1.3 补
    ) -> AsyncIterator[StreamEvent]:
        raise NotImplementedError

    @abstractmethod
    def estimate_tokens(self, messages: list[LlmMessage]) -> int:
        raise NotImplementedError
```

#### 为什么这几个字段是 B1.3 的直接产物

`SamplingParams` / `StreamOptions` / `timeout_s` 三个参数，
**只写 `FakeProvider` 的版本里完全没有**——因为回放不需要采样、不需要请求用量、不会超时。

**真实协议一接进来它们立刻全部暴露**：

| 字段 | 为什么必须有 | 只有 FakeProvider 时暴露不了 |
| --- | --- | --- |
| `temperature` / `max_tokens` | OpenAI 兼容协议的标准参数，评测要控制变量 | 回放与采样无关 |
| `top_p` | 同上 | 同上 |
| `options.include_usage` | **不显式请求，流里就没有 usage** | 回放直接吐 `UsageEvent`，不需要请求 |
| `options.response_format` | 结构化输出（未来用） | 同上 |
| `timeout_s` | 网络调用必须能设超时 | 回放不会超时 |

**这就是 B1.3「用真协议逼出签名问题」的实际收益——上表五个字段，一个都躲不掉。**

**注意 `signal: CancelToken` 仍是自造类型。** 真实 `httpx` 用
`asyncio.CancelledError` / `httpx.TimeoutException`。
**这个抽象在批次 1 无法被完全验证**，需在批次 4 接真实 API 时复核——
已记入第 9 节「待批次 4 复核」清单。

**硬门槛**：`BaseProvider()` 与 `CancelToken()` 直接实例化**必须抛 `TypeError`**。
这是 a2（继承制）的第一处落地验证。

### 2.4 `events.py` —— 五类流式事件

```python
class TextDelta(BaseModel):
    type: Literal["text_delta"] = "text_delta"
    text: str
    text_signature: str | None = None

class ToolCallDelta(BaseModel):
    type: Literal["tool_call_delta"] = "tool_call_delta"
    index: int
    id: str | None = None
    name: str | None = None
    arguments_delta: str = ""

class UsageEvent(BaseModel):
    type: Literal["usage"] = "usage"
    usage: Usage

class StopEvent(BaseModel):
    type: Literal["stop"] = "stop"
    stop_reason: StopReason

class ErrorEvent(BaseModel):
    type: Literal["error"] = "error"
    error: ProviderError

StreamEvent = TextDelta | ToolCallDelta | UsageEvent | StopEvent | ErrorEvent
```

**关键设计点**：工具调用是**增量**到达的（`arguments_delta` 是 JSON 片段字符串），
需要在外层累积。这个累积逻辑**放在批次 4 的 loop 里**，不在本批次。

### 2.5 `errors.py` —— 五类错误码

```python
class ErrorCode(StrEnum):
    RATE_LIMIT = "rate_limit"
    CONTEXT_OVERFLOW = "context_overflow"
    AUTH = "auth"
    TRANSIENT = "transient"
    INVALID_REQUEST = "invalid_request"

class ProviderError(Exception):
    code: ErrorCode
    message: str
    raw: dict[str, Any] = {}
    retriable: bool          # 由 code 推导，不是独立字段
```

**`context_overflow` 是重点**：它是压缩机制的两条触发路径之一
（另一条是本地 `estimate_tokens` 超阈值）。**必须在 P1 就被正确识别并向上抛**，
哪怕 P1 还没有压缩——因为识别逻辑属于 provider 层，不属于压缩层。

**`retriable` 由 `code` 推导**，不让人手填。理由：手填就会填错，
而"该重试的没重试"和"不该重试的狂重试"都是线上事故。

### 2.6 `fake.py` —— 确定性回放

```python
class FakeProvider(BaseProvider):
    """按 transcript 顺序吐事件。用于 agent loop 的离线测试。"""
```

**transcript 格式**：JSONL，每行一个"轮次"，含该轮要吐的全部事件。

**硬门槛**：**同一 transcript 回放两次，产出的事件序列逐字节一致。**
这条断言本身就是架构方案 7.2 节「确定性回放」那个设计的验证方式。

### 2.7 `openai_compat.py`

只做 OpenAI 兼容协议（a3 拍板），覆盖 DeepSeek / Kimi / GLM / 通义 / Ollama。

**必须处理的协议细节**（不做会踩）：
1. SSE 流的分块边界可能切开一个 JSON —— 需要缓冲累积
2. `[DONE]` 是结束标记，不是 JSON
3. `finish_reason` 与 `stop_reason` 要做映射
4. `usage` 默认不在流里返回，需显式请求（`stream_options.include_usage`）
5. `tool_calls[].index` 用于多工具并行时的归属

**单测策略**：用 `httpx.MockTransport`注入录制好的 SSE 字节流，
**不联网、不需要 API key**。

### 2.8 `tokens.py`

**保守估算**：`len(text) / 3` 之类，**明确标注是估算**。

**为什么不做精确 tokenizer**：不同 provider 的 tokenizer 不同，
自实现一个既不准又要维护。**真实用量以 provider 返回的 `usage` 为准。**

## 4. 三处需要注意的设计取舍

### 4.1 `estimate_tokens` 是预警不是账本

**判据**：任何"我们自己算的 token 数"都只能用于**预警**（接近上限时提醒），
**不能用于报告**。评测报告里的 token 数字必须来自 provider 的 `usage`。

理由：模型换了、provider 换了，我们的估算就不准了，
而报告里的数字是给人看的结论——**估算数进报告等于造假**。

### 4.2 LLM 层不做抽象（与批次 1.5 的 agent 层形成对照）

本批次四个消息模型**都是纯 `BaseModel`，没有基类**。

理由：它们严格对应 wire protocol，字段就是协议要的样子。
加基类只会让协议转换更难写，且没有行为需要统一分派。

**对照**：批次 1.5 的 `AgentMessage` 要 `ABC`，因为它**有行为**（`to_llm()`）、
需要被统一持有、需要运行时分派。**判据是"有没有行为"，不是"重不重要"。**

### 4.3 中途 system 消息的张力（本批次要留口子）

架构方案 4.0.4 节说明：`SystemMessage` 承担提示词演进，
但**中途插入 system 消息会破坏 prompt cache**（D4 节要求常驻区逐字节稳定）。

**本批次的处置**：类型上**保留** `sections` / `tools_added` / `tools_removed` 三个字段，
但 `OpenAICompatProvider` **P1 只在会话开始处发一条 system 消息**。
中途变更的能力**保留类型但不启用**，等 P2 做压缩时一并设计缓存策略。

**要写的转换逻辑**：OpenAI 兼容协议接受中途 system 消息则原位发；
不接受的 provider（未来加 Anthropic 时）需按重放状态重建首条 system 消息。
**这条逻辑 P1 就要写**，不能推——它是类型的一部分。

## 5. 硬门槛汇总（本批次验收）

| # | 门槛 | 为什么这条 |
| --- | --- | --- |
| G1 | `BaseProvider()` / `CancelToken()` 直接实例化抛 `TypeError` | a2 继承制的第一处落地验证 |
| G2 | 带三个 `*_signature` 的消息 JSONL 往返后逐字节不变 | 防一类极难排查的 bug |
| G3 | 五类 `StreamEvent` 逐类 round-trip 序列化 | 事件是 UI / 落盘 / 测试的公共契约 |
| G4 | `FakeProvider` 同 transcript 两次回放逐字节一致 | 确定性回放的前提 |
| G5 | 全部单测在无 API key 环境下通过 | 与 P0 门槛一致 |
| G6 | `context_overflow` 能被识别并抛出 | 压缩的两条触发路径之一，P2 要用 |
| G7 | 三道门禁（lint-imports / mypy / pytest）保持全绿 | 每批次固定门槛 |
| **G8** | **`sigma_ai` 的 import-linter 契约不破**：`sigma_ai` 不得 import `sigma_agent` | 消息层不混用；`sigma_ai` 是依赖图最底层，不允许它认识 `AgentMessage` |
| **G9** | **`SystemMessage` 的定义里没有任何"压缩摘要"语义的字段** | 摘要必须降级成 `user`（架构方案 4.0.6 / 第 8 节门禁「摘要降级位置」） |
| **G10** | **`BaseProvider.stream()` 的签名同时被两个性质不同的实现者满足**（`FakeProvider` 回放式 / `OpenAICompatProvider` 协议式），且签名含 `sampling` / `options` / `timeout_s` | **B1.3 的核心**：单一实现者永远暴露不出签名缺漏。见 7.1 |

### G8 / G9 是 2026-09-20 补记的

**G8**：批次 1 会新增 `messages.py`，它有很强的动机去 import `sigma_agent`
（比如想写 `def to_llm(self)` 就把 `AgentMessage` 引进来）。**必须从第一天就钉死。**
P0 已有这条契约（分层契约覆盖），但批次 1 详规原先没把它列为本批次门槛。

**G9 的来由 —— 一个真实的踩坑风险**：

批次 1 定义 `SystemMessage` 时有三个字段（`sections` / `tools_added` / `tools_removed`），
它们让 `SystemMessage` 看起来"可以承载任何想注入上下文的东西"。
实施时把**压缩摘要拼进 `SystemMessage.content`** 是非常自然的选择
——因为**没有任何东西阻止这么做**。

但架构方案 4.0.6 节明确规定：**摘要降级成 `user`，不是 `system`。**
理由是 system 消息占常驻区，而常驻区在会话内**必须逐字节稳定**（D4）。
把摘要写进 system 消息 = 常驻区中途变化 = **prompt cache 从变动点起全部失效**。

**症状不会在本批次暴露**，要等到 P2 做压缩时才会以"成本异常上升"的形式出现，
而那时已经很难定位到 `SystemMessage` 的定义上。

**所以 G9 的落地形式**：在 `messages.py` 的 `SystemMessage` 类 docstring 里
写一条显式警告（见 2.1 节补充），并加一个单测断言
`SystemMessage` 的字段集合**恰好**是约定的那些，新增字段时测试失败。

这条门禁**成本极低**（一个字段集合断言），防的是一个跨阶段的隐蔽错误。

### G10 是 B1.3 的直接产物

**这条门槛的形状本身就是一条方法论**：

> 一个抽象基类的签名，**不能只被一个实现者适配**。
> 单一实现者不会告诉你签名少了什么——尤其是当那个实现者是"我说吐什么就吐什么"的
> 回放器时。

**具体到本批次**：`FakeProvider` 是回放式实现，它对采样参数、请求选项、超时
全部无感。所以只要 `FakeProvider` 是唯一实现者，
`BaseProvider.stream()` 就会看起来「刚好够用」。

**G10 的落地形式**：单测里**同时**用两个子类去满足签名——
一个回放、一个走 mock transport 的真实协议路径。
若签名缺字段，两个子类的测试必有一个写不下去。

**这条门槛防的不是 bug，是"抽象层设计错误的延迟发现"。**
它对应 7.1 节记录的方案丙风险：等批次 4 才改签名，
批次 1–3 的全部单测与验收证据会一起返工作废。

### 7.1 B1.3 的决策过程与被否决的方案

**原始问题**：批次 1 是否真的需要 `OpenAICompatProvider`，
还是可以只写 `FakeProvider`、把真实协议层推到批次 4？

**曾考虑的三个方案**：

| 方案 | Provider 实现 | 单测 | 否决理由 |
| --- | --- | --- | --- |
| 甲 | httpx 直连 | `MockTransport` 注入 SSE | **初始推荐**，但被本人以「直接用 openai SDK 就行」质疑，见下 |
| 乙 | openai 官方 SDK | mock 掉 SDK 客户端 | **技术上与 B1.2 矛盾**：`httpx.MockTransport` 挂在 httpx client 上，而 SDK 自己内部创建 client，不暴露 transport 注入点。强行注入等于依赖 SDK 私有实现 |
| 丙 | 只写 `FakeProvider` | transcript 回放 | **被否决，理由见下**（循环论证） |

**关于「直接用 OpenAI SDK」的讨论结论**：

SDK 路线被否决，不是因为它「不好」，而是因为它与本项目的验证目标冲突：

1. **它不减少工作量，而是多一层翻译。** 用 SDK 仍需自己写
   `ChatCompletionChunk → StreamEvent` 的转换；SDK 只代劳 HTTP 与 SSE 分帧。
2. **它隐藏了本批次要验证的协议细节。** 批次 1 详规 2.7 节列的 5 条协议细节中，
   「SSE 分块边界可能切开一个 JSON」「`[DONE]` 不是 JSON」两条**恰恰是最容易出问题、
   且最难复现的**（缓冲区切分错误会导致随机丢字符），SDK 把它们藏了起来。
3. **它让两个 Provider 的抽象层级不对齐**：一个在 SDK 之上，一个在字节流之上。
   G4「同 transcript 两次回放逐字节一致」因此失去可比性。
4. **诊断能力**：OpenAI 兼容协议的「兼容」是有限度的（不同厂商在
   `finish_reason` 取值、`usage` 字段位置、`tool_calls` 分片方式上可能有出入）。
   用 SDK 则失去在这层排查的能力。

**方案丙被否决的理由（本批次最重要的一条判断）**：

> **只写 `FakeProvider` 会构成循环论证，并把「接口设计问题」推迟成「集成问题」。**

具体两点：

1. **G4 天然成立，因而不构成验证。** 「同 transcript 两次回放逐字节一致」
   验证的是 `FakeProvider` 自己的一致性——它读 JSONL、按顺序吐事件，
   两次当然一致。**这条断言是被写来通过它的。**
   这正是架构方案 7.3 节与 R1「评测自欺」要防的东西，
   如果落进门槛设计里，就是自欺。
2. **`BaseProvider` 的签名只经一个实现者适配，无法暴露缺漏。**
   `FakeProvider` 是「我说吐什么就吐什么」，**永远不会告诉你签名少了什么**。
   真实 provider 才暴露得出来的问题包括：
   - 采样参数（`temperature` / `max_tokens` / `top_p`）**不在签名里**
   - `response_format` / `stream_options`（`usage` 依赖它）**不在签名里**
   - `timeout` 与重试策略**不在签名里**
   - `signal: CancelToken` 是自造类型，真实场景用
     `asyncio.CancelledError` / httpx `Timeout`——**这个抽象对不对只有接了真协议才知道**

   **这些都是抽象层的核心接口，不是实现细节。** 等到批次 4 才发现签名要改，
   意味着 `FakeProvider`、全部回放 fixture、批次 1–3 的单测**一起返工**，
   批次 1–3 的验收证据**随之作废**。

**最终决定**：**两个都写。**

`OpenAICompatProvider` 在批次 1 的职责**不是**「完整支持真实调用」，
而是**「作为第二个实现者，把 `BaseProvider` 签名里的缺漏逼出来」**。

职责划分：

| 项 | 批次 1 | 批次 4 |
| --- | --- | --- |
| `OpenAICompatProvider` 类本身 | ✅ **必须写** | — |
| 用它验证 `BaseProvider.stream()` 签名是否够用 | ✅ **本批次的核心用途** | — |
| 采样参数 / `stream_options` 进签名 | ✅ 此时定下来 | — |
| SSE 分帧完整实现 | ✅ | — |
| 离线单测（`MockTransport`） | ✅ **主要目的是逼出签名问题** | — |
| 真实 API 联调 | ❌ | ✅ |
| 错误码映射全覆盖 | 部分 | ✅ 补全 |

**这就是「用真协议逼出签名问题」的具体含义。**
额外成本：约 80 行 SSE 解析 + 一个 MockTransport fixture。

**何时应该重新考虑（换回 SDK）**：
协议细节在批次 4 被真实 API 验证过一遍之后，
若开发速度成为瓶颈，可考虑改用官方 SDK——那时协议已在自有测试里固化成 fixture，
换 SDK 不会丢失验证能力。**这条写入 7.1，作为未来的复议触发条件。**

**另有一项提醒已由 B1.3 解决**：本批次会第一次真正用到 `httpx`
（已在 `pyproject.toml` 的 `dependencies` 里，不是新增依赖）。
