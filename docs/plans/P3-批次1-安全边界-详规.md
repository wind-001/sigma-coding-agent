## 0. 要解决的问题

CLI 每次启动都打印：「P1 的工具没有任何边界约束……bash 会以你的用户权限执行任意命令」。
这条提示存在的意义是"**不知道边界在哪，比边界不存在更危险**"——
现在轮到把"边界在哪"从提示词变成代码。

D5 的三层里，**可靠性排序是明确的**（architecture 6.1）：

| 层 | 机制 | 可靠性 | 本批 |
| --- | --- | --- | --- |
| L1 | 写路径 resolve 后必须在 workspace_root 下 | 高，可证明 | ✅ 做 |
| L2 | 影子 git checkpoint（每写批次前提交，可整体回滚） | 高，可证明 | ✅ 做 |
| L3 | 钩子规则（危险命令匹配） | **低，只能减少不能消除** | ⬜ P3-批次2（要 HookManager） |

L3 不是不做，是它需要 P3 的钩子总线（before/afterToolCall）——那是一个独立的架构件，
本批做它会同时引入"总线 + 规则"两个新东西，违反"一次一个逻辑单元"。

### 0.1 两条既有的"不要自作聪明"的约束（来自 `_paths.py` 与 `bash.py` 的 docstring）

1. **"顺手加一句 `is_relative_to` 检查"是名义防护**——挡不住符号链接，却制造虚假安全感。
   所以 L1 必须**连符号链接与真实路径一起处理**（resolve 后再比），否则宁可不做。
2. **bash 命令黑名单是名义防护**——`python -c`、base64、先写脚本再执行都能绕过。
   所以本批**不给 bash 加命令过滤**；bash 的兜底是 L2（可回滚）+ 超时（已有）。
   这两条的出处是本项目已固化的纪律：**名义门槛比没有门槛更坏。**

### 0.2 不做的事

- **不做容器隔离**（D6 已定）；**不宣称沙箱**——README 与文档继续写明边界。
- **不约束读路径**（architecture 6.3 明写"L1 只约束写"；读工作区外的文件是合法需求）。
- **不做 HookManager / before/afterToolCall / steering**（P3-批次2）。
- **不做审批弹窗**（`needs_approval` 标志已在 `BaseTool` 里，但审批通道属 P3-批次2；
  本批不假装有）。
- **不做"模型可触发的回滚"**——回滚是人的动作，不进工具面（模型自己回滚工作区是个
  更危险的能力，要做得想清楚，现在没有那个需求）。

## 1. 关键决策（Q1–Q8，推荐值已给，待拍板）

### Q1 本批范围：**L1 + L2**，L3 明确推后

理由见 §0 的表。L1+L2 是"高、可证明"的两层；L3 单独成立一个批次。

### Q2 L1 落点：**`_paths.py` 加一个新函数 `resolve_write_path`**，不是改 `resolve_path`

```python
def resolve_write_path(ctx: ToolContext, raw: str) -> Path:
    """写路径约束（L1）：解析符号链接后必须仍在 workspace_root 之内。"""
```

- `resolve_path()` 保持原样（读路径用，不约束——architecture 6.3）；
- `write` / `edit` / `bash` 的 `cwd` 参数改走新函数；
- **实现必须 resolve 两侧**：`Path.resolve(strict=False)` 处理符号链接，
  `os.path.normcase` 处理 Windows 大小写（`C:\Users` vs `c:\users` 文本比较会假阳性）。
  这正是 `_paths.py` docstring 警告过的"半成品"形态，本批是它的正解。
- 逃逸时的行为：**返回 `is_error=True` 的 ToolResult**（带"该路径在工作区之外"与
  解析后的两个路径），不抛异常——模型要能读到原因并换路径（详规 3.6 同族纪律）。

### Q3 L2 落点：**`core/sigma_agent/checkpoint.py`**（架构 262 已定）

> 为什么 checkpoint 放在 `sigma_agent` 而不是 `sigma_tools`：它需要感知"一个工具批次"的边界，
> 这个边界只有 loop 知道。放在工具层会退化成"每个工具自己备份"，重复且不可控。

但它**不自己决定 GIT_DIR 放哪**——与"谁决定策略，谁传参"同一条：
构造函数收 `root`（影子库目录）与 `workspace`，都由产品壳（sdk/cli）注入。

### Q4 影子库位置：`<sessions_dir>/<session_id>.shadow.git`

与 P2-5 的会话文件（`~/.sigma/sessions/<id>.jsonl`）同层扁平放置：

```
~/.sigma/sessions/
    20260922-091303-a1b2.jsonl          ← 会话记录（P2-5）
    20260922-091303-a1b2.shadow.git/    ← 影子库（本批）
```

- **不碰用户仓库自己的 `.git`**（D5 写死）：全部命令用 `--git-dir=<shadow> --work-tree=<workspace>`；
- 影子库随会话走：`--continue` 续上的会话天然续上 checkpoint 历史。

### Q5 提交时机：**写批次前 + 会话启动基线**

loop 的 `_execute_batch` 里，`writers` 非空时先 `checkpoint.mark(label=...)` 再执行。
另在会话**启动时提交一次基线**——否则"第一个写批次前的提交"就是"已经改过的状态"，回滚无意义。

```
启动 ──▶ mark("baseline") ──▶ 批次1(含写) ──▶ mark("batch:2") ──▶ 批次2(含写) ──▶ …
                                ▲                        ▲
                          回滚到这个点 = 撤掉批次1          回滚到这个点 = 撤掉批次2
```

### Q6 exclude 与大文件：**全走 git 原生机制，不自写匹配器**

1. shadow 库的 `info/exclude` = **内置默认清单**（`.git/`、`.venv/`、`node_modules/`、
   `__pycache__/`、`.pytest_cache/`、`dist/`、`build/`、`target/`、`.idea/`、`.vscode/` 等）
   **+ 工作区自己的 `.gitignore` 内容**（原样追加）；自写 .gitignore 匹配器是兔子洞，不做；
2. 大文件上限 5 MB：`git status --porcelain -z --untracked-files=all`（已认 exclude）拿到候选列表，
   超上限的**追加进 info/exclude** 再 `git add -A`——**不 hash 就不慢**；
3. 回滚清理只删"`ls-files --others --exclude-standard` 列出的文件"——
   被排除的大文件**不会被回滚删掉**（这条不写清楚，L2 就会变成数据销毁器）。

### Q7 回滚入口：**CLI，独立动作，不启动模型**

```
sigma --session <id> --rollback              # 回到最近一次写批次前
sigma --session <id> --rollback-to <ref>     # 回到指定提交
```

- 与 `-p` / `-i` 互斥（回滚就是回滚，不跑任务）；
- 回滚 = `checkout <ref> -- .` **+ 删除 ref 之后新增的文件**（`checkout` 不会删新增文件——
  architecture 6.2 明写这是最容易漏的一条，本批有专门门槛）；
- 执行前打印"将撤销到 X（N 个批次）"，执行后打印"已恢复，工作区与 X 一致"，
  并**先做一次 checkpoint**（回滚本身也可回滚——把"回滚错了"也做成可恢复的）。

### Q8 开关：**默认开，`--no-checkpoint` 可关**

安全默认要开；可关的理由有两个：ablation 的自变量（"checkpoint 值不值"是评测要回答的问题）、
性能排查。关掉时 CLI 横幅明说"无回滚保障"——**不许静默变弱**。

## 3. 接口定义

```python
# core/sigma_tools/_paths.py
class PathEscapesWorkspace(ValueError):
    """路径解析后落在 workspace_root 之外。继承 ValueError：调用方传错了值。"""


def resolve_write_path(ctx: ToolContext, raw: str) -> Path:
    """写路径约束（L1）。

    resolve(strict=False) 解析符号链接与 ..，os.path.normcase 处理 Windows 大小写；
    越界时**抛 PathEscapesWorkspace**（由工具转成 is_error 结果，不穿透）。
    读路径请继续用 resolve_path()——L1 只约束写（architecture 6.3）。
    """
```

```python
# core/sigma_agent/checkpoint.py
class ShadowCheckpoint:
    """影子 git checkpoint：独立 GIT_DIR，绝不碰用户仓库自己的 .git。"""

    def __init__(self, *, root: Path, workspace: Path,
                 max_file_bytes: int = 5 * 1024 * 1024,
                 git_bin: str = "git") -> None: ...

    @property
    def available(self) -> bool:
        """git 不可用 / 初始化失败 → False。此时 mark/restore 返回空结果，
        **不抛异常**——checkpoint 是保险丝，保险丝烧断不该让电器停止工作。"""

    def mark(self, *, label: str) -> str | None:
        """提交一次快照，返回 commit ref；不可用时返回 None。"""

    def refs(self) -> list[str]:
        """已有快照（新→旧），用于 --rollback-to 的可选值与横幅计数。"""

    def restore(self, ref: str) -> RestoreReport:
        """回到 ref：checkout + 删除 ref 之后新增的文件（只删未排除的，见 Q6）。

        返回的 RestoreReport 含：改了哪些文件、删了哪些、跳过了哪些（被排除的）。
        **回滚前自动 mark 一次"pre-restore"**——回滚本身也是可回滚的。
        """
```

`AgentLoop.__init__` 增加 `checkpoint: ShadowCheckpoint | None = None`（默认 None = 无 checkpoint，
回放与旧测试路径不受影响——**不加它时行为与加它之前逐字节一致**，同批次 6 observer 的纪律）。

## 4. 门槛（G64–G70）与注入实验

`scripts/gate_injection_batch13.py`，沿用"破坏 → 红 → 还原 → 绿"形态。

| 门槛 | 断言 | 注入方式 |
| --- | --- | --- |
| **G64** L1 拦截 | write/edit 到 workspace 外 → `is_error` + 目标文件不存在 | 去掉 containment 检查 → 文件真被写到外面 |
| **G64b** 符号链接逃逸 | workspace 内 symlink 指向外部 → 写入被拦 | 用未 resolve 的路径比较 → 拦不住，测试红 |
| **G65** 启动基线 | 会话启动后影子库必有 `baseline` 提交 | 去掉启动 mark → refs 为空 |
| **G66** 写批次前提交 | 含写工具的批次执行前必有 mark（refs 数 = 基线 + 写批次数） | 去掉 `_execute_batch` 里的 mark → refs 数少一 |
| **G67** 回滚恢复修改 | 修改后 restore → 内容回到 ref | restore 不 checkout → 红 |
| **G68** 回滚删除新增文件（**最易漏**） | 新建文件在 restore 后消失；**被排除的大文件不被删** | restore 只 checkout 不清理 → 新增文件残留 → 红 |
| **G69** 不碰用户 .git | 用户仓库 `git log` 里不出现 checkpoint 提交 | 注入改用 workspace 自身 GIT_DIR → 用户 log 多出提交 → 红 |
| **G70** checkpoint 失败不阻断任务 | git 不可用时写批次照常执行，警告可见 | 注入让失败 raise → loop 中断 → 红 |
| **G71** 回滚前核对工作区配对 | 影子库属于 A、却拿 B 回滚 → **拒绝且一个字节不动**；无标记也拒绝 | 去掉 `workspace_mismatch()` 检查 → B 的文件被删 → 红 |

回放新增场景 `destructive_then_rollback`：write 一个文件 → bash 删掉一个已有文件 →
restore → 断言两者都恢复（真实 git、真实文件系统、FakeProvider 驱动）。

## 5. 测试计划

全部离线、免 key；**需要真实 git**（`shutil.which("git") is None` 时 skip，并写清楚——
这与"无 key 全绿"不矛盾：git 是开发依赖，不是网络）。

1. L1：相对路径 `../x.txt` 逃逸被拦；`subdir/../../etc` 归一化后被拦；正常写入照常；
2. L1：符号链接逃逸被拦（Windows 建 symlink 需要权限——**mklink 需要管理员或开发者模式，
   测试里用目录联接 junction 兜底**，`skipif` 兜底）；
3. checkpoint：baseline + 两次写批次 → refs 顺序正确、label 可读；
4. restore：修改被恢复；**新增文件被删**；**大文件（>5MB）不入库且 restore 不删它**；
   用户 `.git` 的 log/status 全程无变化；
5. 性能：demo workspace（`scripts/make_demo_workspace.py` 产物）上 mark 一次 < 1 s
   （超了就说明 exclude 没生效，直接红）；
6. loop：含写批次 → mark 被调用恰好一次；纯读批次 → 零次（写工具并发纪律不变）；
7. 回放：`destructive_then_rollback` 场景 PASS，进 `evals/reports/`。

**五处实现判断（如实记录）**

1. **端到端证据用集成测试，而不是回放场景**（对 §4 的一处偏离）：
   详规原写"新增 `destructive_then_rollback` 回放场景"，但回放运行器的形状是
   "喂一轮、量一轮"，而**回滚是人的动作**——它不是模型跑出来的一步。
   塞进运行器要同时改"测量仪 + 场景格式"，收益只是报告多一行。
   改在 `tests/test_agent_checkpoint.py::test_loop_write_then_rollback_restores_workspace`
   里用**真 loop + 真 WriteTool + 真 git** 覆盖同一条路径：loop 打快照 → 写坏文件 → 回滚 → 复原。
2. **`git init` 不能带 `--work-tree`**（实测报 "GIT_WORK_TREE not allowed without specifying GIT_DIR"）：
   先建空库，之后所有命令再显式带 `--git-dir/--work-tree`。
3. **回滚的差异统计必须相对 pre-restore 快照算**：第一版拿旧 HEAD 去 diff，
   结果"文件删了、报告说没删"——回滚照常发生而**报告是假的**。
   单测当场抓住，已修（注释钉住原因）。
4. **回滚必须排在 API key 检查之前**：它是人的动作、不启动模型。
   第一版排在后面 → 没配 key 时 `--rollback` / `--list-checkpoints` 只会打印帮助。
   冒烟时当场发现。同理，非控制台（CI/管道）也要放行这三件事。
5. **影子库必须记下"它服务哪个工作区"**（G71，见下）。

**⚠️ 一次真事故（真模型冒烟抓出来的，值得完整记下来）**

冒烟流程：`sigma -p "把 note.txt 改成 BAD 并新建 junk.txt"` → 成功；随后
`sigma --sessions-dir ... --session smoke --rollback`（**忘了传 `--workspace`**）。

后果：影子库是给 `.pytest_cache/tmp/smoke_ws` 建的，而回滚默认用当前目录（= 仓库根），
于是 `reset --hard` 拿冒烟工作区的快照去改仓库 → **删掉仓库 171 个文件**
（含 12 个我未提交的改动文件）。

**为什么能救回来**：`restore()` 在动手前**自动打了一次 pre-restore 快照**（第 3 条里的"回滚也可回滚"），
它完整包含仓库当时的全部内容 → `git --git-dir=<shadow> --work-tree=. reset --hard <pre-restore>` 把仓库还原。
剩下一批只有行尾差异的 ` M`，用"非本次改动的文件逐个 `git checkout --`"清掉。
**没有这次自动快照，未提交的工作就永久丢了。**

**根因与修法**：影子库没有记录它服务的工作区，而"配对"只存在于调用方（CLI 参数）的记忆里。
两份状态各自"知道"配对是不够的——**必须有一处把配对写下来**：

- 建库时写 `<shadow>/sigma-workspace.txt`（`_workspace_marker`，存**resolve 后**的路径）；
- `restore()` 里加**最后一道闸**：`workspace_mismatch()` 非空就拒绝，一个字节都不动；
- CLI 用**记录下来的**工作区执行回滚，用户给的 `--workspace` 只参与核对；
- 旧影子库没有标记 → **宁可拒绝，不要猜**（猜错就是删文件）；
- 门槛 **G71** + 注入 E62（去掉闸门 → 用例必须变红）+ 3 个新用例
  （记录工作区 / 不匹配时拒绝且不动对方文件 / 无标记时拒绝）。

事故现场那个影子库现在会被拒（实测："没有记录它服务的工作区"），
干净路径也重测通过（`已回滚到 <ref>：恢复 1 个文件、删除 1 个新增文件`）。

**一条通用的教训**：*破坏性动作的输入，必须由被保护对象自己记录下来*。
"调用方会传对"不是边界——它只是一个约定，而约定会漏。

**一处工具链缺陷（顺手发现，值得记）**

注入实验的**残留守卫对"新增未跟踪文件"无效**：它提示用 `git checkout -- <file>` 还原，
而本次新增的 `checkpoint.py` 还没进版本库，`git checkout --` 会直接报错。
本次是本会话自己踩到的（超时被杀的 batch13 在 `checkpoint.py` 留下 `reset --mixed` 注入），
靠"扫 `# 注入：` 标记 + 手工还原"才修好。**建议**：守卫的还原建议里补一句
"未跟踪文件请手工还原，或先 `git add` 再跑注入"。
