# P1-批次7 详规：web_search 联网搜索工具

> 状态：**已实现（2026-09-21）**——评审提问在对话中超时未获答复，按第 10 节的推荐值推进；三项都是小改，随时可回退。
> 关联：architecture 2.1 / 5.1 / 7.6、decisions D4（常驻区预算）D5（安全边界）、`docs/plans/P1-批次6-流式CLI与启动入口.md`
> 一句话：给 agent 加**第 6 个内置工具（可选位）**，走 Tavily，硬约束在 1,000 credits/月的免费额度内，超额即拒绝并禁用。

## 0. 要解决的问题

agent 现在完全离线：`read / write / edit / bash / grep` 五个工具都只作用于本地工作区。
遇到"这个库的 API 上个月改了"、"这个报错是什么原因"这类问题，模型只能靠训练记忆猜。

**不做的事**（写清楚，避免范围蔓延）：

- 不做网页抓取（那是 Tavily Extract，另一个端点、另一套计费）；
- 不做多轮 research / crawl / map（同上）；
- 不做结果缓存（P1 无落盘能力，且缓存会让"配额记录"与"实际请求"不再一一对应）；
- 不做 provider 抽象（只有 Tavily 一家，**不做没有需求的设计**——这是删 `BaseLoop` 时定下的原则）。

## 1. 关键决策（需拍板）

### Q1 落点：内置工具的**可选位**，不是核心五工具，也不是等 P4 的扩展

architecture 5.1 节的预算表里本来就有一行 **「工具 schema（+3 可选）| +~450 | 启动时按 flag」**——
`web_search` 正好落进这一栏，因此**不必动"核心 5 工具"的结论**。

| 方案 | 判断 |
| --- | --- |
| **内置可选位（推荐）** | 有 `TAVILY_API_KEY` 才注册，`--no-web-search` 可关。现在就能用、能测、能进评测 |
| 核心第 6 工具（无条件注册） | 无 key 的机器上白付 ~150 token 常驻成本，且会在每次评测里占预算 |
| 等 P4 扩展系统 | 扩展加载器还不存在，这个能力要等一个学期；且它本来就是个好用的"第一个扩展样例" |

### Q2 配额策略：本地月计数为快路径，`GET /usage` 为权威校准

Tavily 免费档的真实口径是 **1,000 credits/月**（Researcher 档），**不是 1,000 次**：

| search_depth | 每次消耗 | 含义 |
| --- | --- | --- |
| `basic` / `fast` / `ultra-fast` | 1 credit | 默认档 |
| `advanced` | 2 credits | 高精度档 |

所以"1,000 次/月"只在默认 basic 档成立；用 advanced 就是 500 次。
**按 credits 记账，不按调用次数记账**——这条写进工具 description，让模型也知道贵。

服务端 `GET /usage` 免费且返回本计费周期该 key 的 `usage` / `limit`（含 `search_usage` 分项）。
两者分工：

- **本地计数**（`~/.sigma/tavily_usage.json`）：每次调用前判定的快路径，零额外请求；
- **服务端校准**：当快照过期（TTL 300s）、本地已用 ≥ 90%、或服务端报超限时强制刷新；
- **校准失败**（断网 / 端点变动）：回退本地计数并记 warning，**不阻断搜索**——
  我们是这个 key 的唯一使用者，本地计数对自己是准确的，`/usage` 只是交叉校验。

### Q3 超额行为：拒绝 + 本进程禁用 + 给模型行动指引

`used + cost > limit` 时：

1. **不发网络请求**（省的是配额，也是延迟）；
2. 返回 `is_error=True` 的 `ToolResult`，文案**给行动指引**：
   "联网搜索额度已用尽（本月 1000/1000 credits），不要重试，请改用本地信息或其它工具"；
3. 本进程内标记禁用，后续调用直接拒绝。

**为什么不从注册表里摘掉工具**：注册表变动 = 常驻区变动 = 会话内 prompt cache 全失效，
而 D4 明令常驻区逐字节稳定。工具在、能力关，是唯一不破坏 D4 的做法。
同理，**不自动放宽额度**：超额就是超额，宁可这条任务做不成，也不越界花钱。

### Q4 工具名：`web_search`

项目内工具名一律 snake_case（`read / write / edit / bash / grep`）。
用户口语里的 "web-search" 是 CLI 风格的连字符，进注册表就用下划线。

## 3. 接口定义

```python
class WebSearchParams(BaseModel):
    """web_search 的参数。"""
    query: str = Field(min_length=1, max_length=400, description="搜索词。具体优于宽泛。")
    max_results: int = Field(default=5, ge=1, le=10, description="返回条数，默认 5。")
    search_depth: Literal["basic", "fast", "ultra-fast", "advanced"] = Field(
        default="basic",
        description="检索深度。basic/fast/ultra-fast 每次 1 credit，advanced 每次 2 credits。",
    )
    topic: Literal["general", "news", "finance"] = Field(default="general", description="检索主题。")
    include_answer: bool = Field(default=False, description="是否附带 Tavily 生成的一段直接答案。")


class WebSearchTool(BaseTool):
    """联网搜索。只读工具，允许与其它只读工具并发。"""

    name = "web_search"
    description = (
        "联网搜索（Tavily）。用于查最新文档、报错原因、库的变更等本地工作区里没有的信息。"
        "返回 标题 + URL + 摘要片段。额度按 credits 计：basic/fast/ultra-fast 每次 1 credit，"
        "advanced 每次 2 credits；免费额度 1000 credits/月，用尽后本工具会被禁用。"
    )
    read_only = True

    def __init__(self, *, api_key: str, quota: TavilyQuota, transport: httpx.AsyncBaseTransport | None = None,
                 timeout_s: float = 20.0) -> None: ...

    @property
    def params(self) -> type[BaseModel]: return WebSearchParams

    async def run(self, args: BaseModel, ctx: ToolContext) -> ToolResult: ...
```

`run` 的三条硬约束（都来自既有纪律）：

1. **不抛异常**：401 / 429 / 超时 / JSON 解析失败一律转成 `is_error=True`（架构 4.3 第 3 点）；
2. **结果两段式**：`content` 给模型（标题 + URL + 摘要，经 `truncate_output` 截断），
   `details` 给审计与评测（`credits_used` / `credits_total` / `remaining` / 结果 URL 列表 / `truncated`）；
3. **不缓存** `ToolDefinition`，也不缓存实例——热重载契约（架构 4.4）。

## 4. 配额状态机

```text
状态文件：~/.sigma/tavily_usage.json
{ "cycle_used": 137, "cycle_limit": 1000, "synced_at": 1758..., "disabled": false, "last_error": null }
```

```text
调用前：
  1) 取锁 → 读状态（内存缓存，进程内只读一次磁盘）
  2) 过期（>300s）或 used ≥ 90% → GET /usage 校准（失败则沿用本地并记 warning）
  3) used + cost > limit ? → 标记 disabled，返回拒绝（**不发搜索请求**）
  4) 放行，发 POST /search（timeout 20s）
调用后：
  5) 成功 → used += cost，落盘（tmp 文件 + os.replace 原子替换）
  6) 服务端报超限 → disabled = true，落盘
  7) 401/403 → 不 disabled，但返回鉴权错误（换 key 即可恢复）
```

**并发**：`asyncio.Lock` 包住步骤 1–5。只读工具是并发执行的（loop 里 `asyncio.gather`），
两个 `web_search` 同时进来会读改写同一份计数——没有锁就是**丢计数**，
而症状是"额度明明没用完却超了"，不指向根因。这条要有专门用例（G39）。

## 6. 门槛（G37–G41）与注入实验

| 门槛 | 断言 | 注入方式（证明它会失败） |
| --- | --- | --- |
| **G37 配额硬闸** | 额度用尽时**零 /search 请求**（/usage 校准是免费端点，不在禁令内），返回 `is_error=True` 且文案含行动指引 | 判定改成恒真（不拦）→ 已用尽仍会发出 /search |
| **G38 记账口径** | `advanced` 记 2、其余记 1；**失败不记账** | 把 cost 恒定为 1 → 断言 `cycle_used == 2` 失败 |
| **G39 并发原子性** | `asyncio.gather` 两个调用后 `cycle_used` 恰好 +2，且 **/usage 只校准一次** | 去掉 `asyncio.Lock` → 两个调用在同一份过期快照上各校准一次 |

> **G39 的口径修正（写代码时才发现，如实记录）**：原先写的"去掉 Lock → 断言失败（读改写竞争）"
> **不可证伪**——reserve 的"判定 + 预留"在没有校准需求时是同步的（中间没有 await），
> 事件循环不会被切走，所以无锁也不会丢计数。锁真正起作用的地方是
> **"校准（含 await）+ 判定 + 预留"这一整段的原子性**，可观测的证据是**校准次数**：
> 无锁时两个并发调用会在同一份过期快照上各校准一次。
> 断言因此改成"恰好 +2 **且** /usage 只调用一次"。
> 本项目明令：**名义门槛比没有门槛更坏**——不能证伪的断言不该留在门槛表里。
| **G40 无 key 不注册** | 无 `TAVILY_API_KEY` 时 `default_registry()` 不含 `web_search`，且既有 G26 常驻区断言仍绿 | 改成"注册了再报错" → 断言注册表名字列表失败 |
| **G41 错误不穿透** | 401 / 429 / 超时 / 非 JSON 响应四类都返回 `is_error=True`，**不抛异常** | 去掉 `try/except` → 用例从"返回结果"变成"抛异常" |

`scripts/gate_injection_batch7.py` 按既有格式逐个"破坏 → 跑门槛 → 断言失败 → 恢复 → 断言通过"，输出 PASS/FAIL 清单。

## 7. 测试计划（全部离线）

`httpx.MockTransport` 注入假响应，**不需要 key、不联网**（沿用 offline-first 纪律）：

1. 正常搜索 → `content` 含标题与 URL；`details.credits_used == 1`；
2. `advanced` → `credits_used == 2`，额度按 2 扣；
3. 额度耗尽 → handler 调用次数为 0（**这是 G37 的核心断言**）；
4. `/usage` 校准：服务端 `usage=999/limit=1000`，本地 2 → 校准后 used=999，下一次 advanced 被拒；
5. 状态文件损坏（非法 JSON）→ 重置为 0 并记 warning，**不崩**；
6. 401 / 429 / 超时 / HTML 响应体 → `is_error=True` 且消息可读；
7. 并发两个调用 → `cycle_used` 恰好 +2；
8. 结果超长（单条 200 KB）→ 经 `truncate_output` 截断，`details.truncated == True`。

外加一条**不联网的真实验证**（手动、不进 CI）：`scripts/real_api_web_search.py`，消耗 1 credit，
用来确认协议与 `/usage` 的真实形状没有变。

  冒烟中发现一处环境事实：账本默认落点 `~/.sigma/tavily_usage.json` 在本机沙箱下
  **写不进去**（`_persist` 吞掉 OSError 并记 `last_error`）——因此 CLI 横幅现在会把
  `last_error` 打出来。静默失败的后果是"额度每次都从 0 开始数"，
  而用户只会觉得额度怎么都用不完。

**一处实现缺陷（如实记录）**：`run()` 里的取消判定最初写成 `ctx.signal.is_cancelled`（属性式），
而 `CancelToken.is_cancelled` 是**方法**——属性式写法恒为真，工具会对任何调用都回"已取消"。
单测当场抓到（除取消用例外的用例全红），已改为 `is_cancelled()`。
