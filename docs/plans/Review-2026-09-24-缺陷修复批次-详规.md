## 组 A：协议层健壮性

### A1（#7）SSE data 是非对象 JSON 时裸抛 AttributeError

- 位置：`core/sigma_ai/openai/provider.py:349`
- 机理：`parse_sse_line` 只保证"合法 JSON"，不保证 dict。`data: 123` 这类行会在
  `chunk.get("usage")` 抛 `AttributeError`，不被任何 except 捕获，裸抛出异步生成器——
  违背本层"流式错误即事件、不裸抛打断流"的既定约定（provider.py 注释明写）。
- 修法：`parse_sse_line` 返回后校验 `isinstance(chunk, dict)`；不是则发
  `ErrorEvent(code=INVALID_REQUEST, message=f"SSE 行不是 JSON 对象：{line[:200]}")`
  并 `continue`（与既有"坏行不静默跳过、但也不中断流"的处置同形）。
- 同点顺手修：`:364` 的 `int(call.get("index", 0))` 改为 `int(call.get("index") or 0)`——
  显式 `"index": null` 时 `.get` 的默认值不生效，`int(None)` 抛 TypeError。
- 回归测试：`test_sigma_ai_openai_compat.py` 加两条——非对象 data 行产生一条
  ErrorEvent 且流继续；`index: null` 的分片按 index=0 装配。

### A2（#14）`_parse_usage` 对显式 null 抛 TypeError

- 位置：`core/sigma_ai/openai/protocol.py:68-69`
- 机理：`int(raw.get("prompt_tokens", 0))` 在键存在但值为 `null` 时崩。
  同函数的 `cached_tokens` 已用 `or 0` 防御——防御不一致就是疏漏。
- 修法：`int(raw.get("prompt_tokens") or 0)`（completion 同理）。
- 回归测试：usage 字段值为 null 的 chunk → Usage 三字段为 0，不抛。

### A3（#8）流中途干净断连被静默当作正常结束

- 位置：`core/sigma_ai/openai/provider.py:316-317, 385`
- 机理：读循环只在 `StopAsyncIteration` 时 break，之后无条件
  `yield StopEvent(stop_reason="stop")`。连接在收到 `finish_reason`/`[DONE]` 之前
  被对端**干净**关闭时不抛任何异常，被截断的响应被报告为正常完成——
  半截 tool_call 参数在上层拼出非法 JSON，症状完全不指向根因（断流）。
- 修法：循环内跟踪 `saw_finish = False`（收到任一 `finish_reason` 或 `[DONE]` 置真）；
  break 后若 `not saw_finish` → 发 `ErrorEvent(code=TRANSIENT,
  message="流在未收到 finish_reason/[DONE] 前结束——响应被截断")` 并 return，
  不再发 StopEvent。**需要确认 `parse_sse_line` 对 `[DONE]` 的现有处理点，把标记接上。**
- 回归测试：Mock transport 流只发半个 tool_call 分片就 EOF → 恰好一条
  TRANSIENT ErrorEvent，无 StopEvent。

## 组 G：工具边界

### G1（#10）write 在 Windows 上把 `\n` 静默转成 `\r\n`

- 位置：`core/sigma_tools/write.py:87`
- 机理：`path.write_text(..., encoding="utf-8")` 未传 `newline`，Windows 文本模式
  默认把 `\n` 落成 `\r\n`——模型写的是 LF（与 read/edit 看到的一致），落盘变 CRLF。
  edit.py 特意用 `write_bytes` 保真行尾，write 漏了。同时 L84 的 `new_bytes`
  统计与实际落盘字节数不符。
- 修法：改 `path.write_bytes(params.content.encode("utf-8"))`（与 edit.py 同形）。
- 回归测试：写入含 `\n` 的内容后读回原始字节，断言无 `\r\n`（Windows 上现为红）。

### G2（#6）truncate 不做二次预算校验 + 头尾重叠

- 位置：`core/sigma_tools/truncate.py:69-90`
- 机理两条：
  1. 只在入口判断 `total_bytes <= max_bytes`；截断分支拼出头 40 行 + 尾 40 行后
     **不再检查 body 大小**。docstring 自己举的例子（3 行 × 3 MB base64）总行数 ≤ 40，
     head 就是全部行，约 10 MB 照样进上下文——截断对最需要拦截的场景完全失效。
  2. `tail = lines[-tail_lines:] if total_lines > head_lines else []` 只挡了
     `total_lines <= head_lines`。`total_lines=50`（head=tail=40）时第 10–39 行
     在输出里**出现两次**，`kept_lines=80 > total_lines=50` 自相矛盾。
- 修法：
  1. 超过阈值的单行先按字符截断（单行上限 = `max_bytes // 4`，标记 `[单行已截断]`）；
     拼完 body 后按 UTF-8 字节做安全硬切（`encode[:budget].decode(errors="ignore")`
     之前先给 marker 留位）。
  2. `tail = lines[max(head_lines, total_lines - tail_lines):] if total_lines > head_lines else []`。
- 回归测试：① 3 行 × 3 MB 输入 → 输出 ≤ max_bytes + marker 余量；② 50 行输入 →
  输出无重复行、kept_lines ≤ 50。

### G3（#15）read 行范围越界静默返回空文本

- 位置：`core/sigma_tools/read.py:95-101`
- 机理：切片对非法范围天然返回 `[]`，无任何校验——模型无法区分"文件是空的"和
  "我给的行范围越界了"，可能基于"文件为空"的错误前提直接 write 覆盖。
- 修法：校验 `start_line <= end_line` 且 `start_line <= total_lines`，越界返回
  `is_error=True` 并报告总行数（给出路，同 L1 文案纪律）。
- 回归测试：越界两种形态各一条，断言 is_error 与文案含总行数。

### G4（#16）混合行尾文件被 edit 全量改写行尾

- 位置：`core/sigma_tools/edit.py:50-54, 167`
- 机理：`_detect_newline` 只要文件里存在一处 `\r\n` 就判整文件 CRLF，写回时
  `new_content.replace("\n", "\r\n")` 把原本 LF 的行也转成 CRLF——一次只改一行的
  edit 产生全文件行尾 diff，正是该模块 docstring 声明要避免的"隐性 diff"。
- 修法：检测到混合行尾（`\r\n` 与裸 `\n` 共存）时**拒绝编辑**并提示
  （"有歧义时宁可报错，不要猜"，与多匹配拒绝同一条原则），文案给出路
  （"先用 bash 统一行尾，或用 write 整体重写"）。
- 回归测试：混合行尾夹具 → is_error=True，文件内容逐字节不变。

## 组 E：checkpoint 回滚自保

### E1（#4）restore 前自保快照失败仍继续 reset --hard

- 位置：`core/sigma_agent/checkpoint.py:409-416`
- 机理：`pre = self.mark(...)` 失败（返回 None）时静默退回旧 HEAD 继续 reset。
  `reset --hard` **不删未跟踪文件**——没被 pre-restore 快照收进去的新文件在回滚后
  残留，回滚实际不完整，而 `RestoreReport.ok=True`。保险丝语义（失败不阻断）在
  "回滚"场景把 L2 从"可回滚"变成"看似回滚了"。
- 修法：`pre is None` → 返回 `RestoreReport(ok=False, ref=ref,
  note=f"回滚前快照失败，拒绝回滚：{self.last_error}")`。**回滚的优先级高于"不阻断"。**
- ⚠️ 行为变更，需拍板：原来"快照坏了也照样回滚"，改为"快照坏了拒绝回滚"。
  拒绝时工作区保持原样，用户可 `--no-checkpoint` 重跑或手工处理。
- 回归测试：注入 mark 失败（如把 shadow git 目录做成只读/删掉）→ restore 返回
  ok=False 且工作区逐字节不变。

## 组 D：二次压缩下标错位（本批最严重的静默缺陷）

### D1（#1）第二次压缩时 keep_from 算错，已压掉的消息全部"复活"

- 位置：`core/sigma_session/context.py:381-387`
- 机理：`compact()` 里 `messages = self.effective_history()` 是**视图**：
  `[摘要, *full[skip_old:]]`，其中摘要是**不在树上的虚拟消息**，所以
  `len(messages) ≠ len(path)`。而 `skip = len(messages) - len(kept)` 是视图下标，
  却被直接拿去索引**原始路径** `path[skip]`。视图下标 i（i≥1）对应的原始下标是
  `skip_old + i - 1`（`skip_old = len(path_to(旧 keep_from)) - 1`）。
  仅当上次恰好只压了 1 条消息（`skip_old == 1`）时才碰巧正确。
  **后果**：长会话第二次压缩时 `keep_from` 指向靠前得多的节点，第一次压掉的消息
  被重新塞回上下文——压缩白做、历史暴涨、两份摘要范围重复，完全静默。
- 修法：
  ```python
  skip_old = (
      len(self._tree.path_to(self._keep_from)) - 1
      if self._keep_from is not None
      else 0
  )
  offset = 1 if self._keep_from is not None else 0  # 摘要在视图里占一个位置
  raw_index = skip_old + skip - offset
  keep_from = path[raw_index] if raw_index < len(path) else head
  ```
  （落地时以"第一条被保留消息的节点 id"为准写，并处理旧 keep_from 已不在树上的
  降级路径——与 effective_history 的 TreeCorrupted 兜底同形。）
- 回归测试：构造 20 条消息的会话 → 压缩一次（keep 最近 N 轮）→ 再追加消息 →
  第二次压缩 → 断言 `effective_history()` 不含第一次已压掉的任何消息、
  且视图长度 ≤ 摘要 + 保留窗口。

## 组 C：挂起兜底

### C1（#11）信箱等待无超时，子任务挂死则 run_turn 永不返回

- 位置：`core/sigma_agent/loop.py:369` + `core/sigma_tools/task.py:271-277`
- 机理：`wait_and_drain` 里 `await asyncio.gather(*running_tasks)` 无任何超时；
  轮数预算管不到两轮之间。一个死锁/失联的子 agent 让主 loop 永久停在收尾处——
  与 09-24 刚修的"任务级超时兜底"是孪生缺陷（那刀切在 provider 流上，
  这刀要切在信箱等待上）。
- 修法：`wait_and_drain` 增加 `timeout_s` 参数（默认 **300 s**，与流式总时长闸
  同量级、有实测凭据），`asyncio.wait_for(gather(...), timeout_s)`；超时后把
  未完成子任务标记 `failed`（error="等待超时"）并照常 drain——**超时要变成
  看得见的失败回报，不是静默丢弃**（丢弃必须可见）。
- 回归测试：假工厂造一个永不完成的子任务，timeout_s=0.1 → wait_and_drain
  在 1 s 内返回，且 drain 出一条 failed 回报消息。

### C2（#5）grep 在事件循环线程同步跑模型给定的正则（ReDoS）

- 位置：`core/sigma_tools/grep.py:77, 131-132`
- 机理：`re.compile(params.pattern)` 后在 `run` 协程里同步逐行匹配。
  `(a+)+$` 类灾难性回溯在长行上指数耗时，不过 `to_thread`、无超时——
  bash 有超时兜底，grep 没有。一次调用冻死整个事件循环，只能杀进程。
- 修法：逐文件匹配放进 `asyncio.to_thread`，外层 `asyncio.wait_for`
  （每文件 **10 s**，构造参数可注入）；超时则跳过该文件、计入
  `files_skipped_timeout` 并在结果文案中可见。
- 备选（不取）：换 `regex` 库（带 timeout 参数）——引入新依赖，AGENTS.md 要求
  只用已确认的库，故用 asyncio 方案。
- 回归测试：`(a+)+$` 对 10 万字符长行，timeout_s=0.1 → run 在 2 s 内返回，
  结果含超时跳过计数。

## 组 B：错误状态透传（评测假通过的数据源）

### B1（#2 + #18）LLM 流以错误收场，turn 仍报 status="completed"

- 位置：`core/sigma_agent/loop.py:247-255, 405, 429-430`
- 机理：`ErrorEvent` 只被收进 `assistant.error_message`，控制流完全不受影响；
  错误流没产出工具调用时走 `not calls` 分支返回 "completed"。
  `TurnResult.status` 的 `Literal` 里有 `"error"` 但**全函数没有路径返回它**。
  另外 `stop_reason` 默认 `"stop"`，流被异常截断（没收到 StopEvent）也伪装成正常。
- 修法（两条规则，都要）：
  1. `_stream_model` 记录是否收到 ErrorEvent / StopEvent，向 run_turn 透出
     "本轮有错误"。
  2. run_turn：**本轮有 ErrorEvent → 本 turn 以 status="error" 收尾**
     （reason 带错误码摘要），已产出的 partial 内容保留在 `messages`/`text`
     里返回——不丢审计。不做"带工具调用就继续"的灰色地带：流已不完整，
     工具参数可能拼错，限流场景还会放大成本。
- 回归测试：fake provider 流 = [TextDelta, ErrorEvent, （无 StopEvent）] →
  run_turn 返回 status="error"，reason 含错误码；error + 半截 tool_call →
  同样 status="error" 且不执行该工具。

## 组 F：会话切换与持久化

### F1（#3）--sub-agent 下 /switch、/new 必然崩溃

- 位置：`core/sigma/cli.py:724,731` + `core/sigma/sdk.py:562-566`
- 机理：`SessionManager` 跨会话共享同一个 `self._registry`；`InteractiveSession`
  在 `enable_sub_agent=True` 时注册 task 工具、已存在则 `raise ValueError`。
  第二次 `_build`（/switch、/new）必撞。REPL 分派层（repl.py:302）不捕获
  命令异常 → 终结会话。`load_skill`（sdk.py:550）有幂等检查，task 没有——
  两处不一致。
- 修法（二选一，需拍板）：
  - **方案甲（推荐）**：`_build` 给每个会话传 **registry 的克隆**——
    与 `_make_sub_agent_factory`（sdk.py:628）里克隆 registry 的做法同形，
    sdk 侧的 `raise ValueError` 保留（它防的是"调用方预注册 task"，仍然有效）。
    会话间注册表互不影响，语义最干净。
  - 方案乙：sdk 侧改成与 load_skill 相同的"已存在则跳过"。改动小，但
    两个会话共享一个 TaskTool 实例，信箱状态会串——**这是引入新 bug 的修法，不取**。
- 回归测试：SessionManager 带 sub_agent=True → new() → switch_to() 往返，
  不抛；且两个会话的 mailbox 互不可见。

### F2（#9）裸敲 /switch 抛 TypeError，REPL 崩溃

- 位置：`core/sigma/repl.py:268-271`
- 机理：argument 为空时 `handler(manager, index_map)` 少传一个位置参数，
  `_cmd_switch` 的空参分支（182-183）是死代码；分派调用在 try 之外。
- 修法：① 分派统一 `await handler(manager, index_map, argument)`，
  无参命令的 handler 签名统一接收 argument 并忽略；
  ② `await _dispatch(...)` 包 try/except，与 send 的"错误要打印但不终结会话"
  纪律对齐（repl.py:309 同形）。
- 回归测试：裸 `/switch` → 打印用法提示，REPL 循环继续；handler 抛异常 →
  打印错误，REPL 不退出。

### F3（#12）--continue 遇到空目录时新会话不落盘

- 位置：`core/sigma/cli.py:421`
- 机理：返回 `SessionBinding(new_session_id(), SessionTree(), False, 0)`——
  `SessionTree()` 没绑 store，是纯内存树。对比正常新建路径（424-425）用
  `SessionTree(store=store)`。这条分支启动的会话全程不写盘，退出后找不到。
- 修法：与 424-425 同形：`store = JsonlStore(sessions_root, new_id)` +
  `SessionTree(store=store)`。
- 回归测试：空 sessions_root 上 resolve_session(resume=True) →
  发送一条消息后会话文件存在于磁盘。

### F4（#13）会话文件含非法 UTF-8 时整个加载崩溃

- 位置：`core/sigma_session/store.py:198`
- 机理：`open("r", encoding="utf-8")` 无 `errors="replace"`，崩溃写入留下的
  半个多字节字符抛 `UnicodeDecodeError` 穿透到 CLI 顶层——与模块自己声明的
  "坏行跳过、能救多少救多少"直接矛盾；`sessions.py:163` 的 `_preview_one`
  恰恰用了 `errors="replace"`，证明是疏漏。
- 修法：`open("r", encoding="utf-8", errors="replace")`——被替换破坏的那行
  自然落入既有 JSONDecodeError 跳过通道并记行号。
- 回归测试：夹具文件写入半截 UTF-8 字节 → load 跳过该行、其余行正常，
  skipped_lines 含该行号。
