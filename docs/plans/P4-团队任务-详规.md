## 1. 成熟方案取舍(不变,增补)

在 v1 盘点(Claude Code teams 的板+信箱 / LangGraph supervisor / CrewAI / A2A /
AutoGen)之上,v3 增补**pull 模型**依据:常驻 worker 池 + 认领制是"团队"与
"派发"的分界线——task 工具(push,单子任务)保留;multi_agent(pull,团队模式)
新增,两档并存。

## 2. 角色:谁触发哪一行(物理分权)

| 角色 | 驱动者 | 事件(=迁移表行) | 接口落点 |
| --- | --- | --- | --- |
| **Worker**(执行者) | 自己的常驻 loop | claim / heartbeat / finish / fail | `team/worker_board.py` |
| **Lead**(管理者) | 主 agent 的调度轮 | create / reclaim / abandon / cancel | `team/lead_board.py` |
| **Scanner**(系统守护,非 agent) | 引擎轮询调用 | lease_expired / dep_succeeded / abandon(自动) | `team/scanner.py`(两个纯函数 tick) |

- **fail 是 worker 的主动义务**(不是可选项):"成功才汇报"的 worker 崩了任务
  永远挂着——lease 是安全网不是主路径,主动 fail 省掉整个 TTL 等待;
- **Scanner 不能交给任何 agent**(不闭环论证):lease_expired 的触发条件恰恰是
  "某个 agent 死了",指望 agent 自己发现死亡不成立。做成纯函数
  `lease_tick(board, now)` / `dep_tick(board)`,由引擎每轮 poll 调用——
  逻辑独立角色,物理是几行轮询;
- **物理堵门**:三个接口模块分立;TeamBoard 工具壳按调用者身份暴露对应
  action 集(主会话=lead 面,worker=worker 面)——越权调用从"运行时报错"
  变成"工具面上不存在该 action"。
- **①-c 落地形态(2026-09-30 拍板)**:**所有子会话统一 worker 面**。
  主会话注册 lead 面(`role="lead"`);子会话工厂把 `team_board`/`multi_agent`
  从克隆里**排除后重注册 worker 面**(`sdk._make_sub_agent_factory`),
  并**共享主会话的 store/mailbox**——两个实例各造各的 `BoardStore`,
  锁就分成两把,claim 互斥(G-TEAM-2)会变成名义上的。
  排除而不是覆盖:registry 重名抛错且拒绝静默覆盖(G24),必须先排除再注册。
  `multi_agent` 一并排除是 ①-c 的附带组成——它修掉"子会话能自己再 start 一个
  引擎"这个 §5 边界的破口。
  **原来的"物理堵门"只写在文档里**:`role="worker"` 在 `src/` 里零构造,
  子会话拿到的是 lead 面(评审取证)。装配级证据由 **G-TEAM-14** 钉住:
  手工直构两个对象只能证明"类支持 role",证明不了"装配下发了 worker 面"。

## 3. Pull 模型与 multi_agent 引擎

### 3.1 multi_agent 工具(触发入口,新增)

**语义**:主 agent 判定"当前任务复杂/值得并行"时调用——触发即声明团队模式。
默认注册(随 `--sub-agent`),`--no-team` 关。

| action | 行为 |
| --- | --- |
| `start(goal, workers=2)` | 启动团队:建板(lead=主会话)+ spawn N 个常驻 worker(默认 2,上限 3,沿 sub_agent 并发)+ 启动引擎循环;回执含 team_id 与"用 team_board 建任务"指引 |
| `status` | 板渲染 + worker 状态 + 引擎运行态 |
| `stop(reason)` | 收尾:非终态任务 cancel(级联),worker 退出,汇总报告写 lead 信箱 |

**自动收敛**:板全终态(success/dead/cancelled)且无 blocked → 引擎自动等效
stop,worker 退出,汇总写 lead 信箱——主 agent 下一轮 inbox 即见。

### 3.2 Worker loop(常驻认领者,引擎内的 asyncio 任务)

```
while 运行中:
    dep_tick(board); lease_tick(board, now)      # Scanner:引擎代调,每轮 poll
    task = worker_board.try_claim(worker_id)      # Pull:手头没活从 pending 捞
    if task is None:                              # 空转**不退出**:继续轮询等新任务
        if 已收敛: return
        await sleep(POLL_S); continue
    lease = spawn(_heartbeat_loop)                # 引擎自动续租(每 TTL/3)
    try:
        result = await 子会话执行(task)           # 复用 sub_agent 工厂,一任务一隔离子上下文
        await worker_board.try_finish(task, result)   # **幂等**:已不在 running 就跳过
    except 中断/异常:
        await worker_board.try_fail(task, reason)     # attempts+1;worker_lost 通道
```

**两条 ①-c 之后才出现的硬约束(实现必须照做)**

1. **收尾必须幂等**(`try_finish`/`try_fail`):worker 面把 `finish`/`fail`
   **真的交给了 LLM**——子 agent 可以自己收尾。引擎若在 runner 返回后再无条件
   `finish`,就撞非法迁移(`fail+FINISH` 不在表里),`except` 分支里的 `fail`
   再撞一次(`fail+FAIL`),异常从 worker 协程逃出去,而任务停在**非终态的 fail**
   上 ⇒ 引擎永不收敛。**用一个新死锁换掉一个文档不一致,不是修复**。
   `try_*` 在同一事务里回读板:读-判-写与 worker 自己的收尾互斥,没有竞态窗口。
2. **派发文案要如实**:v3 早期文案写着"用 op=finish 收尾没有意义"——①-c 之后
   那是**错的**。现行文案:正常完成直接回结论文本(引擎替你登记);搞不定就
   `op=fail` 写明原因(装死要等 lease 超时才被回收,不划算)。

对应门禁:**G-TEAM-15** 两条(门面幂等 + 引擎不重复收尾)。

### 3.3 与 v1 实现的映射(重构而非重写)

- `board.py` 迁移表**零改动**(裁判不变),增 `lease_deadline/attempts` 字段
  与 `blocked` 态(v3 迁移表:dep 未就绪 create 入 blocked,dep_succeeded 放行);
- `store.py`/`mailbox.py` 不变;
- `team.py` 壳:board/send/inbox 保留,action 集按 role 过滤(§2);
- TaskTool(push 单任务)**原样保留**——两档并存,评测臂互不污染。

**已知代价(①-c 的选择,登记不藏)**:`task` 派发的子 agent **也**是 worker 面
⇒ 子 agent 不能再往板上建任务 / 重派 / 撤销,只能 `list / finish / fail` +
`send / inbox`。

- v1 的"**双向信箱**"完整保留:`send`/`inbox` 不受 role 约束(role 只过滤
  `board` 的 op);
- 变的是 v1"共享任务板"的含义:从"主会话与子 agent 都能写板"收成
  "**只有 lead 建与派,子 agent 只报**";
- G-TEAM-4"派发融合"依然成立(子会话照样注册 team_board),但**语义重写**:
  判定面从"看到 team_board"变成"看到 worker 面的 team_board"。

### 3.4 重试上限与"自动判死"的真实触发条件(C8,星辰 A3 追认)

- **取值**:`max_attempts=3`(板级字段,随板落盘)。
- **依据**:① 单任务三次重派仍未成,大概率是任务本身有问题(需求歧义/依赖缺失),
  继续烧 token 的边际收益骤降;② 三次给 lead 留了两次"换个说法再派"的机会窗口;
  ③ 与 `sub_agent` 的轮数三档同一条纪律——**成本闸的取值必须有可解释的来源,
  不许拍脑袋**。改这个值要连依据一起改。
- **真实触发条件(必须说准,否则日后会按错误理解依赖它)**:自动判死的条件是
  **同一任务被反复推动且每次都失败/超时达到 3 次**——
  涨 `attempts` 的路径只有三条:`FAIL`(worker 认输/异常)、
  `WORKER_LOST`(引擎感知异常)、`LEASE_EXPIRED`(扫描器时间驱动)。
  **静止的 `fail` 任务不会自己涨次数**:它要等 lead `reclaim` 才会被再次推动。
  所以"3 次判死"≠"崩 3 次自动消失";这条链是
  **fail → (lead reclaim | 扫描器 lease/abandon) → 再 fail** 的循环上界。

## 4. 预算(消费纪律)

- `multi_agent` 是**新增工具 schema**,实测 121 token(裸 schema;口径见下);
- **口径纪律(D4 v3 的追加条款)**:预算表比的是**含 `{"type":"function"}`
  信封的整栏实测**——与历史测量一致。可选栏同口径实测 **1441**,
  超旧 cap 1250 达 191。裸 schema 之和只有 985,那是**错口径**:
  一度按它判断"无需上调"并回退过一次,`resident_caps.py` 与 ADR-D4 都记了这笔。
- 结论(星辰已追认 2026-09-30):可选栏 1250→**1500**,总额 5500→**5750**,
  余 59。方向是"分区管理,允许工具 schema 占据较大份额"(A1);**不重划分区**。
- 压缩手段照旧(剥 title/default、极短字段说明);`team_board` 双面 op 集是把
  274 收敛到 197 的那一刀——先报数字,数字自己说话。

## 7. 不做与残余暴露

- **A4 重划常驻区分区**:不做(现状已满足"分区管理";A1 追认的方向只到追认);
- **A5 僵局超时自动 abandon**:不做。残余暴露是**诚实的**:
  lead 收到"失败待决"却不处理 ⇒ 团队仍不收敛(空转、不汇报)。本批次承诺的
  只有"**lead 必然会看到**"(②-b 的通知 + 去重),不承诺"没人管也能自己收摊";
- multi_agent 评测臂(与波 2 一并)。
