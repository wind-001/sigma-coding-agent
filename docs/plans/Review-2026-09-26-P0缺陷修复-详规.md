> 立项:2026-09-26 ｜ 需求方:星辰(对照市面 coding agent 的差距分析,P0 两项) ｜ 状态:**✅ 已落地(2026-09-26,G100–G102 全绿)**
> 前置阅读:`architecture.md` 4.1(错误归一化与压缩的两条触发路径)、`P4-批次5` 详规(增量持久化与悬空修复)

## 0. 需求原话(星辰)

> 先把 P0 的两条修复一下。

两条(差距分析的 P0 判据:**会直接影响可用性的正确性洞**):

1. **`context_overflow` 没有处理器**:`errors.py` 定义了码、架构 4.1 承诺"要能被上层捕获并触发压缩——这是压缩的两条触发路径之一",但全项目无人消费。现状:长会话撞窗口直接死于 provider 报错。
2. **unparsed 工具调用的孤儿 tool_call_id**:`loop._failure_message` 合成 `tool_call_id="unparsed_{index}"` 的 tool_result,但 assistant 消息只含拼装成功的调用块——该 id 在任何 assistant 里都无配对,下一轮请求把它发给 OpenAI 兼容协议会被拒(协议要求 tool 消息逐个应答前文 assistant 的 `tool_calls`)。

## 1. 缺陷一:context_overflow → 恢复(修复 + 重跑)

### 1.1 现状与关键事实

- **provider 的错误只走数据路径**:`openai/provider.py` 全部 `yield ErrorEvent(error=ProviderErrorPayload(...))`,**不抛** `ProviderError`(这是 2026-09-20 的设计:数据/异常分离,事件要可回放)。→ 溢出在 loop 里表现为 `error_summary` 字符串,`TurnResult` 无结构化码。
- 恢复动作的归属:**产品壳**(`InteractiveSession.send`)——压缩知识(`SessionContext.compact`)在 sigma_session,loop 是无状态的、消息视图是 run_turn 启动时的快照,轮中无法重建。

### 1.2 方案

1. **错误码结构化**:`TurnResult` 增加 `error_code: str | None = None`;`_StreamedRound` 收集 `error_codes`(ErrorEvent 的 `error.code`);run_turn 的 error 出口填入(有 `context_overflow` 则优先)。
2. **`send()` 的恢复序列**(重跑,不是轮中续跑):
   - `repair_dangling_tool_results`(错误轮的 partial assistant 可能带未应答 `tool_calls`,直接重发就是协议错;P4-批次5 的修复函数在此复用);
   - **强制压缩一次**(`_compact_for_overflow`:无视阈值直接 `context.compact()`,与"本地估算超阈值"那条路径互补;关压缩/无可压段/压缩异常 → 返回 False);
   - 重跑整轮(`build_messages()` 重建压缩后的视图)。**只恢复一次**:再次溢出说明压缩救不了(历史太短/已压过/单条消息巨大),如实返回 error,不无限循环。
3. **轮前悬空修复成为不变量**:`send()` 每次开跑前统一执行一次悬空修复(此前只在 `__init__` 做)——错误轮留下的悬空不该毒死**下一轮** send。
4. 异常路径(`provider.stream` 抛 `ProviderError`)做**防御性捕获**,按同一恢复策略处理——当前 OpenAI 兼容 provider 不抛,但这是 `BaseProvider` 允许的形态,换实现不该让恢复失效。

### 1.3 被否的备选

- **轮中续跑**:loop 拿不到压缩后的视图(快照),改它违反"无状态 loop"的形状(详规 3.8.1)。
- **在 loop 里接压缩回调**:把 sigma_session 的知识塞进回调签名,等于让 loop 间接认识会话。

## 2. 缺陷二:unparsed 失败调用 → 尾部 user 注记

### 2.1 方案

`_failure_message` 从"合成 tool_result"改为 **`LlmMessageWrapper(UserMessage)` 系统注记**:`[系统注记] 你上一次的第 N 个工具调用无法解析,没有被接受、也没有执行。原始参数片段:…\n错误:…\n请修正参数后重新调用。`

**为什么是 user 注记**(三个备选里选它):

| 备选 | 判决 |
| --- | --- |
| ✅ user 注记 | 协议任何位置合法;与**压缩摘要/todo 提醒/信箱回报**同一既有模式;模型仍看得到"调用未被接受";`parse_error` 全文可见 |
| ❌ 把失败调用塞回 assistant 当 tool_call 块 | 反转既有门槛(「失败的调用不该伪装成一次合法调用」),且必须伪造 `arguments` |
| ❌ 静默丢弃 | 违反"宁可崩不要错"/「未知不静默」家族纪律 |

连带:**repair 路径天然不受影响**——unparsed 调用从不在 assistant 里,不产生悬空。
