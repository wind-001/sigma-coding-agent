# ADR-D2：harness 边界画到会话管理为止

> 状态：待确认
> 日期：2026-09-20
> 关联：`docs/architecture.md` 第 1 节 D2、第 2.3 节

## 背景

「harness 边界画在哪一层」是立项前的五个待拍板问题之一。
参考对象 Pi 提供了四种运行模式（交互 / print / RPC / SDK），
外加实验性的远程 protocol / client / server 与多实例编排层。
问题是 sigma 要覆盖到哪一层。

## 选项

| 选项 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 只做 agent loop + 工具 | 最窄，只有引擎 | 最少的代码量 | 无法独立运行，不能演示端到端任务 |
| B. 覆盖到会话管理 | 引擎 + 工具 + 会话 + 上下文；CLI 做薄壳；保留 SDK 入口 | ① 能端到端跑通并演示<br>② SDK 入口成本极低，且能把项目性质从「脚本」变成「可复用 harness」<br>③ 与手绘架构图第 1–3 层对齐 | 需要维护一层 CLI |
| C. 覆盖到远程能力 | 再加 RPC / HTTP server / 多实例编排 | 与 Pi 完全对齐 | ① Pi 自身这部分仍是实验能力<br>② 对作品集是零架构信号<br>③ 大幅增加测试与 CI 难度 |

## 决定

**选 B：覆盖到会话管理为止。做 SDK + REPL + 一次性模式；不做 RPC / HTTP server / 多实例编排。**

## 后果

**变好的地方：**
- 有明确的可演示闭环，且 SDK 让「可复用」这个论断变成可验证的事实（写一个 pytest 用 SDK 跑通即可证明）。
- 削减掉的部分恰好是测试成本最高的部分，CI 能保持轻量。

**变差的地方：**
- **与手绘架构图不一致。** 图里的「产品壳」包含 Slack Bot / Web UI / RPC Mode，本决定砍掉了这三项。
- 无法演示「多个 agent 实例协作」。
