# ADR-D3：扩展层是运行时状态，但只做工具级热重载

> 状态：**部分确认**（形态与继承制已拍板 a2，代价栏待填）
> 日期：2026-09-20
> 关联：`docs/architecture.md` 第 1 节 D3、第 4.4 节、第 0.3 节

## 背景

Pi 最亮眼的能力是**运行时自扩展**：agent 改写自己的扩展文件，jiti 热重载，
当轮即生效，不重启会话。这要求扩展层是**运行时可变状态**，而不是编译期插件注册表。

在 Python 里复现这件事，正确性风险集中在三处：

1. 模块级状态被残留或意外重置，行为不确定
2. 已注册的旧对象仍被某个长生命周期容器持有引用，症状是「改了代码但行为没变」
3. 重载过程中抛异常，注册表处于半更新状态

## 选项

| 选项 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 编译期注册表 | 启动时装配，不支持热重载 | 最简单，无正确性风险 | 放弃全部自扩展能力，等于把这个差异化直接删掉 |
| B. 工具级热重载 | 扩展层是运行时状态，但热重载范围限定在「工具注册表 + 钩子注册表整体替换」，并把「调用方不得缓存实例」写成 CI 契约 | ① 保住核心能力<br>② 边界清晰，三个失败场景可穷举、可单测<br>③ 效果上允许 agent 给自己写工具（写文件 + 触发热重载） | ① 能力范围比 Pi 小<br>② 需要在 Python 里自己实现模块加载与替换 |
| C. 全量自改写 | agent 可改任意扩展代码并即时生效 | 与 Pi 完全对齐 | 上面三个风险无法穷举，行为不确定，经不起追问 |

## 决定

**选 B：扩展层是运行时状态，热重载限定在工具/钩子注册表；禁止调用方缓存 `ToolDefinition` 实例。**

**2026-09-20 拍板（a2）：扩展与内置工具走同一个 ABC 基类。**

```python
class BaseTool(ABC):
    name: str = ""
    description: str = ""

    @property
    @abstractmethod
    def params(self) -> type[BaseModel]: ...

    @abstractmethod
    async def run(self, args: BaseModel, ctx: ToolContext) -> ToolResult: ...
```

扩展文件里定义的是 `BaseTool` 的**子类**，注册时走 `registry.register(tool: BaseTool)`。
这个签名本身就是约束：**传不进"碰巧长得像工具"的鸭子类型对象**，
所以"扩展与内置同路径"不再只是一句约定，而是类型层面的事实。

同时新增一条 CI 门禁（见 `architecture.md` 第 8 节）：
单测断言所有工具实现都是 `BaseTool` 的子类，且直接实例化 `BaseTool` 必须抛 `TypeError`。

## 后果

**变好的地方：**
- 三个失败场景（新模块导入抛异常 / 新模块空注册 / 与内置工具重名）都有确定行为，
  且各配一个单测。
- 「不允许扩展静默覆盖内置工具」成为明确规则，避免了最难排查的一类 bug。

**变差的地方：**
- 不能声称「agent 可以任意改写自己」。演示时需要解释这不是能力缺失而是边界选择。
- 实现 `_import_fresh` 时不能用 `importlib.reload()`（它保留同一个 module 对象，
  其它模块以 `from x import y` 持有的旧引用不会更新），必须每次生成新 module 对象。

## 何时应该重新考虑

- Python 侧有稳定的热重载方案被验证可用（例如某个成熟的模块热重载库）。
- 三个失败场景中有任何一个被证明无法做到确定可控——此时应**进一步收窄**，
  而不是保留不确定行为。
