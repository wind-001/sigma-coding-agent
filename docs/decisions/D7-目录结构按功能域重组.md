# ADR-D7：目录结构按功能域重组（五包 → 15 功能域子包）

> 状态：已确认（2026-09-29 星辰拍板，7 项全按推荐项执行）
> 日期：2026-09-29
> 关联：`docs/architecture.md` 第 3 / 8 节；`docs/plans/P6-目录结构重构-详规.md`

## 背景

D1–D6 拍下的五包布局（`sigma_ai` / `sigma_agent` / `sigma_session` /
`sigma_tools` / 应用壳 `sigma`）以"架构层"命名。用了三个月后暴露出的问题：

1. **包名答不出"系统做什么"**——面试官/新读者无法从 `sigma_session` 读出
   "会话管理"，从 `sigma_agent` 读出"循环与调度"；"钩子系统在哪"要跨三个包才能答全
   （loop 发事件、trace/persist 是订阅者、审批又单住一处）。
2. **私有模块靠 `_` 前缀承担本该目录承担的信息**：`_paths.py` 实为路径沙箱、
   `checkpoint.py` 实为影子 git 回滚——有实无名。
3. 系统提示词硬编码在 `sdk.py`（1102 行）中间；装配点、可观测层都存在
   但埋得不显眼。
4. 触发契机：对标一份同类岗位简历的目录布局
   （config/agent/runtime/sessions/memory/tools/skills/hooks/events/security/cli），
   大方向可对齐，逐项判断哪些有实、哪些是负债。

约束：重构是**结构性**的——零行为变更，常驻区字节（系统提示词 + 工具 schema）
逐字节不变；724 单测 + mypy strict + import-linter 三道门禁每批次必须全绿。

## 选项

| 选项 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A | 维持五包，只做内部文件改名 | 改动最小 | "包名答不出功能"的核心问题原样保留 |
| B | 按简历布局逐目录照抄（含 infrastructure/、mailbox、MemoryHub 多 provider） | 与简历词汇完全一致 | sigma 没有的东西（db/redis/mailbox）要造空壳；面试被问"redis 干嘛用的"答不上，负债 |
| C | 单顶层包 + 功能域子包，**有实才有名**：简历词汇里 sigma 真有的目录全落位，没有的不虚构；import-linter 层表重写为线性栈 | 结构可对简历叙事；每个目录都能答深；层表语义从"线性栈+豁免"变纯线性栈 | 全树搬移 + 全库 import 改写，量大；旧文档/契约/CI 全部要同步 |

## 决定

选 C。15 个功能域子包：`cli` `sdk` `runtime` `agent` `providers` `events`
`hooks` `tools` `skills` `sessions` `memory` `security` `observability`
`prompts` `config`；`infrastructure/`、`agent/mailbox`、`event_bus`、
MCP config **不设**——没有实现就没有目录，虚设目录是面试负债不是资产。
分四批落地（A 搬迁 → B 命名 → C 减封装 → D 文档同步），每批独立过全部
门禁；pydantic 选型判据同步从"尽量 BaseModel"改为"三问判定"（存留清单见
`docs/pydantic-存留清单.md`，42 → 留 36 / 降 6）。

## 后果

**变好的地方：**

- 目录名 = 简历词汇 = 面试叙事：`runtime/`（核心循环）、`providers/`（多协议）、
  `sessions/`+`memory/`（双层上下文治理）、`security/`（沙箱+审批）、
  `observability/`、`prompts/`——每个都能往下答三层。
- 线性层表让 import-linter 语义与文档一致，旧 `independence` 契约及其
  "兄弟层"心智负担删除；hooks/events 的"订阅者/被订阅"关系从事实升级为
  包边界（events 纯定义零行为）。
- 技能、钩子、审批、观测从"散落三处"收敛为单一功能域。

**变差的地方：**

- `git blame` / 历史引用断一代：所有旧模块路径在文档与对话记录里大量存在，
  查历史要经过 `git log --follow`；`scripts/gate_injection_*` 历史脚本里
  的旧路径常量**刻意不改**（它们是一次性证据，改了就是篡改历史）。
- 一次性搬运 163 文件，review 粒度粗：靠"结构变更与功能变更不混提交"
  + 三道门禁兜底，但 diff 本身不可逐行人读。
- 15 个子包对 4.6k 行 src 来说偏细，小包（memory/ 只有 1 个实现文件）
  有"目录比代码多"的观感——这是为叙事对齐支付的税，已知的。

## 何时应该重新考虑

- 出现真实的 infrastructure 需求（要接数据库/队列）而 `security/`+`sessions/`
  开始被塞进不相干的存储代码时——那是该建 `infrastructure/` 的信号，而不是
  继续往功能域里塞。
- 子 agent 协作从"单层派发"演进到需要 mailbox/team_task 语义时，
  再评估 `agent/` 是否要长出协作子包——届时要有实测数据支撑。
- 若常驻区预算表因结构演进再次重排，注意 §8 的教训：**层表排位必须逐边实测**。
