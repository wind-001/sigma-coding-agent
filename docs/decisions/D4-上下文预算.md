# ADR-D4：常驻上下文 ≤ 3,500 token，且会话内逐字节稳定

> 状态：待确认
> 日期：2026-09-20
> 关联：`docs/architecture.md` 第 1 节 D4、第 5 节

## 背景

制约 agent 成本的真正瓶颈是上下文窗口。Pi 的做法是把系统提示词压到 1,000 token
以下（有时约 200），并拒绝 MCP，理由是「某些 MCP 服务器会往上下文塞 13,700+ token」。

但压小只是第一层。第二层是 **prompt cache**：如果常驻区在会话中途发生任何变化，
缓存从变化点起全部失效，成本会成倍上升。

## 选项

| 选项 | 说明 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A. 照抄 Pi，直接压到 <1,000 token | 抄结论 | 起点明确 | Pi 的前提是「前沿模型已被 RL 训练过编码任务」。换模型或换领域后该前提不成立，这个值可能不足 |
| B. 定预算 + 稳定性断言 | 常驻区给 3,500 token 预算，各分区定上限；**并在代码里断言会话内常驻区哈希不变** | ① 预算可拆解、可监控<br>② 断言把「容易违反的约定」变成「不可违反的约束」，成本为零<br>③ 让 prompt cache 命中率成为一个可测指标 | 需要额外实现预算检查与断言 |
| C. 不设预算 | 动态拼接，按需注入 | 灵活 | 成本不可控，缓存必然失效，且无法解释成本为何上升 |

## 决定

**选 B。常驻区预算 3,500 token，分区如下；并在 `Context` 对象上冻结常驻区哈希，每轮校验。**

| 分区 | 预算（token） |
| --- | --- |
| 系统提示词 | ≤ 800 |
| 工具 schema（4 个） | ~700 |
| `AGENTS.md` | ≤ 1,500 |
| 技能索引（name + description） | ≤ 600 |
| checkpoint / 摘要 | ≤ 1,000 |

## 后果

**变好的地方：**
- 成本结构可解释：常驻 vs 动态分开计量。
- `prompt cache 命中率` 成为一个可以报告出来的指标（provider 返回的 `cached_tokens / prompt_tokens`）。

**变差的地方：**
- 禁止了「按任务类型动态调整系统提示词」这类做法。某些场景下这是有用的，但为了缓存必须禁止。
- 系统提示词长度不抄 Pi 的结论，改为必须自己跑 ablation 定值——**这会让 P5 多出一组实验**。
