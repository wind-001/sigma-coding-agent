## 二、缺陷清单（按严重度）

### D1 严重·语义 —— rollback 会退化成空操作【已修复】
- **现象（真实触发的 bug）**：首版把快照记在"推进之后"，运行用例4报 `AssertionError: 回滚后计数应 2，实际 3`——**第一次 rollback 什么都没撤**。
- **根因**：最新快照 == 当前状态，恢复自身即空操作，`step_counter` 永不下降，**回滚功能等于不存在**。
- **规格责任**：任务只说"最多 5 条快照"，从未定义快照记录**前态还是后态**。选后态则功能失效。
- **处置**：改为推进前记录前态快照，实测 3→2→1→0 正常，存留序列 `[2,3,4,5,6]`。
- **建议**：规格补一句"快照必须能撤销对应步"，否则功能正确性完全取决于实现者的隐式选择。

### D2 严重·规格 —— 三个函数均无法产出 error 状态
- **现象**：`new_session`/`advance_step`/`rollback` **没有任何一个**能把 status 置为 error。
- **证据**：用例4实测"全程仅出现 ready/running"。
- **性质**：这不是实现选择问题，是**两条约束冲突**——"status 仅 ready/running/error" ∧ "只实现这三个函数"在逻辑上不可同时满足。
- **v2 更正**：v1 称 ERROR 分支"死代码、永远不可达、需反射才能触达"，**不准确**。实测普通属性赋值即可走到该分支：
  ```
  m._sessions["c"].status = SessionStatus.ERROR   # 非反射，纯赋值
  m.advance_step("c")  ->  SessionError: error 终态不可推进: c
  ```
  准确表述应为：**经三个公开函数不可达；经状态属性赋值可达**。该分支有防护能力，
  只是这能力无法通过公开 API 被正常使用。
- **建议**：二选一——① 规格增加失败入口；② 明确 error 为保留字，当前 API 下不产出。

### D3 中·语义 —— "最多 5 条"的淘汰策略未定义
- **现象**：达上限后是拒绝新快照、覆盖最旧、还是丢弃最旧？任务未说。本次取 FIFO 丢最旧。
- **后果**：FIFO 使 6 步前的历史永久不可回滚，且**回滚次数被静默限制为最多 5 次**。
- **风险**：使用者易把"存 5 条快照"误当成"可无限回滚到任意历史点"，两者语义不同。

### D4 中·边界 —— 引入了任务未要求的行为（扩功能嫌疑）
- 已引入：① 重复 `session_id` 抛 `SessionError`；② `session_id=None` 时自动生成 uuid4。
- **矛盾**：任务说"不扩功能"，但若**不**拒绝重复 ID，重复创建会静默覆盖已有会话（后果更严重）；若不支持自动 ID，则 `new_session()` 无所适从。
- **建议**：规格明确重复 ID 是覆盖/报错/未定义，以及是否要求自动 ID。

### D5 中·健壮性 —— 无并发保护
- `SessionManager._sessions`、`Session.snapshots` 均为可变共享状态，`advance_step` 是"读-改-写"三步非原子操作。
- 多线程下会丢步或计数错乱。任务未要求线程安全，故**仅登记不修**（修即扩功能）。

### D6 中·对象语义 —— 返回值是内部可变对象的别名（v2 新增）
- **现象**：三个函数都返回**内部 Session 对象本身**而非副本。
- **实测证据**：
  ```
  r1 = m.advance_step("a")     # r1.step_counter == 1
  m.advance_step("a"); m.advance_step("a")
  r1.step_counter              # -> 3，而非留存的 1
  r1 is m._sessions["a"]       # -> True
  ```
- **后果**：调用方**无法持有某一步的历史状态**。常见的 `prev = advance_step(sid)` 记录法
  会被后续调用静默篡改，且无任何报错。这是本轮 review 新发现的**真缺陷**，v1 报告漏报。
- **对比**：D1 已修（快照存的是值拷贝），但**对外返回值仍是活引用**，同一类问题没修干净。
- **建议**：返回值改为 `Snapshot`（值对象）或 `Session` 的只读副本；至少写进文档。

### D7 低·状态机一致性 —— 状态约束无强制力
- `Session` 为可变对象且被直接返回，调用方可绕过三个函数直接写 `status`/`step_counter`。
- D2 的实测更正恰好证明这一点：赋值即可把会话推到 error，绕过所有校验。
- 说明"仅三态"只是约定，不是不变量；如需强制，Session 应对调用方只读。

### D8 低·可测性 —— 缺只读观测接口
- 三个动作函数都是"改状态"，没有任何"只读"入口。（v1 此处误写为"状态只能靠返回值读取"，
  实际 `_sessions` 可读、返回值可读，问题不是读不到，而是**没有受支持的只读入口**，
  导致测试要么越界访问私有属性、要么依赖带副作用调用的返回值。）
- **真实后果**：测试初版两处调用 `get_session`，导致用例 3、4 FAIL（`AttributeError`）；删掉后才符合"不扩功能"。
- **建议**：规格明确是否允许一个只读查询接口（如 `get_session`）。

### D9 低·可读性 —— 错误不可分类捕获
- 所有违例都抛同一个 `SessionError`，调用方无法用 `except` 区分"会话不存在 / 终态不可推进 / 快照不足"，只能匹配字符串。任务对错误类型无约束，登记备参。

### D10 中·测试契约 —— 断言依赖了被判为缺陷的行为（v3 新增）
- **现象**：用例3 的隔离断言依赖 D6 的别名行为：
  ```
  other = mgr.new_session("s4"); mgr.advance_step("s4")
  assert other.step_counter == 1
  ```
- **实测（探针3）**：活引用语义下 `other.step_counter = 1`（PASS）；若改为返回副本则 `= 0`（**FAIL**）。
- **含义**：**修 D6 会打破用例3**。测试把「返回值是活引用」这一被本报告判为缺陷的行为，焊死成了期望契约。
- **性质**：不同于 §4.2 的「规格空白」，这是**测试断言与报告结论直接冲突**——两者必有一错。
- **建议**：先拍板 D6（改或不改），再据此改用例3 的观测方式（如经快照观察，而非经返回值别名）。

## 三、结论

1. **实现自身的真实缺陷**：D1（已修复，运行中真实暴露）+ **D6 别名泄漏（未修，新发现）**。
2. **规格层面的硬伤**：D2（三个函数产不出 error）——最值得先拍板。
3. **语义空白需拍板**：D1 快照方向、D3 淘汰策略、D4 重复 ID。不定义则换个人实现会得到
   **行为不同但都"通过测试"**的两套代码——D1 已实证该风险。
4. 规则 1/9/12/13/14 有可核验证据；规则 3/11 为部分符合。

## 四、测试盲区与断言性质标注（v2 新增）

### 4.1 未被任何用例覆盖的路径
| 路径 | 现状 | 风险 |
|---|---|---|
| error 态拒绝分支（D2） | 无用例。走公开 API 无法构造 | 防护逻辑无从验证 |
| 返回值别名（D6） | 无用例 | 真缺陷在测试全绿下隐藏 |
| `rollback → ready → 再 advance` | 无用例（实测可用：ready/0 → running/1） | 恢复路径无回归保护 |
| 多会话交错回滚 | 仅测计数隔离，未测快照隔离 | 快照串扰未被证明 |

### 4.2 断言性质标注：哪些是"规格空白下的实现裁定"
以下断言固化的是**任务从未规定的语义**，不应被后来者当成需求：

| 断言位置 | 固化内容 | 对应缺陷 |
|---|---|---|
| 用例1 `重复 ID 被拦截` | 重复 ID 报错（也可覆盖或不定义） | D4 |
| 用例1 `自动 ID 为 32 位十六进制` | 自动生成 ID 的格式 | D4 |
| 用例3 `kept == [2,3,4,5,6]` | **FIFO 淘汰 + 前态快照**双重裁定 | D1 / D3 |
| 用例4 `回滚到 ready/0` | 消费式回滚、可退到初始态 | D1 |

**已实施**：上表 4 处断言已就地加 `# SPEC-BLANK:` 注释
（`grep -c SPEC-BLANK test_session_manager.py` = 4，加注后测试仍 4/4 PASS），
使"实现裁定"与"规格要求"在源码里可直接区分。

### 4.3 测试与结论的冲突项（v3 新增）
| 断言位置 | 与报告结论的冲突 | 处置 |
|---|---|---|
| 用例3 `other.step_counter == 1` | 依赖 D6 判为缺陷的别名行为 | 待 D6 拍板后改观测方式 |

**提示**：这类冲突比「规格空白」更危险——规格空白只是没规定，而冲突意味着**结论与代码不一致，必有一错**。
