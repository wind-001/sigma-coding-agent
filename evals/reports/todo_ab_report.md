## 结论

1. **通过率无差异**：4 : 4，全部 PASS（判定器 PytestJudge，exit 0）。
2. **有 todo 臂全面更贵**：prompt token **+87%**（208k vs 111k）、completion +51%、
   轮数 +42%（47 vs 33）、工具调用 +53%。方向一致（4 条里 3 条 B2 轮数更多）。
3. **解释**：这批任务的长度 2–16 轮，拆解计划本身要花轮次与 token；
   「先 create 拆解」在有 todo 臂是提示词纪律（工作方式第 3 条），
   模型照做了，但任务短到拆解收益 < 拆解成本。
4. **对 30 条正式集的含义**：todo 消融在这类**修 bug 短任务**上没有区分度
   （与试水时「B0 无区分度」同构）。todo 的 A/B 想测出差异，需要**长程任务**
   （原 P4-todo 详规想造 4 条长程任务的理由仍然成立）——建议 30 条正式集
   保持 todo 恒开（B2 口径），todo 的价值另立长程任务集再测。

## 编排层实战记录（task 工具第一次真跑）

- 编排：`evals/todo_ab.py`——真 sigma 主 agent（`enable_sub_agent=True`），
  `task` dispatch 两个子 agent **并行**跑两臂；子 agent 用 bash 调 task_runner。
- 走到的机制：主 agent todo create（`.sigma/todo.json`）→ dispatch ×2 →
  收尾兜底等子任务（G86 路径）→ 信箱回报注入。两臂写报告互不冲突
  （档位名后缀），临时工作区互不影响。
- 观察到的行为：主 agent **先派了 B 臂（sa1），A 臂（sa2）晚数分钟才派出**
  （子任务调度顺序由模型决定，非固定）；API 高峰期单条任务 20 分钟级，
  编排全程 44 分钟后由运行器接管串行补跑最后一条（syn-004 B2，1 轮决策
  即完成）——**编排层适合「并行拆活」，不适合「等慢 IO」**：等待期间
  主 agent 的轮次纯烧 token，收益为零。
- 子会话 token 用量随回报回传（D-A1）在本轮生效，但编排层被提前终止，
  其用量未落盘——下次跑完应在报告里记录编排层自身成本。
